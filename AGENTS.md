# AGENTS.md

**litestream-rs** (working name): an in-process Rust port of Litestream 0.5.x. Read `docs/PLAN.md` and `docs/decisions.md` before any work; they fix decisions that task plans may not reopen. A change that settles a trade-off (a default, a stop or snapshot rule, a user-visible name, a cost accepted) adds its entry to `docs/decisions.md` in the same pull request, marked as delegated when an agent decided it for the owner.

## The contract
- The replica is the contract: bucket layout plus LTX v3 files. Tolerant reader (everything Go v0.5.0 and later wrote), strict writer (Go v0.5.16 and later must read it).
- Behaviour may differ from Go where Go is wrong. Never silently wrong: a request that cannot be met exactly is an error, never a shorter history.
- Equality with Go is defined on restored database pages, never on LTX bytes (the LZ4 compressors differ).

## Design rules
- Invariants live in types. A value that exists is valid: constructors return `Option` or `Result`, fields are private. Prefer a type that cannot hold the bad state over a runtime check, and a runtime check over an assert.
- Closed enums for states, faults and causes; every `match` on them is exhaustive (the wildcard-arm lints enforce it). A new variant must break the build everywhere it matters.
- Sans-IO core: decisions are pure functions over typed inputs; I/O sits behind traits (`Clock`, `Sleeper`, `Entropy`, `ObjectStore` for the replica and for local staging, `WalSource`, `PageSource`, `Checkpointer`, `DatabaseSink`) so the simulator can drive every path.
- Never use bytes that were not verified on the read that produced them.
- Bounded everything: channels, retries, fan-in, memory per file. No unbounded queue. Every retry wait is capped, and a failure that persists is a typed degraded state the health handle reports (D7); it never retries silently and never spins.
- No panic in release builds. Assertions come in three tiers: `debug_assert!` for cheap pre and postconditions (positive and negative space); `invariant!(cond, BugSite::X)` for invariants whose violation release must report, a panic in debug and test builds and `Fault::Bug` in release, which rebuilds the engine instead of killing the host; the `verify` feature (`lsr_core::VERIFY`, on in the sim, fuzz and tests, off in release) for expensive checks.
- No caching and no parallelism unless a measurement in the PR justifies it.

## Rust style
- The lint set is in `Cargo.toml`; gates run with `-D warnings`. No `unwrap`, `expect`, `panic`, `as`, indexing or unchecked arithmetic in non-test code. An exception is `#[expect(lint, reason = "the invariant")]` on the smallest item, never `allow`.
- Functions are at most 70 lines.
- `unsafe` is denied workspace-wide; only the SQLite crate may opt in, one reasoned `#[expect(unsafe_code)]` per site. The one other exception is the counting allocator the memory gates install (`crates/core/tests/core/heap.rs`; `GlobalAlloc` is an unsafe trait); it lives in a test binary and is never linked into a shipped one.
- Errors are typed (`thiserror`), one enum per crate boundary, each variant carrying what a caller needs to act. No stringly errors, no `anyhow` in library crates.
- Every public item has a doc comment. Comments say why, never what. Mechanism goes in the module's `//!` doc.
- No mid-sentence em dashes in docs or comments.

## Tests
- Test the contract, not the implementation. Every decoder error variant has a test that produces it; every enum variant of a state, fault or cause has a scenario.
- Fixtures are synthetic databases or files generated by pinned Go tools. Never a capture of anyone's real data.
- A bug fix starts with a test that fails on the old code.
- Go compatibility is differential: generate with Go, read with Rust, and the reverse, comparing restored pages.
- Tests wait on conditions, never on the clock. No sleeps.
- A test that needs something outside the process (MinIO, Go builds, Tigris, a C compiler, disk) gets it through `lsr_core::needs` and fails without it; the only skip is the runner's `LSR_SKIP=<name>`, never under CI. A walk over files or fixtures asserts it found some. A hang is killed by nextest (`.config/nextest.toml`), not waited out.
- Property tests (`proptest`) for every codec and every pure planner. Keep each test under a second where possible.
- A crate's integration tests are one binary, `crates/<name>/tests/<name>/main.rs`, with a module per file: add a module there, not a new `tests/*.rs` file, which would link a binary of its own (lsr-compat's `layout` test refuses a second one). A test that starts the binary again as a child names its test by full path (`sidecar::exec_child`), or uses the crate root's `child_process_entry` (lsr-sqlite).

## Build and commands
- Development runs on Linux and macOS; CI runs on Linux. `just check` passes on both (on macOS it skips `upstream-test-map-fresh`, since the test map names Linux-only tests).
- `just check` is the land gate: format, clippy, tests. Scope while iterating: `cargo clippy -p <crate> --all-targets -- -D warnings`, `cargo nextest run -p <crate> <test name>`. The README lists which tests need nothing, Docker, Go or Tigris.
- `just upstream` clones the pinned upstream sources into `.upstream/` (read-only reference: `litestream` at 041a8c3, `ltx` at v0.5.3). [docs/go-terms.md](docs/go-terms.md) maps our terms to Go's, LTX's and SQLite's for the same things.
- Crates live in `crates/<name>` and are named `lsr-<name>` (working prefix).
- New runtime dependencies: prefer none. Dev- and test-only dependencies that strengthen correctness checking (fuzzing, schedule exploration, sanitizer support) are welcome. Either way, each one is named in the report with why and its license. Every dependency, external or `lsr-*`, is declared once in the root `[workspace.dependencies]` and referenced as `name.workspace = true`; a crate may add features, never a version or path. (The `fuzz/` crate is outside the workspace and keeps its own.)

## Branches and landing
- The repository lives on GitHub (`origin`, github.com/emschwartz/litestream-rs); work lands on its `main`, which stays green.
- Work happens on a branch in a worktree under `.worktrees/<name>` (`just spawn <name>`, from the main checkout), with its own `CARGO_TARGET_DIR` left at the default inside the worktree. A worktree shares the main checkout's `.upstream/` (the scripts and the compat harness find it there).
- Each change is a pull request against `main` from a `claude/<name>` branch. The parent session squash-merges it, once its own CI is green and it has no textual conflict (`docs/decisions.md` D31), so `main` holds no merge commits and each PR is one commit whose subject is the PR title. The PR title must pass `just commit-check`. An open branch may merge `main` in to resolve a conflict (the squash drops that merge commit); it is never rebased or force-pushed. Avoid stacking PRs: after the base is squash-merged, the PR on top merges `main` in before it lands.
- A session pushes its own branch with `scripts/push-claude-branch.sh` (no arguments: it pushes the current `claude/*` branch to the same name, and is the one push allowed without a prompt) and opens its pull request when asked to. It never pushes to another session's branch or to `main`, and does not comment on GitHub unless asked.
- Everything Claude authors here that others see (pull request bodies, issues, comments) says it was authored by Claude and names the full versioned model slug, for example "Authored by Claude (claude-opus-5-5)". It never speaks as the owner.
- Commit messages follow Conventional Commits (commitizen's default format): a subject `type(scope): summary`, imperative, lower-case after the colon, at most 72 characters, no trailing period; a blank line; a body that says why; optional footers.
  - Types: `feat` (new behaviour), `fix` (a bug), `perf`, `refactor` (no behaviour change), `test`, `docs`, `build` (dependencies, Cargo, the justfile), `ci`, `chore`, `revert`.
  - Scope: the crate without its `lsr-` prefix (`ltx`, `wal`, `core`, `store-s3`, `store-fs`, `sqlite`, `replica`, `config`, `sidecar`, `sim`, `history`, `compat`, `cli`, `fuzzing`), or `plan` for `docs/PLAN.md` and `docs/plans/`, or `deps`, `ci`, `lint`. Omit it only when a change spans the whole workspace.
  - A change that breaks a public API or the replica format takes `!` after the scope and a `BREAKING CHANGE:` footer saying what breaks.
  - Decisions made mid-task are `Call: <what> (why; cost if wrong)` footers.
  - `just commit-check` checks the subjects of the commits on the branch since local `main` (or `origin/main` when there is none; `just commit-check <base>` names another).
- Write every commit message for an outsider who has not read the plans: say what the change does to the code or the behaviour, in plain words. No plan shorthand in the subject or body (task numbers like "task 8t" or "item 10", ruling and decision codes like P5, D7 or F1, spike or gap ids like S1 or G4, "phase 2 exit"). When the plan's reasoning matters, explain it in a sentence and point at the document by path, for example "see docs/plans/phase-3-syncing.md". Example: `fix(store-s3): send the signed content length on empty uploads`.

## Done
A task ends at a verified commit: `just check` green on the branch, tests named in the task present and passing, docs updated where behaviour is described.
