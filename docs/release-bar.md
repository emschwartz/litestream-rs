# Release bar: what must be true before first use

Authored by Claude (claude-fable-5-2). The owner set the direction on 2026-11-22: no use at all until every gate is met, the strongest thresholds offered, and AWS S3 and Cloudflare R2 as first-class targets beside Tigris. A gate's threshold changes only with an entry in `docs/decisions.md`.

**Verdict today: 0 of 16 gates met, 15 not met, 1 unknown.** Status was read at `origin/main` aa572a1 on 2026-11-22, from the repository, CI runs, issues and open pull requests. Nothing was built or run to write it.

"First use" means any real application on Tigris, AWS S3 or Cloudflare R2, with Go Litestream still able to take over. No gate depends on one application's rollout. A gate is met only on the release-candidate commit (R14). Any change to an engine crate after that commit resets every gate marked **rc**.

Refs: [#99](https://github.com/emschwartz/litestream-rs/issues/99), [#115](https://github.com/emschwartz/litestream-rs/issues/115), [#94](https://github.com/emschwartz/litestream-rs/issues/94), [#86](https://github.com/emschwartz/litestream-rs/pull/86), [#89](https://github.com/emschwartz/litestream-rs/pull/89), [#96](https://github.com/emschwartz/litestream-rs/pull/96), [#97](https://github.com/emschwartz/litestream-rs/pull/97), [#110](https://github.com/emschwartz/litestream-rs/pull/110), [#111](https://github.com/emschwartz/litestream-rs/pull/111), [#119](https://github.com/emschwartz/litestream-rs/pull/119).

## Notes the table cannot carry

**Why these numbers.**

- **R4, ten million seeds.** Zero failures in N trials bounds the failure rate at 3/N with 95% confidence, so ten million seeds rule out defects that one seed in 3.3 million would hit. CI ran 17,329 seeds in 900 s, about 19 a second on one runner, so ten million cost about 145 runner-hours: 25 six-hour jobs in one night, or 8 three-hour jobs a night for a week. The long seeds run about 100 times slower each, so 1,000 of them cost about 1.5 runner-hours. The count is not the limit. Fidelity of the model is, which is what R5, R7, R10, R11 and R16 are for.
- **R5, 30 of 30, twice.** If true recall is r, all of n plants are caught with probability r to the n. Solving r^n = 0.05 for r = 0.90 gives n = 28.4, so 30 of 30 gives a 95% lower bound of 90.5% (0.05^(1/30)). One miss drops the bound to about 85%, which is why batch 2 allows none. If batch 1 is also clean the pooled 60 of 60 gives 95.1%. Only batch 2 is the measurement: batch 1 tunes the checkers, and a checker fixed for a known miss proves nothing about the next unknown one. The swarm floor of 24 of 30 is a point estimate of 80%, against 7 of 22 measured.
- **R7, 10,000 and 100,000 cycles.** The same rule of three: under 0.03% per LazyFS cycle and under 0.003% per crash-law cycle, for that fault mix. A LazyFS cycle takes about 3 s, so about 8 hours. The crash-law campaign runs 1,200 cycles in about 2 minutes on 4 cores, so about 3 hours.
- **R10, 14 days and 168 restarts.** Zero failures in 168 restarts bound the per-restart rate at 1.8% per provider, and 504 over three providers at 0.6%. That is weak next to R7, which carries the statistical bound. The soak is there to meet what nobody modelled, where one occurrence is the finding. The 12-hour soak saw 10 throttles and 1 transient error, so 14 days should see about 280 and 28 per provider. A real outage cannot be scheduled, hence the two drills. At one sync a second the run makes at most 1.2 million puts per provider, a few dollars.
- **R11, 1,000 workloads.** The same rule of three: under 0.3% of workloads can differ. The runs are short, so the count is cheap; the single large replica covers size.
- **R16, every cell once.** The list of call sites is finite, so this gate is a coverage claim, not a sample: a cell that never ran is a row with no evidence.
- **14 nights.** Two full weeks of the rotating nightly seeds, long enough that a flake at one night in five almost surely shows (0.8 to the 14th is 4%).

**R2, the open classes.** The open defects reduce to three classes, and closing #99 item by item does not close them. (1) The engine remembers nothing across a restart: the journal (#119) must carry the floor, the unproven-WAL debt, the stop and the snapshot budget, and a law in the simulator must kill the process right after any injected fault. (2) No layer states a cost bound: a cost oracle must fail a crash loop that snapshots on every boot. (3) Detectors that go quiet when they find something: that is R3. R2 is met only when each class has a closed-world guard, not a list of fixed instances.

The lag law must not differ by provider. The engine does not know which store it talks to, and an S3-compatible endpoint may be none of these, so it has to be correct under the weakest one: a listing or a read that lags. The simulator keeps one law at least as bad as the worst probe result. What differs is the expectation: on AWS S3 and R2 the probe should count zero stale answers, and a single one is a finding to report to the provider and to widen the law for. On Tigris the count is measured, from one region and from two.

**R10, the writer.** One seeded generator, the same on every provider and in R11 and R16, frozen with the rc commit.

- **Shape.** Bursts of up to 200 commits a second, then idle periods from seconds to hours. Transaction sizes drawn from one row up to 200 MiB, so some spill and some pass the multipart threshold. Inserts, updates and deletes, so pages are freed and reused. A database that grows past 4 GiB (the lock page) and shrinks.
- **What the application does to SQLite.** Its own PASSIVE and TRUNCATE checkpoints from another connection, long readers, `VACUUM` and incremental vacuum, a page-size change once, `synchronous=NORMAL` and `FULL`.
- **Restarts.** SIGTERM with a drain, or SIGKILL at a random moment, including mid-upload and mid-checkpoint, with the writer still running. Some restarts land on a fresh volume, so boot starts from the bucket alone.
- **Judging.** A job outside the engine copies the live database under a read transaction, notes the transaction id, restores at that id and at a random earlier point, and compares page hashes. Once a week Go v0.5.18 restores the same prefix and must agree.
- **Optional, not a gate.** A shadow instance of a real application: a second deployment from the same image and pipeline, its own volume, a database seeded once from the production replica with a read-only credential, and its own bucket with credentials scoped to it. It never touches the production database or the production prefix, so it is never the only copy of anything. It is worth running if it is cheap, because a real application's write pattern is the one input the generator cannot invent. Running a second replicator beside Go on a production database is not this: an earlier run saw commits get `SQLITE_BUSY` for 30 s under that arrangement (issue [#58](https://github.com/emschwartz/litestream-rs/issues/58)).

**R13, what counts as new.** A finding is new when it is not already a row, an open defect, a blind spot, an accepted limit or an owner-signed exclusion in `docs/BEHAVIOR.md` at the rc commit, and acting on it would change code, a mark, or a guarantee's conditions. A finding that maps to an existing row and shows its mark is wrong is new. A rewording or a duplicate is not. Each new finding becomes a row and a rig, and the count of reviews in a row goes back to zero.

**R14, what the freeze resets.** A change under `crates/` to core, ltx, wal, sqlite, replica, journal, store-fs or store-s3 moves the rc commit, and every gate marked **rc** is run again on it. R10's 14 days restart with it. Docs, CI and test-only changes reset nothing.

**R15, why zero.** The lint thresholds are today's counts, so the gate costs nothing to hold and any rise is a regression someone chose. The reviewer's three counts are zero because each is a yes or no per module: a concept with two homes is exactly how the stop, the failed fsync and the snapshot cause came to be forgotten across a restart. The pass runs after the last feature so it is not undone, and before the rc tag because it changes engine code and would reset every **rc** gate. The checklist per module: which one concept does this module own; does any other module also decide it; is every item reachable from a non-test caller.

**From TigerBeetle's practice, folded in.** The canary seed that must stay red and the seed database that makes "N seeds, 0 failures" a stored number per commit (R4), the crash after every durable step (R7), the check of the published artifact (R14). One more belongs in R4's setup and is not a gate of its own: a write-once checker on replica keys.

**Added for "everything we can", and why.** R11, because Go is the only independent implementation and nothing else can catch a belief the engine shares with its own simulator. R16, because every other rig injects above the system call or models the filesystem, and its call-site list is the closed inventory BEHAVIOR 7.4 says is missing. In R4, the long seeds, because 300 steps never reach a retention window. In R9, versioned buckets and lifecycle rules, because backup buckets usually have both.

**Considered and left out.** A formal proof of the engine (the journal and the restore planner are model-checked; the rest is too large to prove before use). A second SQLite implementation as an oracle (none is independent enough to trust). Speed against Go ([#42](https://github.com/emschwartz/litestream-rs/issues/42)) is not a correctness gate.

## Order

R3 before R4 and R5, since a soak judged by a blind checker counts for nothing. R2 and R1 next, then R15's simplification pass, then R14's strict merging and the rc tag. R4, R6 to R9, R11 and R16 run on the rc commit in parallel. R12 and R13 follow. R10 starts as soon as R9 is green on a provider and runs longest.
