# Known limitations

What to know before trusting litestream-rs with data, as of main on 2026-11-24. The short version: it is version 0.0.0, nobody has run it in production, and the defects below are open. [release-bar.md](release-bar.md) lists what must be true before first use; none of that bar is met yet.

Where an issue exists it is linked. Row ids such as BOOT-20 are rows of [BEHAVIOR.md](BEHAVIOR.md), which has the detail.

## Not yet done

- **No release.** Nothing is published, and the library's public interface will change before it is ([#318](https://github.com/emschwartz/litestream-rs/issues/318)).
- **Replication pauses while the whole database is staged.** The one thread syncs nothing new while it stages a copy of the whole database at level 0; Go's sync does the same, as the copy is its sync. Uploads of the files staged before it wait too; the upload of the copy itself is sent 8 MiB at a time with syncs and checkpoints in between, and the files staged meanwhile reach the replica only after it, as under Go ([decisions/D217.md](decisions/D217.md)). A pass lasts the database's size divided by the copy speed ([#352](https://github.com/emschwartz/litestream-rs/issues/352) has the one measurement). A start without WAL continuity makes three passes back to back ([#340](https://github.com/emschwartz/litestream-rs/issues/340)). A level-9 snapshot, daily by default, is sent a slice at a time with syncs and uploads in between, as Go keeps syncing through its snapshots; the engine's checkpoints wait for it, so the WAL grows for its length, as under Go ([decisions/D255.md](decisions/D255.md)). Compactions are sent a slice at a time too, with syncs, uploads and checkpoints in between, as Go compacts beside its sync ([decisions/D259.md](decisions/D259.md)).
- **Writes can wait at start when the working folder is lost.** Under the default `hold-start`, writes are held until the replica is listed and the start is decided, which is short. A start with no working folder first compares the database with the replica page by page, and writes wait for that comparison, which grows with the database's size.
- **No limit on read load.** A snapshot or a scheduled verify reads the whole database as fast as it can, in the application's own process when used as a library ([#315](https://github.com/emschwartz/litestream-rs/issues/315)).
- **Memory during a snapshot grows with the page count.** A snapshot holds an entry for every page of the database in its page plan, in the page checksum table and in the file's index, inside the application's process when used as a library ([#64](https://github.com/emschwartz/litestream-rs/issues/64)). A replica's whole file listing is also held in memory ([#68](https://github.com/emschwartz/litestream-rs/issues/68)), and the hot paths are still being reduced ([#46](https://github.com/emschwartz/litestream-rs/issues/46)).
- **A start without WAL continuity needs free disk about the size of the database.** It stages a compressed copy of the whole database in the working folder before uploading it, and nothing stops it when the space is short: litestream-rs logs a warning and reports `local_disk_full` in health, then copies as Go does. If the copy does not fit, each retry reads the database again. Continuity is lost at a first start, after a `VACUUM`, when another connection closes last ([#316](https://github.com/emschwartz/litestream-rs/issues/316)), and when the WAL restarts while no replicator runs, as between stopping Go and starting `lsr`.
- **One object holds at most 10,000 parts**, which is S3's limit. At the default part size (5 MiB, 16 MiB on Tigris) a file that compresses to more than about 48 GiB (156 GiB) fails after the rest was sent, and every retry sends it again. Set `part-size` so that 10,000 parts cover the database ([running.md](running.md)).
- **Restore reads one file at a time.** Restore time grows with the number of files in the chain times the store's round trip ([#326](https://github.com/emschwartz/litestream-rs/issues/326)), and it downloads every version of a page, not only the newest ([#44](https://github.com/emschwartz/litestream-rs/issues/44)).
- **Commits are noticed by polling** once a second, as in Go, so a commit waits up to a second before replication starts ([#43](https://github.com/emschwartz/litestream-rs/issues/43)).
- **Parts of Go's surface are missing.** Credentials from assumed roles, IAM Identity Center and login sessions are refused by name ([#176](https://github.com/emschwartz/litestream-rs/issues/176)), and so are `status`, `sync`, `list`, `info`, `reset`, `restore -f` and the control socket ([#177](https://github.com/emschwartz/litestream-rs/issues/177)). Storage other than S3 and a local directory, server-side encryption settings, storage classes and age encryption are refused at load ([config-keys.md](config-keys.md)).
- **Databases are found once, at start.** A `dir` entry is scanned once, so a database that appears later is not replicated until a restart, and a config change needs a restart ([#21](https://github.com/emschwartz/litestream-rs/issues/21)).
- **One thread and three SQLite connections per database**, which is fine for tens of databases and untested for hundreds ([#17](https://github.com/emschwartz/litestream-rs/issues/17)).
- **Linux and macOS only, and only verified SQLite builds.** Nothing is built or tested on Windows. The engine reads SQLite's private file layouts, so it refuses any build outside its list (SQLite 3.51.3 to 3.54.1 today).

## Known defects

- **Go Litestream and `lsr` writing one bucket path at once corrupt its history.** Go overwrites without a condition, so one transaction id can end with two contents. A later restore can exit 0 with a database that fails SQLite's integrity check, and `lsr` does not always report another writer ([#346](https://github.com/emschwartz/litestream-rs/issues/346)). Stop one, confirm its process has exited, then start the other ([running.md](running.md)).
- **A lying disk plus a repeated write can fork history silently.** If a power loss drops two or more replicated transactions and the application then writes the same final transaction again, the check at start passes and the replica's history differs from the database's ([#12](https://github.com/emschwartz/litestream-rs/issues/12)). The next snapshot puts the newest state right; a restore to a point in that range stays wrong until retention deletes it. The test for it fails and is marked ignored.
- **A crash loop is expensive and partly invisible.** A start that cannot prove continuity takes a full snapshot, with no limit on how often, so a process killed every few seconds can upload the database again and again (row BOOT-20). `/healthz` and the hold on writes do not see a failure across restarts; the age gauge does ([#331](https://github.com/emschwartz/litestream-rs/issues/331)).
- **With the S3 permissions in Litestream's guide, a start on AWS does not finish.** Every start lists and aborts unfinished multipart uploads, which takes `s3:ListBucketMultipartUploads` and `s3:AbortMultipartUpload`; that policy grants neither. The denial is a refusal, so under `hold-start` writes stay held until the policy changes ([running.md](running.md)). Read from the code, not yet run against AWS.
- **A very recent older copy of the database with no working folder can still replace the replica's newest state.** The start stops on an older copy whose replicator counter (`_litestream_seq`) is below the bucket's. The counter moves only at a checkpoint, 60 seconds apart by default. A copy taken after the bucket's last counter bump, so within about one checkpoint interval before the bucket's newest file, is taken for the same database with extra commits: the start warns `ahead_of_replica` and snapshots it on top. The commits the copy lacks stay restorable by transaction id until retention deletes them, 24 hours by default. A start can also stop wrongly when the bucket holds a counter the database never had, as after a Go build uploaded a bump SQLite never committed; `lsr trust-local` answers it ([D214](decisions/D214.md)).
- **`lsr restore -force` can write into the database in place.** After a restore that was killed at its last step, the scratch file and the database are one file, so the next `-force` restore truncates and rewrites the live database, and leaves it that way if it fails.
- **`hold-start` is best effort.** A first attempt at the start that fails for any reason but a refusal releases the writes, and a store that hangs releases them at the request deadline (60 seconds). If a later attempt then stops with `other_writer`, the application keeps writing, unreplicated, behind a 503.
- **A long store outage grows the WAL, and it does not shrink.** Once 4,096 files wait to upload (about an hour at one a second), new commits stay in the WAL on the database's disk, and with TRUNCATE checkpoints off (the default) the file keeps its size afterwards. A restart during the outage is covered when the local files and the WAL agree: 15 seconds in, the engine stages and checkpoints from local state as Go does, and the WAL stays short ([decisions/D220.md](decisions/D220.md)). When they do not agree (nothing staged yet, a staged file that does not read, a WAL that no longer continues the staged files), nothing is staged or checkpointed until the store answers, where Go takes a local snapshot and carries on. Tests hold such a fault for tens of simulated seconds, not hours (row WORLD-34).
- **Changes staged during an outage across a restart can lose their single restore points.** They are kept apart in the meta directory (its `ltx/8` directory, beside the `ltx/0` Go also uses) until the store answers. If the replica then holds changes past the other local files, because the directory had lost its newest files or was put back from an older copy before the restart, they are deleted, and the engine decides as at any start: it continues, takes a snapshot, or stops with `other_writer`. The database keeps every change; the restore points in between are gone. Go and `lsr` builds before this one never read `ltx/8`: one that runs before the store answers carries on from `ltx/0` alone, and the next start of this build deletes the files left in `ltx/8` the same way.
- **On Cloudflare R2, one stray file name can stop a level from listing.** R2 lists names that extend one another out of byte order, and the store refuses such a page. A replica only `lsr` and Go wrote is not affected ([#342](https://github.com/emschwartz/litestream-rs/issues/342)).
- **A stray connection that closes last costs a full snapshot.** If any connection closes after the replicator's, SQLite deletes the WAL, and the next start uploads the whole database with no warning beforehand ([#316](https://github.com/emschwartz/litestream-rs/issues/316)).
- **One crash-test failure is unexplained.** With the WAL sync removed, the real-SQLite crash rig once saw rows no commit made. It does not reproduce on main, and its cause was never found ([#94](https://github.com/emschwartz/litestream-rs/issues/94)).

## Untested conditions

- **Production, and size.** No real application has run on it, and nothing has run with `lsr` as the writer on a database of tens of gigabytes. The longest run on a real provider was 12 hours on Tigris, at older code, with a steady writer and no restarts. No soak has run on AWS S3 or R2.
- **Real providers, beyond one pass.** The conformance checks ran once each on AWS S3, R2 and Tigris on 2026-11-24, from one region, on buckets with no versioning and no lifecycle rule ([spikes.md](spikes.md)). Not run: a request cut mid-body against a real provider, versioned buckets, object lock, and a Tigris bucket read from a second region.
- **The newest rig has one counted run, and 151 anomalies in it are known and excused.** The rig that kills and partitions the real binary against an S3 server completed one counted run on Linux: nightly run 45565674128, 2026-11-25, seed 1688438391, 1,000 cycles in 123 segments, 7,399 s, 128,316 commits, 14,369 restores, 0 failing anomalies. It drew and ran partition 148, slow-uploads 103, kill9 268, none 152, power-loss 87, cut-uploads 94, go-concurrent 45, cut-reads 42 and clock-step 61. It is one seed and one run, so it bounds nothing about other seeds. In the 45 segments where the pinned Go Litestream wrote the same prefix, the rig excused 151 anomalies under [#346](https://github.com/emschwartz/litestream-rs/issues/346), and in 35 of those 45 `lsr` logged no `OtherWriter`. The older power-loss rig for the real binary judges only the newest restore. See [D216](decisions/D216.md).
- **Filesystems where SQLite's locks or shared memory do not work** (NFS, some container file sharing). The read lock proves nothing there, and nothing refuses to start ([#332](https://github.com/emschwartz/litestream-rs/issues/332)).
- **Retention and compaction over real time windows.** No test lists what retention must keep and restores each item after a real delete job ([#333](https://github.com/emschwartz/litestream-rs/issues/333)).
- **A paused process.** What writers see while the process is stopped holding its write lock is a guess (row WORLD-2). So is a second fault during recovery from a first (row WORLD-10), and a read-only remount or an exhausted file-descriptor limit (row WORLD-16).
- **A clock that steps forward.** The step is believed, so a restore to an instant inside that window is off by up to the step. No test covers it (guarantee G3 in BEHAVIOR.md).
- **Two failures inside SQLite's own checkpoint:** a failed sync of the database file (row CKPT-8) and a failed release of the write lock (row CKPT-6). Nobody knows what follows.
- **Upgrading `lsr` over its own working folder**, SQLCipher, a non-default VFS and WAL2 (rows WORLD-33 and WORLD-38).
- **Lag.** No test asserts how long a commit takes to reach the replica when all is well.
- **How many unknown defects the tests would catch.** The planted bugs are defects already fixed. The one blind measurement is old and small: the simulator alone found 7 of 22 bugs planted without a test written for them.
- **The simulator's SQLite is a model.** A wrong belief about SQLite that the engine and the model share is caught only by the real-SQLite rigs and the Go comparison, and every judge but Go's restore reads the replica with the engine's own decoder. Mutation testing is complete for the LTX crate only ([mutants.md](mutants.md)), and one fuzz target still owes its 24-hour run ([#322](https://github.com/emschwartz/litestream-rs/issues/322)).
- **Outside review.** Every whole-project review so far was by a Claude model. No person outside the project has reviewed the code.

## Deliberate limits

These were decided, with the cost accepted. [differences-from-go.md](differences-from-go.md) has the comparison with Go.

- **One writer per bucket path, one replicator per working folder.** The folder's lock works only on a local filesystem and does not exclude a Go process. A second writer on the path is refused only where the store supports create-only writes; elsewhere `lsr` runs as Go does and says so ([decisions/D079.md](decisions/D079.md)).
- **A store whose listings lag its writes is unsupported.** A restore inside the lag can succeed with an older state. A Tigris global or dual-region bucket read from another region is such a store ([decisions/D173.md](decisions/D173.md)).
- **No file certifies the one before it.** Files carry no running database checksum, as Go's default, so a chain of files that each verify and together are wrong restores without error (row REST-9). The scheduled verify (`validation.interval`, off by default) compares the replica with the live database and is the check for this ([#14](https://github.com/emschwartz/litestream-rs/issues/14)).
- **A page damaged on disk while the process was down is trusted** on its first read after a start, and can be uploaded ([#10](https://github.com/emschwartz/litestream-rs/issues/10)).
- **A bucket rolled back while the replicator is down is taken as the bucket.** A hole below the newest file is not watched: a restore fails with `Gap` until the next snapshot, up to 24 hours by default ([decisions/D173.md](decisions/D173.md)).
- **Nothing but one small record is remembered across a restart.** Retry counts and degraded states start from zero, as in Go ([decisions/D174.md](decisions/D174.md)).
- **Files waiting in the working folder are uploaded as they are.** A folder put back from a backup that does not match the database uploads the other history's files ([decisions/D175.md](decisions/D175.md)).
- **It stops where Go carries on.** Restoring on a new host while the old host is still uploading, then starting replication, stops with `other_writer`, and under `hold-start` the application waits for a person. That is the design, and a rolling deploy can meet it.
- **Point-in-time restore is as fine as the files that remain.** Single transactions older than the level-0 retention (5 minutes by default) cannot be restored once merged. A commit is dated by when it was staged, so commits made during an outage are dated at catch-up.
- **A replica holds one page size.** After a page-size change the way on is a new bucket path.
- **TRUNCATE checkpoints are off by default.** With `app-readers: none` each one that empties the WAL is followed by a copy of the whole database ([decisions/D190.md](decisions/D190.md), [#334](https://github.com/emschwartz/litestream-rs/issues/334)).
- **A checkpoint needs SQLite's write lock for a moment and never waits for it inside SQLite.** An application that holds the lock at every attempt (one long write transaction, or writes with no gap between them) puts the checkpoint off for as long as it does, one attempt a second, and the WAL grows meanwhile ([decisions/D225.md](decisions/D225.md)).
- **An upload abandoned by a kill is aborted at the next start, not before.** Set a lifecycle rule on the bucket to abort incomplete uploads as the backstop ([#20](https://github.com/emschwartz/litestream-rs/issues/20)).
- **The engine thread runs on a fixed stack.** Its size comes from a measured peak, and the land gate runs the tests on half of it. An overflow would end the whole process, the application included, and nothing can catch it ([#358](https://github.com/emschwartz/litestream-rs/pull/358)).
