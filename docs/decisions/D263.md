## D263. The simulator prices I/O in time, bounds every tick, and ends every run with a healthy tail (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5) · test code only (`crates/sim`)

- **Question:** the simulator's stores answered at once whatever the size, so a level-2 compaction of a 16.7 GB input that held sync, upload and checkpoints for minutes in the full-size drill was one cheap tick, and the slicing defects fixed in #461, #465 and #466 passed every seed. Its only liveness check counted ticks. How does the simulator see a stall?
- **What Go does, and why:** not applicable to the engine; Go's tests have no simulator. The prices follow what Go's deployments pay: an object store a request and a byte at a time, a local disk much faster.
- **Choice** (fixed before the first confirming run; loosening any number is a new decision):
  1. **Prices** (`crates/sim/src/cost.rs`, `Profile::DEFAULT`): the replica at 10 ms a request and 1 MiB/s, staging at 0.1 ms and 16 MiB/s, scaled down with the databases so the large profile's 10 MiB takes seconds as tens of gigabytes take minutes. A tick's price is the sum over both stores of requests times latency plus bytes read and written over bandwidth, from the recorders' counts, never from the engine. With `Opts::cost` the clock moves on by each tick's price.
  2. **Per-tick bound, every tick whatever its event, every run:** on each store, 128 requests plus 4 a file put there (plus 2 staging reads a part when the S3 replica sends in parts); bytes read at most a slice plus one 1 MiB read; bytes written at most a slice plus 1 KiB to the replica, the staged-bytes limit to staging. Each kind has its own share, so reads cannot hide in the share of writes. Bytes written to the replica in one tick stay bounded by a slice plus the held header for every tick, not only upload ticks.
  3. **Named allowances, refilled at each boot from the stores' own sizes:** the newest file of each level read whole twice (the boot, and the read-back after it in `maintain::audit`), a boot with nothing staged restoring the replica whole, and staging's files read and moved at boot. Each is a stall the engine makes in one tick today; they are kept by name so the bound stays tight elsewhere.
  4. **Healthy tail, every run** (`crates/sim/src/run/tail.rs`): after the run's own judges, a level-9 snapshot is requested and the application commits 40 times, 10 s apart, with the clock charged. Each commit is made with the replica caught up and must reach it (the bucket's newest transaction rises, read from the bucket) within (10 + 9 × pending slices) slice prices plus 1 s. A fault the world still imposes restarts the window after it and after the retry wait the engine announced. Bytes handed to uploads the store never took stay within one slice and a file. `liveness.judged` and `tick_cost.judged` are required marks.
  5. **Large profile** (`crates/sim/tests/sim/liveness.rs`): 20,000 pages of 512 bytes, 64 KiB slices, charged.
  6. A drain that runs out of grace restarts the engine, lets it settle to idle and drains again; draining at once sent the same backlog from its start each time and never ended once a backlog took longer than the grace.
- **Cost accepted:** about 300 more ticks a seed (the fixed seed set's batch budget rises from 4,000 to 6,400 ticks); the per-tick request share is loose (128 plus 4 a put), so one extra request per sync is not seen by it and waits for exact request budgets; CPU work costs no time.
- **Revisit if:** a confirming run shows the lag bound within 10 percent of a fault-free commit (seen: 3.5 s of 4.3 s at the large profile), or the allowances in 3 are fixed in the engine and can go.
