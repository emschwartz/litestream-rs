## D263. A TRUNCATE checkpoint proves no commit slipped in, so it takes no snapshot (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5)

Amends D121 and D190, and point 3 of D225, for the engine's own TRUNCATE checkpoint. Issue #334.

- **Question:** after its own TRUNCATE empties the WAL, must the engine copy the whole database, in case a commit made since the last sync was backfilled and truncated before any step staged it?
- **What Go does, and why:** Go always copies. Its TRUNCATE runs with its read transaction ended (`db.go:2805-2849`), so it cannot tell whether a commit slipped in, and it takes a snapshot of the database under the write lock (`db.go:2737-2797`). Correct, and a full upload per TRUNCATE.
- **Choice:** prove it instead. The protocol is the PASSIVE's: barrier, seal (every commit staged), PASSIVE on the reader with the read transaction retaken at mark 0 (everything backfilled), barrier released. Then the TRUNCATE runs on the writer connection with the engine's read kept. In SQLite (`walCheckpoint`, `walRestartHdr`, `walTryBeginRead`), a reader at mark 0 holds back no backfill of what it reads, but a commit after it began is a frame past that read's snapshot; SQLite's TRUNCATE returns `SQLITE_OK` only with every frame backfilled and every reader lock above slot 0 free, and a writer can only restart past a reader at mark 0. So a commit since the barrier's release makes the TRUNCATE busy and stays in the WAL, and the next step stages it (`Busy`). A TRUNCATE that succeeds truncated only what the seal staged, and the engine follows the new generation (`Truncated`, position pinned) with no snapshot. `SnapshotCause::CheckpointBoundary` and `CheckpointOutcome::BoundaryOwed` are gone.
- **Guards (the proof is never relied on where it may not hold):**
  1. *One copy of SQLite.* Another copy of SQLite in the process keeps POSIX locks the engine's copy cannot see (they belong to the same process), so its checkpoint can backfill past the engine's read. The backend counts the process's descriptors on `-shm` (`/proc/self/fd`, `/dev/fd` on macOS) before and after the TRUNCATE; one copy opens it once for all its connections (`unixOpenSharedMemory`). Any other count, or none readable, voids the proof.
  2. *The reset the seal sealed.* After an `SQLITE_OK` the WAL's `salt1` must be the sealed generation's plus one. A writer that restarted the WAL and died after publishing `mxFrame = 0` but before clearing `nBackfill` leaves frames nobody copied counted as copied, and SQLite's TRUNCATE then succeeds over them: `salt1` moves by two. So does another process's TRUNCATE in between, or fresh salts from a writer whose connection has run no checkpoint of its own.
  3. *Busy is not proof:* `SQLITE_BUSY` with counts, `SQLITE_BUSY` with -1/-1 (another checkpointer) and `SQLITE_LOCKED` all mean nothing was proved.
  4. *A void proof costs Go's price, never a commit:* the position is left unpinned, and the next sync snapshots (`GenerationChanged`).
- **An application that links its own SQLite:** a Rust application on `rusqlite` or `libsqlite3-sys` shares lsr's copy (`links = "sqlite3"` admits one, D152, D200), and the proof holds. One that brings a second copy (a C library with SQLite compiled in, an embedded interpreter's `sqlite3`) has its own `-shm` descriptor: guard 1 sees it, and each TRUNCATE costs a snapshot, as in Go. A second copy that opens and closes the database entirely between the engine's two counts is missed; its close drops every POSIX lock the process holds on the file, the engine's included, which SQLite documents as corrupting in itself. Another process, with any SQLite version, is arbitrated by `fcntl` locks and needs no guard.
- **Reviews:** a GPT review (Codex) held the proof with two conditions, guards 1 and 2, and asked for guard 3's `SQLITE_LOCKED`. A second Claude (Opus) review held it with five: one copy of SQLite whose connections share one `-shm` node, on a file system that honours locks (guard 1; a VFS with a `-shm` of its own shows as a second descriptor); the read held at mark 0 from the PASSIVE until the TRUNCATE returns, with the TRUNCATE on the writer (plant `truncate-on-the-reader`); only `SQLITE_OK` with counts means truncated (guard 3); a busy timeout of 0 on the writer, for liveness, which D225 already keeps; and mainline WAL, not wal2 or begin-concurrent, which the verified build list (D200) keeps. All are met, and the new ones are tested on real SQLite: `truncate_proof::a_second_opener_of_the_wal_index_voids_the_proof` (a held second descriptor), `truncate_proof::a_restart_whose_writer_died_mid_reset_is_not_followed` (another process commits and sets `nBackfill` to `mxFrame` in `-shm`), `truncate_proof::a_commit_after_the_barrier_makes_the_truncate_busy` (the SQLite fact itself, so a SQLite upgrade that changed it fails the build), and `truncate_proof::a_commit_anywhere_around_a_truncate_restores_whole` (a commit before every engine call and inside the TRUNCATE, with another process checkpointing).
- **SQLite versions:** `walCheckpoint`, `walRestartLog`, `walRestartHdr` and `walTryBeginRead` are the same in 3.51.3 and 3.54.1, the ends of the verified range.
- **Cost accepted:** a snapshot where none was needed, in three cases: a commit between the TRUNCATE and the engine's next read of the WAL header that wrote fresh salts; a writer that takes the lock before the engine's bump frame and writes fresh salts (CKPT-12); another process's TRUNCATE right after the engine's. Each is the old price, and each needs a commit inside a window of microseconds after a TRUNCATE, which comes once per `truncate-page-n` frames.
- **Revisit if:** SQLite changes the functions above, or the engine stops holding its read transaction across the TRUNCATE.
- **Links:** `crates/core/src/checkpoint.rs` (`truncate_held`), `crates/sqlite/src/checkpoint.rs`; BEHAVIOR rows CKPT-4, CKPT-12; plants `truncate-proof-beside-a-second-sqlite`, `truncate-proof-after-an-unseen-reset`, `busy-truncate-taken-as-proof`, `wal-index-descriptors-not-counted`, `truncate-on-the-reader`.
