## D108. A cure that reads the WAL before it checkpoints (delegated)

Status: open to owner review · Decided by: Claude (journal), **delegated**, from a Fable review

- **Question:** after a failed WAL fsync the engine cures the debt with a TRUNCATE checkpoint and then trusts the database file (`crates/core/src/actor/unproven.rs`). The pages the failed sync covered live in the page cache only. If the kernel evicts them, a later read returns the disk's older bytes, and SQLite's checkpoint, which does not verify frames, copies those bytes into the database file. The snapshot after the cure then shipped them as the latest state (issue #197, R2; the simulator's `EvictPageCache` shows it). What must the cure do?
- **Choice:** read the WAL with checked reads before the cure runs its checkpoint (`crates/core/src/cure.rs`): every committed frame of the current generation, with its salts and chained checksum. An evicted frame fails its checksum, the chain breaks below the committed end, and the step fails `WalCorruptBelowCommitted` (`wal_corrupt`, through its configured response) instead of checkpointing: no checkpoint of the engine's copies an evicted frame into the database file. The debt stands, so the cure is tried again each retry, and the WAL's next generation (an application's checkpoint or a restart) ends it as before. Never snapshot from the unproven frames: they were never proven durable.
- **Options considered:** Fable's fuller design: the scan, then a new `CheckpointMode::Full` (which, unlike TRUNCATE, leaves the WAL so its frame counts are real), a check that it copied exactly the scanned frames, a read of every copied page against its frame's digest, then the TRUNCATE, with a new `wal_frames_lost` notice on a mismatch. It also closes the window inside the checkpoint call itself; it needs a new checkpoint mode across the seam, the simulator and lsr-sqlite, and its frame counts proven on the real-SQLite rig first, so it is left as the follow-up below. Staging the frames instead of the file (they are the unproven ones). Holding the engine's write barrier across the scan and the TRUNCATE (a checkpoint needs the writer lock that barrier holds, unproven on real SQLite).
- **Cost accepted:** an eviction between the scan and SQLite's read of the same frames, inside one checkpoint call, is not caught. An application's or another process's checkpoint after an eviction copies the older bytes too: SQLite's own exposure, not the engine's, and the engine's next snapshot then replicates the database as SQLite serves it, unmarked. The sync task stays degraded at `wal_corrupt` until the WAL's generation changes, and commits made meanwhile are unreplicated. A reboot or power loss that drops the page cache is unchanged (D103 covers what a boot finds).
- **Revisit if:** the real-SQLite rig shows `SQLITE_CHECKPOINT_FULL`'s `log` and `checkpointed` counts as the fuller design assumes (then add the verify step and its notice); an eviction is seen outside the simulator; the application's own checkpoint after an eviction is seen to ship older bytes.
