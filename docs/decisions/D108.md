## D108. A cure that proves what its checkpoint copied (delegated)

Status: open to owner review · Decided by: Claude (journal), **delegated**, from two Fable reviews; the user-visible names are **owner-approved**

- **Question:** after a failed WAL fsync the engine cures the debt with a TRUNCATE checkpoint and then trusts the database file (`crates/core/src/actor/unproven.rs`). The pages the failed sync covered live in the page cache only. If the kernel evicts them, a later read returns the disk's older bytes, and SQLite's checkpoint, which does not verify frames, copies those bytes into the database file. The snapshot after the cure then shipped them as the latest state (issue #197, R2; the simulator's `EvictPageCache` shows it). What must the cure do?
- **Choice:** prove each step before the next (`crates/core/src/cure.rs`):
  1. Read the WAL with checked reads: every committed frame of the current generation, with its salts and chained checksum, keeping each page's newest frame and its digest. An evicted frame fails its checksum, the chain breaks below the committed end, and the step fails `WalCorruptBelowCommitted` (`wal_corrupt`) instead of checkpointing.
  2. Run a FULL checkpoint (`CheckpointMode::Full`). It copies every frame and syncs the database file like TRUNCATE, but leaves the WAL, so its counts are real (held to real SQLite in `crates/sqlite/tests/sqlite/sim_model.rs`). It must report not busy, `log == checkpointed ==` the frames read, with the same committed end and generation after it. Busy, or a commit between the read and the checkpoint, is `WalSyncFailed` again: the debt stands and the task says so. A WAL that restarted is `WalMoved`. Either way the step runs again from the read.
  3. Read every mapped page back from the database file and compare it with its frame's digest, then read the committed end again; an end that moved is `WalMoved`, with no verdict, since another checkpoint may have copied newer frames.
  4. Only then the TRUNCATE. A TRUNCATE that goes busy after a proven FULL is retried alone while the WAL's committed end is the one proven, so an eviction after the proof cannot turn a proven file into `wal_corrupt`.

  A page unlike its frame was evicted between the read and the checkpoint's own read: commits the application made are lost. That is D103's response under its own kind (`AheadKind::WalLostCommits`): the verdict keeps the newest staged transaction restorable for seven days, is journalled at the end of the tick, before any TRUNCATE (the step returns the stop and the next attempt runs the TRUNCATE alone), degrades the sync task at `WalLostCommits` through `database_ahead_of_wal`'s response (under `STRICT`: stop), and stands in `/healthz` and the metrics until the window ends. With nothing ever staged there is no restore point, and the verdict is raised without one.
- **Names (owner-approved):** `/healthz` field `wal_lost_commits`, metric `lsr_wal_lost_commits`, and the kind `WalLostCommits` (snake `wal_lost_commits`) on `Ahead.kind` and on `Event::AheadOfWal`'s `Kept` and `Released`. No responses key of its own: `STRICT` already covers stopping, and `database_ahead_of_wal` answers it. The names are spelled once, in `verdict_name` (`crates/sidecar/src/health.rs`). `StopCause::WalLostCommits` and `PersistentCause::WalLostCommits` are internal.
- **Delegated sub-choices (Fable):** the kind is a flag bit beside the journal's verdict bit, adding no bytes, and only a record holding a lost-commits verdict is version 4, so older binaries read every other record (`docs/journal.md`); two verdicts merge as D103's do (the older restore point stays, the newer kind and facts replace the rest, the window restarts); the read-back covers every mapped page, not only those this checkpoint copied; the proof of a FULL lives in this process only. The verdict cannot tell the cure's checkpoint from the application's over the same frames, so it says a checkpoint lost the commits, not which.
- **Options considered:** the checked read alone, before a TRUNCATE (the first version of this decision): it leaves the window inside the checkpoint call. Staging the frames instead of the file (they are the unproven ones). Holding the engine's write barrier across the read and the TRUNCATE (a checkpoint needs the writer lock that barrier holds, unproven on real SQLite). A responses key of its own (`wal_frames_lost`; owner: no new knob). Keeping the FULL's proof across a restart in the journal (more format for a narrow window).
- **Cost accepted:** an eviction between the read-back and the TRUNCATE is harmless (the TRUNCATE copies nothing new). A restart between a verdict or a proven FULL and the TRUNCATE forgets the proof; the next read finds the evicted frames and the task stays at `wal_corrupt` until the WAL's generation changes, with the verdict already recorded. A steady writer can keep the FULL from matching the read, holding the debt at `wal_sync_failed` while commits stay unreplicated. One FULL checkpoint and one read of each page in the WAL per cure. An application's or another process's checkpoint after an eviction copies the older bytes too: SQLite's own exposure, not the engine's. A reboot or power loss that drops the page cache is unchanged (D103 covers what a boot finds). Health shows only the newest verdict's kind; an older one of the other kind is in the log only.
- **Revisit if:** an eviction is seen outside the simulator; the steady-writer case is seen to hold a debt for long (then take the write lock across the read and the FULL); the application's own checkpoint after an eviction is seen to ship older bytes.
