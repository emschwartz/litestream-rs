## D177. Holding the application when replication stops stays in v1, with `hold-start` the default

Status: decided · Decided by: owner, 2026-11-23 · Recorded by: Claude (claude-fable-5-2)

- **Question:** D173 left fail-stop undecided. `if-replication-stops` has three values: `report` (health and metrics say so and the application is never held, as under Go), `hold-start` (a stop or a refusal by the store at start holds an application that has not started yet; once it runs, a trip only reports) and `stop-app` (every trip holds the application, including changes that have waited too long for the replica). Go has nothing like it. Keep it, keep it with `report` as the default so the default matches Go, or cut it from v1?
- **Choice (owner):** keep it as it is, `hold-start` the default.
- **Why:** the default acts only where the engine itself already stops at start: another writer on the replica, a database that did not write it, or the store refusing the credentials. Each needs an operator's mistake, which is D173's rule for a stop, and starting the application anyway is how a wrong or empty database becomes the newest state of the backup. The stronger value is something an operator asks for.
- **Cost accepted:** about 700 lines in the engine and its plumbing in the replicator, the sidecar and the CLI, and a default that differs from Go at start.
- **Open defect:** under `stop-app` a trip for age can fire with no cause after the clock jumps forward (the nightly simulator, 2026-11-23). It is fixed in a change of its own.
- **What this does not decide:** whether `lsr take-over` should exist, which is issue #290.
