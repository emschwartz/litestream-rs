## D246. The requests a first start sends beyond Go's (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5)

- **Question:** a first start on S3 sent requests Go does not: a `GET ?uploads` and an abort, a one-byte GET of the level-9 key, a 17-byte GET of the level-0 file, and more LISTs than Go (30 against 28 at a large part size, counted through a proxy). The rule is that lsr sends more than Go only where Go is wrong and the extra request makes the replica safer. Which stay?
- **The level-9 GET is removed.** Every merge, the first snapshot included, read its output key before writing it, and a key it found was planned again. The read guarded a key that held an object the listing did not show, so that a rejected commit's delete could not take an earlier run's output. A store whose listings lag is unsupported (`docs/decisions/D173.md`), the job is planned from a listing that shows every file this engine wrote, and a fault forgets what the engine remembered of the replica, so the next plan lists again. No reachable plan names a taken key. Go reads nothing either (`compactor.go:104`). The plant that guarded the read is retired and the read itself is planted as the defect.
- **The level-0 GET stays.** A level-1 merge reads its level-0 inputs from staging only when each local copy's last 17 bytes (the trailer, with the whole file's checksum) match the replica's. Go merges any local level-0 file that opens (`compactor.go:139-147`, `LocalFileOpener`), so a stale staged copy (a backup of the staging directory put back, a file staged again after the replica took the first) becomes the level-1 file every later restore reads, while the replica's level 0 holds other bytes for the same transactions. One 17-byte GET per input tells them apart (comment on `local_is_replica`, `crates/core/src/maintain.rs`).
- **The `?uploads` listing and the abort stay.** Each boot lists the bucket's open multipart uploads and aborts the ones under this replica's keys. Go hands multipart uploads to the SDK's uploader (`s3/replica_client.go:513`), which aborts only an upload that fails in the process, and nothing in Go lists open uploads, so the parts of an upload a killed process left stay billed until a bucket lifecycle rule removes them. On a clean bucket the boot sends the one listing and no abort; the abort measured came from a Go process the benchmark killed in the same prefix (comment on `remove_scratch`, `crates/store-s3/src/orphans.rs`).
- **The LISTs stay.** Of the 37 LISTs against Go's 33 first counted, 7 against 5 came from another process listing the same bucket; lsr's own are 30 and one `?uploads` against Go's 28. lsr lists all ten levels on each full listing, where Go's maintenance lists only its configured ones (0 to 3 and 9 by default). Go's retention walks only the configured levels (`store.go:871-879`), so a file an earlier configuration left at level 4 to 8 is never deleted, stays billed and stays in the chain Go's restore builds. Listing every level is what lets retention here clean it (comment on `Inventory::load`, `crates/core/src/inventory.rs`).
- **Cost accepted:** without the output-key read, a store that breaks D173 (a listing that hides a file this engine wrote) could have a rejected merge delete an earlier output under the same key; such a store is already unsupported, and the consistency probe is its gate.
- **Tests:** core `the_first_start_sends_no_read_ahead_of_the_snapshot`, `a_compaction_writes_its_output_without_reading_the_key_first`; plant `compaction-reads-its-output-key-first`.
- **Links:** D173, D205, D245.
