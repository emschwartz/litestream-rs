## D290. The healthy tail does not count a staged file written again as before its commit (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5) · test code only (`crates/sim`)

- **Question:** the healthy tail (D265) takes a commit as reached once the replica holds a transaction newer than everything staged or uploaded before it. A staged file the engine could not trust (its fsync failed: the store published a file whose checksum did not match) is written again under the same name from the WAL as it then stands, with the tail's commit in it. The rule waited for a transaction newer than that file, which never came: a healthy run failed with "milliseconds from a commit to the replica: 3450 is over the limit 2552" (nightly 2026-11-26), where the commit had reached the replica 84 ms after it was made.
- **What Go does, and why:** Go assigns a transaction its number only when the sync that writes its LTX file succeeds; `DB.sync` in `db.go` names the file `LTXPath(0, txID, txID)` with `txID = pos.TXID + 1` and returns on a failed `ltxFile.Sync` before the position moves, so the retry writes the same name again from the same WAL offset to the WAL's end, every frame committed since among it.
- **Choice:** before each tail commit the judge records every staged file with the digest of its bytes (`Before` in `crates/sim/src/run/tail.rs`). A file whose name in staging or on the replica later holds other bytes stops counting as before the commit, for the rest of that commit's window. Every other file, the backlog the run left staged among them, still counts, so a backlog that reaches the replica unchanged says nothing of the commit.
- **Cost accepted:** a file written again with a sync that stopped short at its frame cap might not hold the commit; the judge then takes the commit as reached one file early and judges a shorter lag. Tail commits are two pages, so that needs a WAL backlog past the cap behind an untrusted file at the tail's start.
- **Revisit if:** the engine writes a failed staged file again from anything but the WAL as it stands, or the tail's commits grow toward the sync cap.
- **Links:** D265, D268; unit tests `a_backlog_staged_before_a_tail_commit_counts_as_before_it` and `a_staged_file_written_again_after_a_tail_commit_counts_as_after_it` in `crates/sim/src/run/tests.rs`.
