## D166. A boot takes no transaction id at or below the confirmed floor (delegated)

Decided by: **delegated**

- **Question:** D107 journals the confirmed floor: every transaction id at or below its bound was confirmed on this destination by an earlier process. A boot used to trust the replica's listing alone, so a bucket rolled back while the engine was down was just a short bucket, and a freed id was put again with other bytes (BOOT-19; simulator seeds 0x484 and 0x8f7, the second through a lagging listing). What should a boot do with the floor, and where must it not count?
- **Choice:** the floor stands for the replica's tip wherever an id must stay taken, and nowhere else. Boot recovery takes `max(confirmed, floor)` as the replica's newest transaction, so a position below the floor is behind the replica (`BehindRemote`). `snapshot_after` is raised to the floor, so that snapshot goes above it. `lose_staged` resumes uploads past the floor when the staged files below it are gone, so the snapshot above the floor follows with no hole. The engine's own `acknowledged` mark and the check for whether a listed file is this engine's (`known`, which `listing_untrusted` uses) leave the floor out: the floor says an id was taken, not that the file under that key now is this engine's. A replica that lost the engine's file can hold another writer's under the same key, and counting the floor there let the engine take that file as its own and keep going (fixed simulator seeds 8 and 0x2c caught this in a first version).
- **Options considered:** raise only the boot's `acknowledged` mark (it also feeds the own-file check, so it hid another writer); read every listed key at or below the floor against the floor's anchor before trusting a listing (a read per boot, and the anchor is absent when the confirmed file was verified without a witness); stop at a boot whose listing ends below the floor (a rollback is an operator's act, and D7 keeps stops for another writer).
- **Cost accepted:** after a rollback the replica's history has a gap below the snapshot the boot writes; the files the rollback took are not restored. With no destination named, or a journal lost, unwritable or unread, there is no floor, and the short bucket is the bucket, as before. A boot in which another writer has put a file at an id at or below the floor still tells it apart only by the own-file check, as on main.
- **Revisit if:** a boot needs to tell its own file from another writer's at an id the floor covers (then compare against the anchor), or the floor's bound is found raised past what this destination held.
