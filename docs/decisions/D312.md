## D312. A restore reads a large file through a window of ranged GETs (delegated details)

Status: decided · Decided by: the owner (parallel ranged restore, 2026-11-27); the window shape, span size and bounds by Claude (claude-opus-5-5), **delegated**; the owner can overturn them · Recorded by: Claude (claude-opus-5-5)

- **Question:** a restore read every file as one GET, so a large snapshot downloaded at one stream's speed. Should it read one file as several ranged GETs at once, and how?
- **What Go does:** opens up to 32 plan files at once (`restoreOpenConcurrency`) but reads each file as one GET. It has no ranged parallel download.
- **Measurement that asked for it:** one stream from Linode to Tigris ran at a median 89 MiB/s; two at 159, four at 276, eight at 364 and sixteen at 286.
- **Decision:** a file of at least two spans is cut into 8 MiB spans. Up to the store's `BatchKind::Spans` width of them are open at once, each one ranged GET that the S3 store reads ahead on a thread (at most 16 MiB per span). The restore takes the bytes in file order, so the decoder, every check and the sink's writes are those of one stream, and no byte is used unverified. The width is the replica's `concurrency` setting (5 by default, 2 on R2); `1` keeps one stream per file. The last span reads to the object's end, so a listed size that is off changes nothing.
- **First design, dropped:** each span decoded on its own and written as it arrived, with the file's checksum assembled from the parts. On the studio's APFS disk, writing pages out of order cost two to three times the kernel time: a 4 GiB restore from local MinIO took a median 23.2 s at four spans against 7.5 s for one stream.
- **Measured (studio, 2 GiB database, local MinIO, disk, 6 interleaved rounds, load average 50 to 70):** medians 4.07 s and 4.03 s for two arms at concurrency 1 (the A/A spread, 1%), 3.85 s at 4, 4.04 s at 8, with the same CPU time (about 3.5 s). Local MinIO is not bound by one stream, so this shows the window costs nothing locally; the gain is where one stream is slow, as the Tigris numbers show.
- **Cost accepted:** one GET per 8 MiB where one stream makes one per file: about 8,500 GETs for a 68 GB database, under a cent at S3's read price (requests traded for wall time, by the owner's approval; docs/decisions/D305.md widened the request rule the same day). Memory: up to the width times 10 MiB (a span read ahead, the piece being read and the piece handed out), 50 MiB at the default of 5, where one stream holds one 4 MiB chunk.
- **Revisit if:** a store bills ranged GETs differently, a deployment needs restore memory under 50 MiB at the default concurrency, or a measurement shows a span size that does better.
