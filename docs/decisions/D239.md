## D239. A compaction's output is a create-only write, and the bucket's refusal is the answer (delegated)

Status: decided · Decided by: Claude (claude-fable-5-2), **delegated**; the owner can overturn it · Recorded by: Claude (claude-fable-5-2)

Found by counting requests in lsr-core: every compaction began with a one-byte GET of its output key, 8 in two minutes of a steady writer.

- **Question:** a compaction must not write over an output a listing did not show (an earlier attempt whose answer was lost, another writer's output for the same range): the delete after a rejected commit may only take the object that attempt wrote. The engine read the key first and replaced. Is the read needed?
- **What Go does.** It asks nothing and writes over whatever the key holds (`compactor.go`, `Compactor.Compact` pipes the output to `WriteLTXFile`).
- **Choice.** The output is written create-only, through the path level-0 uploads already use (`If-None-Match: *` on the PUT or on the multipart complete; a hard link on a file replica). A refusal is read as the probe's "taken": nothing is written, nothing is deleted, and the job is planned again from a whole listing. No request asks about the key first.
- **When the object under the key is not what this run would write.** It stands, untouched, exactly as when the probe found it. The next whole listing shows it as the level's file for that range and planning goes on above it; it is then a listed file like any other.
- **Providers.** Create-only writes and their races pass on AWS S3, Cloudflare R2 and Tigris (`just test-provider`, 2026-11-24) and on MinIO in CI: every provider the store has been run against. A provider that answers the condition with `NotImplemented` fails the commit and publishes nothing; the engine reports it as it does for an upload (degraded at `conditional_writes_unsupported`, or a stop under that response, D79), and for the rest of the process a compaction writes without the condition and replaces, as Go does. No store gets a read of the key first (`docs/decisions/D246.md`). A provider that ignores the header silently writes over the key, as Go does, and is not detected (D79's accepted cost). A file replica on a filesystem without hard links replaces (D79's open question).
- **Cost accepted.** The refusal comes at the commit, after the inputs were merged and the output's bytes sent, where the probe refused before any work; a refused multipart output leaves its parts to the orphan list. That happens only when a listing did not show the output. A create-only attempt asked nobody whether the key was free, so a part the store rejects deletes nothing under the key: only a commit the bucket let in can have left this attempt's object.
- **Counted.** `actor::tests::steady::a_compaction_asks_nothing_about_its_output_key`: two minutes of a steady writer on a store that lists as S3 does: 8 level-1 GETs before, none after.
