## D186. `s3://bucket` with no slash stays refused in v1, with an error that says what to write

Status: decided · Decided by: owner, 2026-11-24. The error's wording is Claude's (claude-fable-5-2), pending the owner's approval of the line.

- **Question:** Go accepts `s3://bucket` (no slash after the bucket), reads its path as `.` and writes keys under `./` (D181). litestream-rs refused it with the store's "the replica prefix is not a clean path", which does not say what to do. Support Go's `./` layout, or keep refusing? Whether Go intends the `.` is asked upstream in [benbjohnson/litestream#1651](https://github.com/benbjohnson/litestream/issues/1651).
- **Choice:** keep refusing in v1. The refusal is now its own error at config load and on `--replica` (`ReplicaProblem::NoSlashAfterBucket`): it says to add the trailing slash for the top of the bucket and that Go reads the URL as a folder named `.`.
- **Cost accepted:** someone moving from Go who wrote `s3://bucket` has a replica under `./` that litestream-rs cannot read; they move the objects or start a new replica. This is a stop at startup where Go has none, for a URL a reasonable person writes.
- **Options considered:** support the `./` layout (the `url` type the store builds requests with drops a `.` segment, so the request path would have to be built another way and proven against each provider's signing); read `s3://bucket` as the top of the bucket (silently a different layout from Go's, and a restore of a Go replica finds nothing).
- **Links:** D181; issue 298; `crates/config/src/map/s3.rs`, `crates/config/src/map/replica.rs`; `docs/differences-from-go.md`.
