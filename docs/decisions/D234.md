## D234. A send holds its staged file open, and a file renamed over it mid-send goes up as it was opened (delegated)

Status: decided · Decided by: Claude (claude-fable-5-2), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5), who finished the measurement · It adds the public `ObjectStore::open` and `Opened`

- **Question:** the engine sends a staged file to the replica in reads of 256 KiB, and the directory store answered each one by opening the file again: a stat of the path, an open, a stat of the file, a seek, a stat for the buffer's size, the read and a close. That is 16,384 opens for a 4 GiB first sync, each one a new file as far as the kernel's read-ahead knows. One descriptor for the whole send removes four of the seven calls. But a descriptor follows the file and not its name: what does a send do when the staged file is replaced under it?
- **What Go does, and why:** `Replica.uploadLTXFile` (`replica.go`) opens the staged file once with `os.Open` and hands the open file to the replica client, which streams it to its end. A file renamed over the name during the upload is not what Go sends: it sends what it opened, and verifies none of it. So the handle's meaning is Go's already. This engine takes it and keeps its own verification.
- **Choice:**
  1. `ObjectStore::open(key)` answers with the object held open for a run of reads (`Opened`, one method, `read(offset, len)`), or with nothing, which is the default: a store with nothing to hold open is read by range as before (memory, S3).
  2. The directory store holds one descriptor, after the same check a read makes that the name is a regular file (a FIFO is still never opened).
  3. A send asks at the file's first byte and keeps what it got beside the decoder and the open upload (`upload::Sending`). It is dropped with the send. A send that begins again, after any failure, opens the file again.
  4. Every chunk is verified on the read that produced it, and the whole file against its witness token before the commit, exactly as before.
  5. A file renamed over the staged one while its send is part-way is not read. The file the send opened goes up, if it is the one that was witnessed. Before, the reads after the rename were of the new file, the send was refused (`StagedLost`), and a second refusal dropped the staged files and took a snapshot.
  6. A file changed where it lies is the same open file with other bytes, and is refused as before.
  7. The second read an S3 upload makes of each part (`docs/decisions/D222.md`) stays a read of the staging directory by name, on a read of its own, compared with the tally of the first read. It is not made through the held file: through one descriptor the two reads could never disagree about which file they read. So on S3 a file renamed over mid-send is still refused, by the second read.
- **Why accept line 5:** nothing but this engine writes the staging directory. What goes up is a file this engine staged and witnessed, checked against its token's length, digest and trailer checksum. The file left under the name is verified by whatever reads it next by name. Refusing instead would take a stat of the path for every chunk, to turn down bytes that are valid.
- **Cost accepted:**
  - One descriptor is open for the length of a send, across the ticks other work runs in. There is at most one send in flight, so one descriptor.
  - After a rename over a staged file mid-send, the replica holds the file as staged and the directory holds the newer one, until that one is read by name.
  - A wrapper around a store that does not forward `open` gets reads by range: correct, and as slow as before. The role wrappers and the simulator's four wrappers forward it.
  - A read through the held file is still a seek, a stat and a read (three calls where there were seven). One positional read would do; it is left for the change that needs it.
  - One more public method on `ObjectStore` (defaulted) and one public trait.
- **Measured** (studio, M1 Max, macOS arm64, release builds, main c5c8f9817 against this branch with that main merged in, 2e1ce214d; first start of a 4 GiB database to a file replica on the same disk, to "snapshot complete"; interleaved pairs, order alternated; the plan and its five amendments were written before each run and are quoted in the pull request). Another project's test suite used two to seven of the machine's ten cores during most runs, outside the bench lock, so each reading is given with the same binary against itself (A/A):
  - Calls per 256 KiB chunk, counted at the store's filesystem seam by a counting filesystem (`crates/store-fs/tests/store-fs/opens.rs`; `dtruss` needs root on that machine): before, a stat of the path, an open, a stat of the open file and a read for every chunk (48 of each for a 12 MiB file, and a close each); after, one of each of the first three for the file, and a read for every chunk. Inside each read the seek, the size stat and the read are unchanged: seven system calls a chunk before, three after.
  - Random pages, 12 pairs. The copy pass (the staged file's send, the only pass this touches): 2.15 s before, 1.87 s after, -15.8% [-22.0, -9.2] (A/A +1.2% [-7.4, +10.6], 8 pairs). System time: 3.73 to 3.26 s, -9.5% [-16.9, -1.5] (A/A -2.2% [-8.6, +4.6]). CPU: 8.56 to 8.08 s, -5.4% [-10.0, -0.6] (A/A -1.7% [-5.6, +2.4]). In the four quietest runs of each arm: copy 2.00 to 1.78 s, CPU 7.73 to 7.53 s.
  - Whole-run wall did not move and cannot show this change: 21.66 s before, 21.67 s after, +1.2% [-1.6, +4.1]. After the level-0 file is on the replica the engine waits for its next maintenance listing (the next 30 s window or 15 s later, whichever is first) before it builds the first snapshot, so the run ends on that clock and a shorter copy is a longer wait.
  - Text-like pages (LZ4 ratio 0.57): 12 pairs in a second run (another project's suite was running during the first, which resolved nothing: one run took 119 s against a median of 41 s). The copy pass: 4.62 s before, 4.17 s after, -5.9% [-10.6, -1.0] (A/A, 6 pairs: -4.6% [-21.7, +16.2], too wide to read against). System time: 2.94 to 2.53 s, -9.7% [-15.7, -3.2] (A/A -6.9% [-21.6, +10.4]). CPU: 25.97 to 25.80 s, -1.0% [-3.0, +1.2], not resolved. Whole-run wall: 39.0 to 39.8 s, -1.9% [-17.4, +16.5], not resolved (same wait as above)
  - Predicted before the runs: 0.1 to 0.4 s less system time (measured: about 0.2 to 0.5 s) and a copy pass 1 to 5% shorter (measured: 16% on random pages; the pass is two seconds, shorter than the prediction assumed).
- **Checked by:** `a_send_opens_its_staged_file_once_however_many_chunks_it_reads`, `a_staged_file_replaced_under_a_send_goes_up_as_it_was_opened` and `a_staged_file_edited_under_a_send_is_refused_and_leaves_nothing_visible` on a real filesystem (`crates/store-fs/tests/store-fs/opens.rs`; the first two fail on the code before); four tests of the send against a store that holds files open (`crates/core/src/upload/tests/slices.rs`), one of them that a retry opens the file again; the store conformance case `an_opened_object_reads_as_a_read_by_range`; and `a_file_held_open_is_yielded_counted_and_faulted_read_by_read` for the simulator's wrappers. The simulator's nightly seeds for 180 s: 1,946 and 1,639 seeds on the branch, 1,910 and 1,798 on main, none failed on either.
- **Options considered:** keeping the refusal by remembering the file's identity and checking the name again for every chunk (a stat a chunk to refuse valid bytes); descriptors kept by the store, keyed by file (a cache, with a lifetime nothing bounds); making the S3 second read through the held file (it would weaken that check, line 7); positional reads on a shared descriptor (the next step's, when a second thread reads).
- **Revisit if:** anything but the engine comes to write the staging directory; a store other than the directory store has something worth holding open; the three calls a chunk show in a profile.
