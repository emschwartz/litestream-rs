## D275. The engine's heap between ticks is gated across two database sizes (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5) · test code only (`crates/core/tests/core/carried.rs`)

- **Question:** the memory gates in `mem.rs` measure paths that run in one call. A level-9 snapshot of the database or a merge runs across thousands of ticks, so what the `Actor` carries from one tick to the next is state of its own. A job that kept every page it had read would hold the database in RAM and pass every one-call gate. What bounds it?
- **Rig:** the public `Actor` ticked over `FakeWal`, `FakeCheckpointer` and `FakeClock`, a database whose pages are computed on read, and a staging directory and replica that are files on disk (the engine's own uploads are listed back to it, as keys and sizes). Slices are 64 KiB (`UploadConfig::bytes_per_tick`). The live heap is read after each tick (`heap::live_now`); carried is that minus what was live when the job before ended, and the gate takes the largest over the job's ticks, and the peak of each tick above the same mark. The database snapshot is reached by letting the snapshot built from level 0 fail once (reads cut), as a replica whose files cannot be read does; the next snapshot is then a read of the database.
- **Choice:** at 4,096 and 40,960 pages, carried and per-tick peak heap each grow by at most `SNAPSHOT_BYTES_PER_PAGE` (20, mem.rs) bytes for each page more, plus the allocator slack `FLAT_SLACK` (256 KiB). The fixed part (carried at N minus the slope times N) is at most `SNAPSHOT_CARRIED_FIXED` (1 MiB) for a database snapshot and `MERGE_CARRIED_FIXED` (2 MiB) for a merge, and no tick holds more than `TICK_EXTRA` (128 KiB) beyond what its job carries. A merge of several level-0 files carries at most `FLAT_SLACK` more than a merge of one.
- **Measured (debug build):** database snapshot carried 529 KiB at 4,096 pages and 838 KiB at 40,960: 8 B/page, fixed about 497 KiB (peak 561 and 866 KiB). Level-1 merge from staging: 533 and 843 KiB, 8 B/page, fixed 501 KiB. Level-2 and 3 merges from the replica: 1,339 and 1,660 KiB, 8 B/page, fixed 1,307 KiB (the 512 KiB read window of each input and the output buffers). Several level-0 files: 558 KiB against 533 KiB for one. The slope is the page index and the pinned checksum table, under the one-call snapshot's coefficient of 20.
- **Plant:** `sliced-snapshot-keeps-its-pages` keeps a copy of each chunk the sliced snapshot encoded. The gate reads 17.5 MB carried at 4,096 pages and 169.9 MB at 40,960 (about 4,133 B/page) and fails.
- **Cost accepted:** each run writes about 160 MiB to a temporary directory at the larger size and takes about 4 s in a debug build. The 8 B/page slope is well under its ceiling of 20, so a 12 B/page regression would pass; the gate is for a copy of the pages, which is 4,096 B/page.
- **Revisit if:** the slice size, the checksum table or the page index changes shape, or a measured slope nears 20.
- **Links:** plant `sliced-snapshot-keeps-its-pages`; D164 (the one-call memory gates).
