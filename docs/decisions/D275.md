## D275. The simulator's S3 cells are 128 bytes, and a refused second read is charged a commit (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5) · Amends D270, which set the simulator's cell to 32 bytes

- **Question:** after the S3 store stopped hashing a staged file in a second read (D270), the nightly failed on one seed: "replica commits: 15 is over the limit 13", then, with that fixed, the healthy tail's WAL bound. What did the change do to the simulator?
- **Cause:** D270 gave the simulator a 32-byte cell so its files reach a second read. A file of a few hundred bytes then took 6 to 9 reads from staging where it took 2 before, so each tick was priced higher and read faults on staging, which fail the commit that asked for the read, hit more often. A run that backs files up ended its drain with 51 files still staged, and the tail judged the WAL against uploads of that backlog.
- **Choice:** the simulator's cell is 128 bytes, so a few-hundred-byte file is read again in two or three cells, about the count it had. `tests/sim/remote_s3.rs` pins that a run reads the replica again no more than once a file. The commit budget (`crates/sim/src/budget.rs`) also charges one commit for each second read that was refused or gave other bytes: such a read fails the upload that asked, and the engine commits again. Before, only faults on the replica were charged.
- **Cost accepted:** a part of 128 bytes or less is sent from the bytes it kept, so the simulator's 64-byte parts are never read again. The scenarios that need a part read back use parts of 256 and 512 bytes.
- **Revisit if:** the simulator's files grow, or a scenario needs a smaller part read again.
- **Links:** D270, D265; `crates/sim/src/remote.rs`, `crates/sim/src/budget.rs`, `crates/sim/tests/sim/remote_s3.rs`.
