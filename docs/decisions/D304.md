## D304. A reader guard always holds off TRUNCATE; `ReaderTracking` is gone (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5)

- **Question:** `lsr_replica::Config.readers` (`ReaderTracking::Untracked` or `Tracked`) decided whether the checkpointer honoured the `ReaderGuard`s the application took from `Replicator::long_reader`. Under `Untracked`, the default, a guard was counted and silently ignored. Does the switch earn its place?
- **What Go does:** nothing comparable; Go's library has no reader signal, and its TRUNCATE meets a busy reader as SQLite reports it, which is what an application holding no guard gets here.
- **Decision:** delete the enum and the field; the checkpointer refuses TRUNCATE and FULL whenever a guard lives. A guard exists only because the application asked for one, so honouring it is what taking one means.
- **Behaviour:** unchanged for every application that takes no guard (the sidecar and every default configuration) and for every one that set `Tracked`. The one change: an application that took guards while leaving the default `Untracked` now has them honoured; before, they did nothing. No store request changes.
- **Cost accepted:** a public field and type go (`BREAKING CHANGE` on lsr-replica).
- **Revisit if:** an application needs guards counted but not honoured (none is known).
- **Links:** `crates/replica/src/readers.rs`, `crates/replica/src/config.rs`, docs/BEHAVIOR.md CKPT-3.
