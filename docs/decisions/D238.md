## D238. Retention ages a file this process put by the created-at time the put was answered with (delegated)

Status: decided · Decided by: Claude (claude-fable-5-2), **delegated**; the owner can overturn it · Recorded by: Claude (claude-fable-5-2)

Found by counting requests in lsr-core on a store whose listings carry only a last-modified time, as S3's do: from the first level-0 retention delete on (five minutes after a start), the engine sent one HEAD per level-0 file it deleted, as many as it sent level-0 PUTs. The head-to-head against Go ended before that and saw 3 HEADs a minute, the retention check's anchors.

- **Question:** retention ages files by their exact created-at time, never by a listed last-modified time (`crates/core/src/maintain/retain.rs`, "Time base"). On S3 that time is object metadata and a listing does not carry it. Must the engine ask for the time of a file it wrote itself?
- **What Go does.** It ages level-0 files by the time the listing carries, which on S3 is `LastModified`, and sends no HEAD (`db.go`, `EnforceL0RetentionByTime`).
- **Choice.** The engine remembers, in memory only, the created-at time of each file it put, as the store's answer to the put gave it: every level-0 file until retention deletes it, and the newest 64 files at each level above 0 (the anchors, and the older snapshots retention ages one by one). A maintenance decision is lent these and asks the store only for a file it does not find there. A listed file is taken for a remembered one only under the same key with the same length. Nothing read from the store is added: this is what the process wrote, not a cache of reads. The rule itself is unchanged, so retention deletes exactly what it deleted before.
- **What bounds the memory.** At most 16,384 level-0 files of about 64 bytes (1 MiB), four and a half hours of level-0 retention at one file a second, and 64 files for each of the nine levels above (576 in all). An entry goes when retention deletes its file. Past the cap the oldest goes, and its time is read from the store when retention reaches it: a level-0 retention longer than the cap holds pays the HEADs it paid before.
- **What a restart costs.** A new process knows none of the times. Each level-0 file an earlier process left costs one HEAD when retention reaches it, once: at most a retention period's worth, 300 at one file a second. The files retention keeps reading and this process has not written yet cost one HEAD per retention check (every two minutes by default) until it writes them: the newest file of each upper level until that level's next compaction, the snapshots until the next snapshot, and the first level-0 file while level 1 starts above it. On the counting test that is 3 HEADs per check after a restart, none before one.
- **Cost accepted.** An object replaced on the replica by another hand, under a key this process put and with the same length, is aged by this process's time for it, not by its own. Level-0 deletes still need a level 1 to 8 file that covers the range, listed in the same pass.
- **Counted.** `actor::tests::steady::retention_reads_no_created_at_time_of_a_file_this_process_put`: four minutes with two retention deletes, 20 commits a second, one level-0 file a second: 251 HEADs before (246 of level-0 files, 3 of level-1 files, 2 of snapshots), none after. The short-interval scenario (`a_steady_writer_with_short_intervals_pays_the_bill_and_no_more`, snapshots every two minutes kept three) sent 72 level-9 HEADs in 330 seconds while only the newest snapshot was remembered: none after.
- **Revisit if:** the HEADs after a restart matter. Remembering the answers of those HEADs would end them, and that is a cache of store reads, which needs the owner's yes.
- **Links:** `crates/core/src/created_at.rs` (`Known`, `resolve_knowing`), D193.
