## D220. A restart during a store outage stages and checkpoints from local state, in files kept apart (owner decision)

Status: decided · Decided by: owner, 2026-11-25, confirming the choice Claude (claude-fable-5-2) made as delegated · Recorded by: Claude (claude-fable-5-2)

- **Question:** a boot decides nothing before the replica's listing answers. A process that started during a store outage therefore had no position: it staged nothing and checkpointed nothing, and the WAL grew for as long as the outage lasted. May the engine sync before the store answers, from what, and what happens to the files it stages when the store comes back?
- **What Go does:** its database sync never asks the store (`db.go` `Sync`, `verify`): it reads its newest local file and the WAL, stages, and checkpoints, through any outage and across any restart. When the store answers, the replica uploads every local file above the replica's newest by name, with no check of its content or its place (`replica.go` `Sync`, `uploadLTXFile`). So Go keeps the WAL short, and when its local directory was behind the replica at the restart it uploads files that do not continue what the replica holds.
- **Choice:** Go's behaviour for the WAL, without the unchecked upload.
  - **When it begins (`actor/local.rs`).** Once boot attempts have failed for 15 seconds with the listing never answering, the moment held writes are released (`docs/decisions/D207.md`), the engine reads every staged file once and the WAL. They agree when every staged file reads whole, each after the oldest starts where the one before it ended, and the WAL holds the newest file's range with the same pages and continues from its end (`Agreed`, which only `agree` makes; the course's constructor takes one). Then it takes that position and runs the WAL side of a booted engine: sync steps and checkpoints. Anything else begins no course, and the judgment is made once per process, because it reads every staged file. Tying it to the 15 second bound and not to the first failure keeps a blip from costing that read.
  - **What it may not do.** It is a variant of the engine's closed course type that is not booted: uploads, prune and compaction run only in a booted engine, and so does every snapshot a boot or a sync step decides on (a step that would need one ends the course, because only a boot numbers a snapshot). The one snapshot a course stages is the boundary snapshot of its own TRUNCATE checkpoint, as a booted engine's TRUNCATE and Go's local sync stage theirs; it continues the staged chain and is a file in the slot like the course's others. Boot attempts go on, paced by the upload task, whose state carries the store's fault to health; a due attempt takes its turn after eight of the course's steps in a row, so neither starves the other.
  - **Where its files are kept (`actor/apart.rs`).** In a slot of their own in the staging directory, its level-8 directory (`ltx/8` in the meta directory, beside the `ltx/0` Go stages in), which staging uses for nothing else. The course sees staging through a store view: level 0 through the newest file there as it began, and above that the slot. No boot, upload or prune reads the slot, in this process or a later one. That is why no file of a course can be uploaded before a boot judged the replica: it is not where uploads read.
  - **What the boot does when the store answers.** After its own listing answered, it settles the slot. The replica's newest transaction, at any level, at or below the newest level-0 staged file: every slot file is above the replica, as a file staged after a boot is, and is moved up (copied, compared on a second read of both copies, then deleted from the slot). The listing stands: what it decided is about keys the replica holds, and the files that moved are all above those. The replica past it (staging was behind when the course began, another writer wrote, the bucket was rolled forward): the slot's files are deleted, a course in progress ends, and the boot judges level 0 as it stood before the course, by the rules it has (`docs/decisions/D201.md`, `docs/decisions/D206.md`): the live WAL vouches, a takeover record covers the files, or the engine stops for another writer. A replica rolled back is refilled or gets a snapshot as at any boot.
  - **A build that does not know the slot.** Go writes local files only in `ltx/0` and reads no other local level (`db.go` `MaxLTX`, `replica.go` `Sync`); an `lsr` build before this one lists staging at level 0 only. Go, run after a course, ignores `ltx/8`, finds the WAL no longer continues `ltx/0` (the course checkpointed), writes a snapshot at the next number in `ltx/0` and stages on from there (`db.go` `verify`, `sync`). An older `lsr` ignores it as well and boots from level 0 once the store answers. What either stages then stands at the numbers the slot's files have. So the settling boot also deletes the slot when level 0 ends past the slot's oldest file: a course writes above level 0 and a move copies the oldest first, so no state of this engine has that. Before this rule the move compared each slot file with the other build's file of the same name, deleted the other build's file as a bad copy, failed the attempt, and put the course's file in its place on the next.
  - **Health and the write gate meanwhile.** Nothing new. The engine reports neither booted nor listed; the upload task is `Retrying` and then `Degraded` with the store's cause; writes held at the start were released at the same 15 seconds. No event, health field or log line was added.
- **Why the files are kept apart:** the first version staged them at level 0. The simulator's fixed seed 0x3b failed on it (step 204, "transaction 32 covers commit 444 and then commit 385"): a staged file had been deleted, so staging was behind the replica; the course staged its own transaction 32; two restarts later, with reads of the replica lying, a boot took the replica's unreadable transaction 32 for its own upload cut short and wrote the course's file over it. Every level-0 staged file is assumed to have been staged after a listing, and nothing in the files says otherwise. An in-memory record of where the course began is lost by the second restart, and a marker file can be separated from the files it describes. An independent design review (claude-opus-5-5, given the code and the hazard, not this choice) found no design without durable state and ranked "location as provenance" first, a marker second, a mark in the LTX header's node id third, narrowing the replace-on-unreadable rule fourth.
- **The reviewers of the study:** neither the Gemini nor the Codex review of the boot study addressed its section on this change, so there is no verdict of theirs on it to record. Two of their general objections bear on it. "First-start and recovery copies need a durable base before later deltas can publish": a course publishes nothing and starts no history (its only snapshot is a TRUNCATE's boundary snapshot, which continues the staged chain), and its files reach level 0 only after a listing showed the replica at or below their base. "Preserve same-read verification through commit": the move up to level 0 compares both copies on a second read before the slot's file is deleted, and the boot's one pass then verifies each moved file on the read that makes its upload token, as for any pending file.
- **Evidence, and what kind:**
  - WAL bound, confirming tier, one registration. Claim written before the run: `store_down_across_a_restart` (fixed operations, 40 commits with the store down after a restart) keeps the WAL at or under 32 frames, the TRUNCATE threshold of those runs, and fails where the course never begins. Result: 13 frames on the branch, 77 with `no-local-course` planted. This is a regression kill, not a recall number.
  - The hazard above was found unaided, by 1 of the 64 fixed seeds (300 steps each) and by no test written for the change. `store_returns_unreadable_after_staging_fell_behind` restates it as explicit operations; with `local-course-stages-at-level-zero` planted it fails with "transaction 2 covers commit 3 and then commit 10".
  - Record: `fixed seeds 1 to 64 x 300 steps on the branch (generator unchanged from main), 0 anomalies, reach boot.local_course required and met; 5 scenarios, 5 plants killed by their named tests (regression kill); unaided recall of the 5 plants not measured; missing: no generator damages the slot or copies the directory mid-course, no real-binary run`. The rule for a build that does not know the slot has core tests and one plant (`local-course-slot-over-newer-files`) and no simulator run: no generator runs another build over the directory, and no test runs a real Go binary over a slot.
- **Cost accepted:** one more directory in the meta directory that Go lacks, present only between a course and the next boot that lists the replica. The boot after a course reads each of its files twice more than a pending file. A course begun behind the replica can end in a stop for another writer, where without the course the WAL would have vouched: its checkpoints remove those frames. The commits staged by a dropped course lose their single restore points. One more local listing call per boot.
- **Not covered:** another build that staged exactly one file after a course leaves level 0 ending at the slot's oldest file, which is also what a move that stopped between its copy and its delete leaves. The move takes it for its own copy, finds it differs, deletes it and copies the course's file up on the next attempt; the boot then judges those files against the WAL as any pending files. Empty staging, staging that does not read whole or chain, and a WAL that does not continue staging begin no course, so the WAL grows there as before (Go snapshots locally). A rebuild or a disagreement spends the process's one try. The 4,096-file cap on staged files applies to the course. Fail-stop's age clock does not run before the first real boot.
- **Revisit if:** the owner prefers the WAL to grow over a second directory; local level 8 is wanted for something else; or first starts during an outage (empty staging) matter enough to let a course take a snapshot.
