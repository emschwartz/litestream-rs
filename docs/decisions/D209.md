## D209. A credential source that fails at start opens a store that asks again (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5)

- **Question:** `open_store` resolved the credential chain eagerly, and the daemon left a database whose store failed to open without a replicator for the rest of the process, with no retry. A pod that starts before its credential agent answers, or an instance metadata service that answers 5xx once, lost that database until a restart. BEHAVIOR CFG-7 called the refusal "as Go". What does a failed credential fetch at start do?
- **Go:** `Init` calls `config.LoadDefaultConfig` (`s3/replica_client.go`), which fetches no credentials; the SDK fetches on the first request and again when they expire, so a source that is down at start costs one failed sync that the next retries. The row's "as Go" was wrong.
- **Choice:** when the chain fails because a source it asked did not answer (`CredentialError::fetch_failure`: a source's own failure, or the instance metadata service failing with nothing else configured), `open_store` opens the store anyway (`S3Store::deferred`). It signs nothing until the chain resolves, asks the chain again on each request, and fails each request without sending it: `Transient` when waiting may fix it, a credentials refusal otherwise (the same classification as a refresh that fails after expiry). The engine then retries and health names the failure as for any store refusal. The daemon logs `credentials not available yet, retrying` with the source's words. A configuration no source can satisfy (nothing named and the metadata service off, a profile that cannot be used, an unreadable shared file) still refuses the start: asking again cannot change it.
- **Cost accepted:** (1) Under the default `hold-start`, a refusal before the first listing holds the application's writes (D16), so a credential source that stays down now holds them, where before the database ran unreplicated and unheld. `if-replication-stops: report` does not hold. (2) Every request asks the chain, so while a source is down a batch of parts asks once per part, each bounded by the source's own timeout (5 s for the remote sources, 60 s for a process); the engine's retry waits bound the rate. (3) A source error that is really configuration (a container URL that is not loopback, a role ARN not set) is retried and reported by health instead of refused at start. Not told apart from an instance role that is not attached yet, which a retry fixes. (4) The log line is new user-visible text and waits for the owner's approval.
- **Options considered:** retry `open_store` in the daemon's waiter, which gives no health state for the library and re-resolves only at the waiter's interval; retry only the failures that classify as transient, which leaves an unattached instance role (a 404) permanent, as Go's is not.
- **Revisit if:** a hold on a down credential source costs a production application its writes: make credentials-at-start exempt from the hold (D16).
