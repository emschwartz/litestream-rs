## D215. A CLI restore writes the takeover record only for a database a config names (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5)

A rehearsal ran `lsr` in place of Go's binary against a deploy's scripts. `lsr restore -o backup.sqlite <url>` left `.backup.sqlite-litestream/` beside its output and printed `takeover recorded through <txid>`; Go's restore leaves only the database, so a script that removes `backup.sqlite*` left the folder behind.

- **Question:** the record exists so a replicator started on a restored database builds on the replica it came from instead of stopping with `other_writer` (D12, D21, D188). What is the smallest change that keeps that protection and leaves a Go script's output alone?
- **Choice:** the CLI writes the record only when a config names the restored path. For a DB_PATH restored to its own path that is the `-config` it was given; for a REPLICA_URL or `--replica` restore it is the default config (`LITESTREAM_CONFIG`, else `/etc/litestream.yml`), read as `replicate` reads it, quietly: one that is missing, does not load, names other paths or is standard input names nothing. The record goes in that database's meta directory (its `meta-path` or `meta-dir`, else `.<name>-litestream`). Any other restore leaves only the database and prints no takeover line. The library's `restore` and the sidecar's `-restore-if-db-not-exists` are unchanged.
- **Why this one:** the disaster-recovery flow, restore into the place a config names and then start, keeps its protection, and now writes the record where the config says the replicator looks: before, a URL restore wrote it beside the output even when the config set another `meta-path`, which the replicator never read. A backup, a copy or a drill has no replicator waiting for it and now looks like Go's.
- **Alternatives:** (a) a flag to skip the record: a Go script does not pass it, so the surprise stays for exactly the scripts that matter. (b) a flag that asks for the record: a start after a restore that forgot it stops with `other_writer`, the false stop D12 accepted only for operator acts. (c) never write it from the CLI and rely on the identity check (D176, D194): an unmodified restore passes, a point-in-time restore may not, and the stop would then name `lsr trust-local`. (d) keep writing it and document the folder: the surprise stays.
- **Cost accepted:** a restore to a path no config names, replicated later from a new working folder, no longer has the record. The start compares the database with the replica and goes on when they are equal (D176) or when it was written after the replica's newest file and holds most of its pages (D194); otherwise it stops with `other_writer` and the refusal names `lsr trust-local`, one command. A config absent at the restore and present at the start is the same case. D12's "a restore followed by a start never stops" now holds for a database a config names.
- **Revisit if:** an operator reports that stop after a restore, or a restore flow runs where the config is only mounted after the restore.
