## D212. Memory floor: a shared compaction budget and buffers kept for a file (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5)

Issue #46 (memory on the hot paths); the owner's concern is that lsr runs inside an application's process, and asked for much better memory, CPU and speed.

- **Question:** after D199 the remaining memory is buffering by design. What should each bound be, given what each costs in requests and speed?
- **Choice:**
  - Restore is left as it was (4 MiB reads, 8 at a time). A 1 MiB x 16 window held 19 MiB instead of 35 but changed the resident size of a 1 GiB restore by 1 MiB (43 to 42), cost 8 percent wall and 26 percent CPU, and sent four times the GET requests (1,024 a GiB); the owner does not want to raise a bill for that. 1 MiB x 8 (+16 percent wall) and 256 KiB x 32 (+38 percent) were worse.
  - A compaction's replica inputs share a 16 MiB budget: each reads `min(1 MiB, 16 MiB / inputs)`, never below 128 KiB. A merge of 16 inputs or fewer reads as before; 32 read 512 KiB each (33 MiB of windows down to 17). Staged inputs keep 128 KiB.
  - The output buffer of a compaction and of a staged file is allocated once per file at 256 KiB and emptied at each flush (was a new buffer per 1 MiB flush that grew by doubling from empty: three large blocks per flush). The LTX encoder keeps its compression buffer between pages. An upload's part buffer is reserved whole once an upload passes 256 KiB, not regrown by doubling.
  - The HTTP client keeps 16 idle connections per host and reads through a 32 KiB buffer (ureq's default is 128 KiB), a connection's write buffer staying at 128 KiB (see the fix for the pool). A 32 KiB write buffer made a 1 GiB upload spend 7 percent more CPU (2.12 s against 1.98 s, medians of five interleaved runs on the studio) in four times the writes; the read buffer costs nothing. Idle, a connection holds 160 KiB, 2.5 MiB for the 16 a wide batch leaves open.
- **Measured (M1 Max "studio", local MinIO, 6 interleaved rounds, medians; 1 GiB restore):** 4 MiB x 8: 0.92 s wall, 0.85 s CPU, 256 requests per GiB. 1 MiB x 16: 0.99 s (+6 percent), 1.00 s CPU, 1,024 requests. 1 MiB x 8: 1.07 s (+16 percent). 256 KiB x 32 (8 MiB of window): 1.27 s (+38 percent), 1.68 s CPU. Compaction of 32 L1 inputs of 4 MiB into L2, budget 32 MiB (the old 1 MiB windows) / 16 (the choice) / 8 / 4: 0.85 / 1.02 / 1.58 / 3.24 s wall, 157 / 285 / 541 / 1,053 requests. Request counts through a counting proxy. A request costs about 1.5 ms of MinIO time and 0.5 ms of client CPU here, plus a round trip on a real network.
- **The final binary against the one before the series (studio, local MinIO, 8 interleaved pairs, medians; two copies of the old binary differed by at most 2 percent; this run had the 1 MiB restore window, since reverted):** a 1 GiB upload 2.73 s both, CPU 1.93 s to 1.98 s (+3 percent), resident 40 MiB to 34; a compaction of 32 level-1 inputs 0.71 s to 0.85 s (+19 percent wall, +7 percent CPU), resident 137 MiB to 50.
- **Resident size, macOS (laptop, `footprint` of a replicator on a 64 MiB database, first start then idle, 45 s):** 164 MB (peak 291) before, 35 MB (peak 35) after; a database written once a second for 75 s: 9 MB (peak 289) before, 16 MB (peak 36) after. The live heap did not change much (peak 29.8 to 27.3 MiB, end 1.2 to 0.9 MiB); what changed is the number of large blocks the allocator was handed and kept (`MALLOC_LARGE (empty)` 147 MB to 25 MB): 3,558 MiB allocated in 298,000 blocks became 1,225 MiB in 135,000.
- **Cost accepted:** a compaction above level 1 of 32 inputs sends 285 GET requests where it sent 157 (128 more, a few hundredths of a cent on S3), runs 19 percent longer on a zero-latency server, and holds the actor for the extra round trips; it holds 50 MiB resident instead of 137. A merge of 16 or fewer inputs reads as before. An 8 MiB budget would cost 86 percent more wall time and 541 requests (the owner's lever if replicating memory matters more).
- **Not done:** the upload's part buffers (C x P) are untouched: a streamed compaction output has no file to read a part from, and a part's `Content-MD5` must be known before its body is sent; a part read back from the staged file would need the `Upload` trait to carry a source. The page-count terms of a snapshot (issue #64) are not touched here.
- **Revisit if:** a Linux profile shows resident memory above these bounds.
