## D195. The fault rig: one frozen menu, sampled points, and what counts as an anomaly

Status: decided · Decided by: delegated, Claude (claude-sonnet-5-5), 2026-11-24, for the owner · Recorded by: Claude (claude-sonnet-5-5)

- **Question:** the review of the correctness claims (issue 328, sections 3, 4 and 6) found no rig that runs the shipped binary against an S3 server under kills, partitions and a second writer and judges point-in-time restores. `scripts/lazyfs.py` is the only real-binary rig, and it judges the latest restore on a directory replica. What does the new rig inject, how much does it judge per cycle, and what is an anomaly?
- **Choice:** `scripts/fault_rig.py` runs the real `lsr replicate` beside the chain writer of `scripts/lazyfs.py`, with the replica on MinIO behind Toxiproxy. Its menu, weights, timings and budgets are tables at the top of the file, frozen before the first counted run; changing one makes earlier counts incomparable and the commit that does says so. The menu: nothing 15%, kill -9 of `lsr` 25%, partition 15% (1 to 120 s, short ones likeliest), slow uploads 10%, cut uploads 10%, cut reads 5%, LazyFS power loss 10% (Linux), clock step 5% (libfaketime, Linux), the pinned Go Litestream on the same prefix for 10 s 5% (one cycle in twenty). A draw the platform cannot run is recorded as skipped and runs as a quiet cycle, so the seeded schedule is the same everywhere and the summary says what was not exercised.
- **Judging:** each cycle restores, from MinIO directly, every level-0 transaction id not yet judged (a random 12 of them, with the first and last, when more than 12 are new: the engine writes about 15 files a second under load, so judging all of them would cost hours), two earlier ones again (a transaction id must restore to the same pages), two random instants, the latest, and the latest with Go's restore. `lsr-history judge --signals-required` judges the lot: a rewind explains a step back only when the engine logged a loss cause after it. A restore that matches no recorded commit, a refusal nothing injected explains, a stop the nemesis gives no reason for, and a loss cause logged under a nemesis that cannot lose history (the cycle's or the one before) are anomalies, kept with the seed, the cycle log, the commit log, the engine log and the replica's objects. An as-of refusal that names a compacted file is a documented refusal, counted. The segment that a concurrent Go writer touched ends at once, and its later refusals are counted as explained.
- **Consequences accepted:**
  1. Points are sampled, not exhaustive, when a cycle makes more than 12 new ones; the summary counts those it never judged. An old level-0 file that a later latest restore does not read is found only by the random re-checks.
  2. Plant runs and the canary use the menu without the Go nemesis, because that nemesis is an anomaly on the unplanted head too (the review's gap 2) and would hide a plant.
  3. Where the platform has no LazyFS or libfaketime (macOS), power loss and clock step are not exercised by a local run. The Linux paths were written against the LazyFS driver in `scripts/lazyfs.py` and libfaketime's documented timestamp file, and have not run on a Linux machine as of this commit.
  4. The seed fixes the schedule of nemeses and their parameters, not the interleaving with real time, so an anomaly keeps its evidence instead of promising a replay.
- **Known issue exemption:** the Go nemesis finds a filed defect (issue #346: after Go and lsr write one prefix, restores of past points and instants can be unsound databases, and the engine does not always log OtherWriter). So the nightly is not red every night for it, anomalies inside a segment the Go nemesis touched are counted and printed under "known: issue #346" and do not fail the run; any anomaly in another segment fails it. A Go cycle in which lsr logged no OtherWriter is printed on its own line (`go-cycle: ... SILENT`) and listed in the summary, since that silent case matters most. The exemption is one named constant, `KNOWN_GO_ISSUE` in `scripts/fault_rig.py`, removed with its uses when the issue closes. `just fault-rig-canary` checks that a tainted segment's anomaly is known and exits 0 and an untainted one still exits 1. The nightly runs the canary, then `wal-barrier` under power loss for 60 cycles (found or not found, never failing the job), then the counted run; the summary lists nemeses that did not run.
- **Cost if wrong:** the exemption hides a different defect that lands in a Go-touched segment until the issue closes.  a nemesis weight that starves a fault kind hides its defects (the run fails the REQUIRED_REACH floors from 100 cycles on). A sampled point set can miss a bad old level-0 file for a while.
