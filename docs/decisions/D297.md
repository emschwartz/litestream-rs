## D297. The compaction memory gate counts the part that fills beside the batch in flight (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5) · Amends: D232

- **Question:** CI failed `memory::a_compaction_into_s3_at_a_large_part_size_holds_its_parts` (54.1 MB held, bound 43.5 MB) after the bound was tightened from the parts in flight and one more to the parts in flight alone, because one quiet local run peaked at 37.6 MiB. Did memory grow, or is the bound wrong?
- **Decision:** the bound is wrong, memory did not grow. An upload holds the parts it has in flight and one more that fills or waits (D232); the compaction fills that part while the batch goes up. Whether it coexists with the whole batch depends on how fast the transport drains it, so the peak is 37.6 MiB on an idle machine and 54 MiB on a loaded one, 3 parts either way within the design. The gate counts `concurrency + 1` parts again. Holding the batch alone would need the compaction to wait for each upload before it fills the next part, a stall Go does not make and a throughput cost for no memory the budget does not already bound.
- **Cost:** this gate no longer sees a copied part body at 16 MiB x 2 (the plant part-body-copied). The upload gates `an_upload_through_the_real_client_holds_five_parts_in_flight_and_one_more` and `the_bound_follows_part_size_and_concurrency` see it and are the plant's tests.
