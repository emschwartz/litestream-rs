## D283. An unproven position stays unproven until a staged file reaches the committed end (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5) · test code only (`crates/sim`)

- **Question:** the needless-snapshot check forgot `PositionUnproven` (a boot behind the committed end, a failed step, a wal-index reset) as soon as any level-0 file was staged after it. A large-profile seed (`0x0000126d69302c6f`, 5,000 steps, `LSR_SIM_LARGE=1`) then failed with "a needless snapshot for GenerationChanged" on a snapshot the engine had to take. When does an unproven position become proven again?
- **What happened in the seed:** the engine was hundreds of frames behind the WAL's committed end (each step stops at the simulator's 16 KiB cap and commits are 8 times larger in the large profile). Another process checkpointed every frame, the process died, and the next process's read transaction landed on read mark 0, which blocks no WAL restart. The boot continued from the newest staged file, one step staged up to the cap, and the next commit restarted the WAL. The frames past that step were then only in the database file: the snapshot was the only way to keep them. By our reading of Go's `verifyWithExecutor` (`db.go:1782-1925`), Go would find the last page still in place, see no unknown salt, and continue in the new generation, dropping those commits from the replica's history without a word.
- **Choice:** `PositionUnproven` is forgotten only once a level-0 file staged after it reaches the WAL's committed end (`ForgottenAt::StagedThrough`, judged with `World::staging_behind_newest_commit`). That is the engine's own rule: a step stopped short by the cap ends `StepEnd::Limited`, which never pins the position.
- **Evidence:** `needless_snapshot::a_restart_after_a_sync_step_stopped_short_of_a_boot_backlog_justifies_a_snapshot` fails on the old check with the seed's message and passes now; the seed replays clean.
- **Cost accepted:** the forcing can outlive a step that did reach the end when the application commits again inside the same tick, so for that tick the check is quieter about `GenerationChanged` and the other causes `PositionUnproven` excuses. The engine snapshots there only if the WAL also restarted, which the scenario above shows is real.
- **Revisit if:** the engine learns to pin a position that stops short (then a restart under it is a needless snapshot again), or the sync cap changes how a step ends.
- **Links:** D277 (the large profile); `crates/sim/src/forcing.rs`; `crates/core/src/sync.rs` (`StepEnd::Limited`).
