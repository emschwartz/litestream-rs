## D201. Writes are released once the start is decided, not after its snapshot

Status: decided · Decided by: the owner, 2026-11-24 (implementation calls delegated to Claude)

- **Question:** D82 judged the boot, and so released held writes, only once the snapshot the boot asked for was staged. On main a 783 MiB database held every writer for 3.6 s at start, about 4.6 s per GiB, and the hold grows with the database. Go never holds writes at start. When should the start be released?
- **Choice:** release writes once lsr has reached the bucket and decided how to start: the boot is judged once the replica was listed and the engine decided to continue from a position or to snapshot for a named cause, or once a boot attempt failed for anything but a refusal. The snapshot runs after the release, while the application writes. Released means the write lock is let go, an `-exec` child starts, and `ready()` and `wait_booted` answer `Booted`.
  - Stops found before the decision still stop before any release: another writer, a page size change the WAL shows, a store refusal.
  - A stop only the snapshot can find surfaces after the application has started writing and is handled like any later fault: the page size changed (a WAL missing at boot), WAL corruption or truncation below what was committed, an unlinked WAL, a failed WAL sync, a database page mismatch, a bug. Under its `stop` response fail-stop trips; under `stop-app` the write lock is taken again with the trip as its reason, kept until a restart. Under `keep-trying` the task degrades and the unreplicated-age bound trips it. Transient faults are retried.
  - The identity check (a boot over an empty meta directory that finds the replica's own state compares the database with the replica's newest state before it decides) keeps writes held: it is part of the decision. It takes about a restore's time, store bandwidth plus one read of the database, so minutes for tens of GiB on S3. The engine tells its driver as the check starts (`Event::CheckingIdentity`, through `Env::notice`, in the tick that lists the replica) so health and the `writes blocked` line name it: `WhyBlocked::CheckingIdentity`, `held_by=checking_identity`.
  - `ready()` now means "the start was judged and writes go through". An application that must wait for the first snapshot waits on health: staged once `resnapshot` is `None`, on the replica once `unreplicated_since` is also `None` (`Replicator::wait_until`). Nothing new was added for it.
  - Log levels: `writes blocked` is INFO while booting or checking identity (every start says it) and WARN for a trip.
- **Cost accepted:** commits made between the release and a stop the snapshot finds are in the local database, not on the replica, until an operator resolves the stop. The boot no longer needs to write before it is judged, so the replicator's pass-through for a boot's own sequence bump is gone; a bump the snapshot needs waits on a hold like any other write.
- **Calls (delegated):** the identity check is named from inside the tick that runs it, not a tick ahead: an earlier form announced it one tick early, and every retry of a failed boot then listed the replica once more for the announcement (cost if wrong: the hold's reason is published as the long work starts rather than before it). `Event::CheckingIdentity` and `WhyBlocked::CheckingIdentity` are new public variants (a breaking change for exhaustive matches). The `-exec` end-to-end test holds the database's write lock so the snapshot's sequence bump waits, as its door to see the child start before anything is staged.
- **Amends:** D82 ("the snapshot the boot asked for, if any, was staged or its step failed") and D192 (writes held "until the boot is judged" now ends at the decision; the boot-write pass-through is removed).
- **Links:** issue #351, `crates/core/src/actor/lag.rs` (`boot_judged`, `checking_identity`), `crates/replica/src/thread.rs` (`Worker::fail_stop`).
