## D164. `replicate -once -force-snapshot` and `-enforce-retention`: Go's snapshot, lsr's retention rules (delegated)

Status: open to owner review · Decided by: Fable, **delegated**

- **Question:** Go's `-once -force-snapshot` writes a level-9 file at the current position and `-once -enforce-retention` deletes aged snapshots and the level 1 to 8 files under their floor, on the listing alone (`replicate.go:488-532`, `store.go:863`). `lsr` refused both by name (D48). Build them as Go does, or on the daemon's own snapshot job and retention planner?
- **Choice:** the daemon's. After the drain has uploaded everything, `-force-snapshot` writes one level-9 file `1..position`, replacing one already at that position as Go does; it bypasses the snapshot planner, which would call a snapshot at an unchanged position idle. `-enforce-retention` then runs the retention planner with level-0 deletion off until it has nothing to delete (built in a second change; refused until then). Departures: (1) the planner's trust gates apply, and a hold deletes nothing and exits 1 naming it; (2) ages are measured from the replica's newest created-at time when that is behind the clock, so an idle replica keeps snapshots Go deletes, with exit 0; (3) every database drains and runs its work, each outcome is reported and any failure exits 1, where Go stops at the first; (4) the snapshot and deletes are not cut by `shutdown-sync-timeout`, since Go's `runOnce` has no deadline. A snapshot is not retried: a fault, or a step that cannot prove the position (a reset wal-index on an idle database), ends that database's run without it, exit 1 with the reason, as Go returns its first error. With `retention.enabled: false` nothing is deleted and the run exits 0, as Go.
- **Options not taken:** writing a level-0 snapshot through the existing "next sync is a snapshot" request (Go never writes one there, and a Go reader sees no new level-9 file); a literal port of Go's retention pass (a second delete path without the gates, against fail-closed retention); refusing both.
- **Delegated:** decided by a Fable agent for the owner; the owner's session approved building it in two changes.
- **Cost if wrong:** a cron job that relied on Go deleting from a replica lsr holds on now fails every run until the replica is repaired, and one on an idle database keeps more storage than under Go. Nothing is deleted that Go keeps. A literal port of Go's rule can replace the planner call later without changing the replica format.
- **Evidence:** `-force-snapshot`: `compat::dropin_once` (Go and lsr each end with one level-9 file `1..newest` that Go restores to the database's rows, write the same file again at an unchanged position, and write none without the flag); `actor::tests::once` (after the last upload, a failed write and a reset wal-index each end the drain by name, a passed deadline does not cut it, the request survives a rebuild); `sim::final_snapshot` (explicit scenarios: written and restored, written again, an upload that fails, a published file with a lost response then a power loss); `cli::once_replicates_everything_committed_and_exits`. `-enforce-retention`: named when built.
