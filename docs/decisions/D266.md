## D266. The boot's read-back goes a slice a tick (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5) · fixes #476

Amends D265 (its defects bullet): the read-back no longer fails the per-tick bound, and `liveness::the_read_back_of_a_large_snapshot_goes_a_slice_a_tick` asserts that the run passes and judges the tail's lag.

- **Question:** after every boot, maintenance reads back the newest file of each level above 0 (`crates/core/src/maintain/audit.rs`). It read every file whole in one tick. A level-9 snapshot is the whole database (about 16 GB for a 24 GiB database), so the engine neither synced nor uploaded until the read ended, minutes after every restart. How is that read spread out?
- **What Go does, and why:** Go has no read-back. lsr keeps it (docs/decisions/D006.md), so the work stays and only its shape changes.
- **Choice:** the read-back reads at most a tick's bytes (`upload.bytes_per_tick`, one read of at most 256 KiB past them) and then ends the tick, reporting `MaintainedEvent::ReadBack`. Its state (the file being read, its held stream, and the files after it) is kept in memory between maintenance ticks, which take their turn after sync and upload as any maintenance unit does. Whether each file is covered by the others (`restores_without`) is decided on the listing the read-back began on. A read-back that spans ticks ends with no plan, and the next maintenance tick lists again to plan, since its listing is ticks old. A failed read drops the state; the next listing begins the read-back again from its first file. One failed verification still leads to a second read on a later listing before anything is deleted.
- **Cost accepted:** a read-back longer than one tick costs one more whole listing than before. A store fault part-way reads the earlier files again. A stream held between ticks keeps its connection open as a compaction input's does.
- **Simulator:** with the read-back sliced, the large-profile run reaches the end of its healthy tail with the snapshot the tail asked for still part-way, and the tail's wasted-bytes check counted that open upload's bytes as waste. The recorder now keeps the bytes of each upload still open (begun and neither committed, aborted nor dropped), and the check leaves those out; an upload the engine drops still counts.
- **Requests:** one GET a file where the store can hold a stream (S3), as before.
