## D227. A restart can date a no-commit snapshot as a commit

Status: decided (delegated, decided by Claude for the owner; the parent session ruled on the cost) · Decided by: delegated

- **Question:** after a restart, a pending snapshot staged over a restarted or deleted WAL, with the replica's newest file pruned from staging, is dated by its stamp as a commit though it holds none (seed 0x6b0658f3, #366). Can the boot tell cheaply that it equals the replica?
- **Choice:** no, so the file stays counted. The running engine already keeps such a snapshot quiet in memory; only a restart loses that.
  - Header checksums cannot say it: every level-0 file Go writes (`db.go:2301`, `db.go:3038`) and every file lsr writes carries the NoChecksum flag, and Go's compactor forces it on its output (`compactor.go:165`, D002). There is no post-apply checksum to compare.
  - A WAL span cannot say it: in another generation the span ends nowhere near the newest file's.
  - Restoring the replica's newest state to compare reads the whole database (tens of GiB), at a boot before it is judged, so with the application's writes held (D201), and in the case where the store may not answer.
- **Cost accepted:** under `stop-app`, a restart followed by a store outage longer than the bound, with that snapshot the only pending file, trips fail-stop and holds writes with nothing unreplicated. Default settings never hold writes on this trip.
- **Revisit if:** tracked checksums land (D2), which would make it one header read.
