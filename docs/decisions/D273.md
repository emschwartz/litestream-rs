## D273. A timestamp restore lists each level only as far as its chain needs (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5) · `crates/core` (`restore.rs`, `inventory.rs`)

- **Question:** an `AsOf` restore listed every level to the end before planning ([#482](https://github.com/emschwartz/litestream-rs/issues/482)). For an instant an hour into a replica with 20,000 level-1 files and a day of level-0 files that is every page of both, where Go reads a few.
- **What Go does, and why:** `CalcRestorePlan` keeps one lazy iterator a level (`restoreLevelCursor`) and stops reading a level at the first file that starts after the chain's end plus one, because nothing later can join the chain. Snapshots (level 9) are all read, since any may be the base. Upstream #1650 relies on this so its hole check does not drain pages past the instant.
- **Choice:** the same. A restore to an instant lists level 9 to the end and one page of each other level, plans, and pages on only the levels whose last listed file still touches the plan's end, then plans again. The plan is the one over the whole listing (a file past a level's first file that starts beyond the end cannot touch the chain; the gap and straddle rules judge only files that touch it). A refusal is planned again over the whole listing so its words describe the replica. Created-at times are kept across the re-plans, so none is read twice. `Latest` and `Txid` targets still list everything.
- **Cost accepted:** a restore that needs more pages re-sorts the listing each round (a few rounds, memory the listing already holds); a refusal costs the full listing it cost before.
- **Revisit if:** a `Txid` restore is also found listing more than Go (it can stop the same way).
- **Links:** plant `restore-lists-every-level`, test `restore::tests::an_early_instant_stops_listing_each_level_near_it`.
