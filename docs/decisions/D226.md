## D226. An upload holds concurrency x part size, allocated whole; streaming parts from the staged file is not done (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5)

A drill replaced Go's binary with `lsr` on a 2 to 4 GiB database at `part-size: 100MB` and `concurrency: 10`. `lsr` reached 6 to 7 GiB resident while it snapshotted and compacted, then fell back; Go stayed near 720 MiB. The memory gates passed because they ran at 5 MiB parts and counted the live heap.

- **Cause:** a part buffer grew from 4 KiB by doubling, so each part left a ladder of freed blocks of other sizes (up to the part's size). macOS keeps freed large blocks mapped, and blocks of a size nothing asks for again are never reused: a probe of four uploads of 1.5 GiB at 100 MiB parts, concurrency 10, reached a footprint of 6015 MB (about the bytes written) while the live heap stayed at 1 GiB. The doubling is also why the live-heap gate saw nothing. The fix, a part buffer reserved whole once an object passes 256 KiB, is the one `claude/memory-floor` made (D212); the same probe stays at 1008 MB.
- **Formula, measured:** an upload's memory is `concurrency x part size` for its part buffers (plus the base of the process, about 250 MiB at 10 x 100 MB), whatever the object's size; the formula in D208 (`concurrency x max(part size, length / 10000)`) is right for the live heap and, with the whole-part reservation, for the resident size. Several uploads in flight at once (a database per replica) add up.
- **Measured (studio, macOS arm64, local MinIO, 2 GiB database, part 100MB, concurrency 10, both databases replicating, drill phases through the load run, one run each):** peak resident size of the replicator 6143 MiB before, 1301 MiB after; Go 715 to 722 MiB. A 1 GiB upload to local MinIO, 12 interleaved pairs against the old build: 5 MiB x 5 -0.67% [-1.18, -0.16] (the run drifted; A/A of 8 pairs -0.06% [-0.53, +0.40]), 100 MiB x 10 -0.03% [-0.49, +0.43] (A/A +0.70% [-0.56, +1.97]), SESOI 5%, equivalent to the old build within it.
- **Go:** a level-0 upload hands the SDK a seekable staged file, which it splits into section readers "without copying it into part buffers" (`s3/replica_client.go`, `uploadSizedLTX`), so its part memory is nearly nothing; a streamed upload (a compaction) goes through the SDK's pooled part buffers, which the drill peaked at about Go's 720 MiB for. So Go's peak at this configuration is below `lsr`'s: 1301 MiB against 720.
- **Not done, and why:** holding fewer buffers means reading a part from the staged file when its turn comes, which needs `Upload` to carry a source (a staged file) and the part's MD5 before its body goes out; a compaction's or a snapshot's streamed output has no file, so it would keep the buffers anyway. That changes the engine's upload unit, which `claude/sliced-send` is reworking. The cost is a memory floor of `concurrency x part size` per upload where Go's staged uploads hold none.
- **What an operator sets:** budget `concurrency x part-size` of memory for the replicator, per database that uploads at once. The default (5 MiB x 5) is 25 MiB. Raise `part-size` only for a database whose compressed copy could pass 10,000 parts, and lower `concurrency` before it (3 x 100MB is 300 MB) if memory matters more than upload speed.
- **Gates:** the S3 upload gate counts the large blocks the writing thread allocates (one per part) beside the live heap, at 5, 8 and 16 MiB parts, and the upload and the compaction into S3 run at a part size above the default with more parts than the concurrency. Planted: `upload-part-regrown-by-doubling`, `upload-parts-queued-without-bound`. Not gated: the snapshot's own path through S3 at a large part size (it uses the same upload), and the resident size on macOS (the large-block count stands in for it).
- **Revisit if:** the owner wants a staged upload to hold less than its parts (a source on `Upload`), or a Linux profile shows resident memory above the formula.
- **Links:** D208, D212; `crates/store-s3/src/upload.rs`, `crates/store-s3/tests/store-s3/memory.rs`.

2026-11-25: the part marked "Not done" above is done in D222: an upload of a staged file holds no part. Compactions and snapshots are as described here.
