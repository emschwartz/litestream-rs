## D286. An upload that leaves staging empty does not clear a staging edit (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5) · test code only (`crates/sim`)

- **Question:** the forcing window (`crates/sim/src/forcing.rs`) forgets a staging edit once the replica takes a level-0 file that reaches the newest staged one. When staging is wiped while the engine sends its newest file, the send still lands (on the directory store its bytes come from a handle opened before the wipe). The replica then reaches the engine's newest file while staging holds nothing, and the edit was forgotten. A commit the engine never staged, then a restart, leaves a boot over an empty staging directory under a database ahead of the replica; the boot snapshots above the replica (`AheadOfReplica`) and the needless-snapshot check called it needless (nightly seed `0x126d69380a38`, exposed when #488 changed how many reads the boot makes).
- **What Go does, and why:** Go with its local LTX directory gone has no position to continue from either, and its next sync writes a snapshot. The engine's snapshot is the forced one; the check was wrong.
- **Choice:** an upload has caught up only when the newest staged transaction (the engine's own, or staging's) is still a level-0 file in staging. With staging emptied under the send, the edit stays in the window until the engine stages again and the replica takes that file.
- **Cost accepted:** after a wipe, the window holds the edit a little longer, so a needless snapshot in the few ticks between the wipe and the next staged file goes unjudged. The plant `upload-forgets-a-wiped-staging` fails the unit test that pins the rule.
- **Revisit if:** the engine ever deletes its own newest staged file in ordinary running, or stages snapshots above level 0.
- **Links:** plants `upload-forgets-a-wiped-staging`, `upload-forgets-damage-it-never-read`.
