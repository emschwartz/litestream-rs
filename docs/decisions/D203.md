## D203. The first level-9 snapshot is built from the level-0 files the first start wrote (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5)

Issue #340; the owner's concern is the load a full copy puts on the database file beside a live application (issue #315).

- **Question:** the first start on an empty replica read every page of the database twice: once for the level-0 file that starts the chain, and again a few ticks later for the level-9 snapshot. What should the snapshot be built from?
- **What Go does:** the same two reads. Its first sync stages a full level-0 file from the database and the WAL (`db.go` `verifyWithExecutor`, first sync is a snapshot), and the store's level-9 monitor starts at once, finds no snapshot, and `DB.Snapshot` reads the database again through `SnapshotReader` (`store.go` `CompactDB`, `db.go` `Snapshot`). Go is wrong to double the read, so lsr departs from it here.
- **Choice:** when level 9 holds no snapshot starting at transaction 1, and level 0 holds a run of at most 32 contiguous files from transaction 1 up to the newest transaction the listing shows, the snapshot is a compaction of those files into level 9 (`SnapshotJob::from`). The first level-0 file holds every page, so the run is the database at its end. The inputs are read from the staged copies when those are the replica's objects (as level 1 is built) and from the replica otherwise; the database is not read. The output header is a compaction's: untracked, no WAL origin, the last input's timestamp. Any other case reads the database as before: level 0 that starts later, has a hole, is longer than 32 files, or a first snapshot built this way that failed (until a restart, `MaintainState::refuse_seed`).
- **Options not taken:** a server-side copy of the level-0 file (the store trait has no copy, and the file carries a WAL origin a level-9 file does not); making the first file the snapshot and starting the chain from it (Go and boot recovery expect a level-0 file at transaction 1); one read written into both files (the sync step would hold the database read through a second upload).
- **Measured (a quiet 40-page database, page 1 in the WAL; `actor::tests::first_start`):** pages read from the database file 78 before, 39 after; bytes uploaded 2,418 before and after (1,209 at level 0, 1,209 at level 9). The upload of the database's pages twice stays: a first start sends the database to the replica twice.
- **Cost accepted:** the snapshot is only as independent as the first level-0 file: a page that file holds wrongly (it passed its checks when it was staged) is in both, where a second read of the database could have differed. The compaction decodes and checksums every input, so a damaged copy is refused, never merged. When the staged copy is gone the replica's file is downloaded instead (more egress than reading the local file). A first start whose level 0 grows past 32 files before the snapshot runs reads the database again.
- **Other full copies, counted (same tests):** a re-snapshot after a restarted WAL reads each page once; a scheduled verify reads each page once; a start with an empty working folder over the replica's own state reads each page twice (the identity check, then the snapshot that starts the new chain). The last is not this defect: the check's pass and the snapshot's pass are different jobs, and joining them is a change to the boot, left to its own issue.
- **Go reads it (differential, `crates/compat/tests/compat/merged_snapshot.rs`):** a first start with writes during the upload leaves a merged level-9 file spanning transactions 1 to 5. The pinned Go builds (v0.5.16, v0.5.18, 041a8c3) restore that prefix to the database's pages with level 0 present and with level 9 alone, and `ltx -level all` lists it. Header fields against Go's own snapshot of the same database: flags (untracked), page size, page count, pages held, first transaction, pre-apply (absent), post-apply (absent) and node id (0) are equal. Three differ and are safe: the last transaction (Go counts its own, ours is the level-0 run it merged), the timestamp (a merge keeps its newest input's stamp, Go stamps the write), and the WAL origin (Go's snapshot carries the offset, size and salts of the sync it came from, ours has none). Go takes no decision from a replica file's WAL origin and restores by pages, page size, page count and chain position.
- **Revisit if:** the second upload matters (a store with a server-side copy), or the 32-file bound is hit by busy first starts.
