## D188. `lsr take-over` stays in v1 as `lsr trust-local`, and the stop is always explained with both ways out

Status: decided · Decided by: owner, 2026-11-24 (the command stays, its new name, restore documented beside it, no alias); the internal names and the wording of the lines are Claude's (claude-fable-5-2), **delegated**; the owner can overturn them · Recorded by: Claude (claude-fable-5-2)

- **Question:** at start, a replica that holds files the local database cannot account for stops the engine with `other_writer` (D12, D173). `lsr take-over` cleared the stop. Issue #290 asked whether the stop needs a command of its own at all: keep it, replace it with something an operator already knows (a flag on `replicate`, or "restore first"), or narrow the stop until a manual step would do.
- **Choice (owner):** the command stays in v1 and is renamed `lsr trust-local`. There is no alias for the old word, since nothing has shipped.
- **Why:** "take-over" does not say who takes over what. What the operator actually states is "trust the local database over what the bucket holds", and the command now says it.
- **The other exit is documented beside it (owner):** wherever the stop is explained, both choices are named, in this order: if this database is the right one, run `lsr trust-local <db> --replica <url>` and start again; if the replica is the right one, restore from it with `lsr restore` and start from the backup. This holds for the refusal log line, the help text, the differences page, the behaviour rows that describe the stop, and the library's doc comments.
- **The refusal line (wording close to the owner's, adapted by Claude):** "replicate refused: the replica holds transactions up to {txid} that this database has no record of writing. Another replicator may be using this prefix. If this database is the right one, run `lsr trust-local <db> --replica <url>` and start again. If the replica is the right one, restore from it with `lsr restore`."
- **Names (delegated):** the library's public names for the operator's act follow the command once: `lsr_replica::take_over` is `trust_local`, and `TakeOverError` is `TrustLocalError` without its `NoMetaDir` variant, which nothing returned. The engine's word for the record stays: the takeover record, `TakeoverRecord`, `crates/core/src/takeover.rs`, the `lsr-takeover` file in the meta directory, `record_takeover`, `TakeoverUnusable` and the `Takeover*` events. The engine writes that record by itself where no operator is involved (every restore, and before it deletes staged files the replica holds), so "takeover record" names the record and "trust-local" names the operator's command that writes one. The simulator's operation and the tests named for the operator's act follow the command too (`Op::TrustLocal`, `vm_restore_stops_until_trust_local`).
- **Lines an operator reads (delegated, open to the owner's approval):** the command prints "trusting this database over the replica: takeover recorded through {txid} in {meta}", or for an empty replica "the replica is empty: there is nothing to trust this database over, and nothing was recorded". The first line of `lsr --help` is "lsr: replicate SQLite databases to a Litestream replica, and restore, verify and list one", since the old line left out replicating.
- **Cost accepted:** two words for related things. An operator runs `trust-local` and the file it writes is a takeover record; the module doc of `crates/core/src/takeover.rs` says so in one sentence.
- **Not decided here:** the further renames of the library's public interface (one public noun for the record, hiding `record_takeover`), which are issue #318.
- **Revisit if:** issue #318 picks one public noun for the record, or an operator is reported choosing `trust-local` where the replica was the right one.
- **Links:** D12, D173, D176, D177; issues #290, #318; `docs/differences-from-go.md`.
