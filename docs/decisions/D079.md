## D79. A replica store without conditional writes (delegated)

Decided by: **delegated**

- **Question:** level-0 uploads are create-only writes, so the bucket refuses a key another writer took (#96). An S3 provider without conditional writes answers `If-None-Match: *` with `NotImplemented`. The S3 store then dropped the condition by itself and counted it in `WriteStats`, which nothing read: the engine went on claiming create-only writes it was not making, and `publish` still handed back a create-only write's rejection token for a write that might have replaced another writer's object. What should the engine do on such a provider?
- **Choice:** run as Go does, loudly. The store fails the create-only commit with `StoreError::CreateOnlyUnsupported` and publishes nothing; it never drops the condition itself. The engine raises `PersistentCause::ConditionalWritesUnsupported` on the upload task and writes its level-0 uploads as replaces for the rest of the process, so `publish` hands back no rejection token for them. The cause stands after every later success until the process restarts, and comes back at the task's next success after another fault held the task's degraded state. `litestream-rs.responses.conditional-writes-unsupported: stop` (and `STRICT`) stops instead (`StopCause::ConditionalWritesUnsupported`). Each process asks again at its first level-0 upload; nothing is persisted.
- **Options considered:** refuse to start unless configured (D7 allows one default stop, another writer); a probe at start (an object Go does not speak, D6, for one request's worth of knowledge); a replica key `conditional-writes: off` that acknowledges the provider and turns the degraded state into a standing notice (rejected by the owner: another knob someone has to know to set, as `lsr accept-pages` was); keeping the silent fallback with a counter (the engine is not told).
- **Cost accepted:** on such a provider, two writers advancing in step replace each other's files and neither stops (UP-14 before #96); only a listing catches a writer that pulls ahead (UP-10). A provider that ignores the header without answering `NotImplemented` is not detected. One refused request per process start, or one multipart upload left to the orphan list. A deployment on such a provider is degraded for as long as it runs, which a coarse alert on "degraded" cannot tell from other faults. A task holds one degraded cause, so while another fault holds the upload task, health names that one.
- **Open question:** store-fs makes a create-only write with a hard link; on a filesystem without links it would need the same treatment. Not built.
- **Revisit if:** a provider is found that ignores the header silently (then probe), or the degraded state proves too noisy for providers that will never support conditional writes.
