## D192. Fail-stop holds the application's writes with a write lock the replicator keeps, not a commit hook

Status: decided · Decided by: owner, 2026-11-24 (a held write lock instead of the hook, writes held while the boot is pending, a ready future, the plain sidecar may use `stop-app`); the rest is Claude's (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5)

Replaces D20 and the commit-hook half of D82 (issue #313).

- **Question:** D82 refused the application's commits through a commit hook that `Replicator::app_connection` installed. Only connections set up that way were stopped: a connection set up on a raw handle without the hook (sqlx), one whose application set a hook of its own, another SQLite library and another process all wrote on, and nothing said so. D20 refused `stop-app` without `-exec` because the plain sidecar had no way to stop anything.
- **Choice (owner):** while writes are held the replicator keeps the database's write lock: `BEGIN IMMEDIATE` on a connection of its own (`lsr_sqlite::WriteGate`), opened by path and checked against the database's device and inode. Every writer, in any process, gets SQLite's own "database is locked"; readers and PASSIVE checkpoints go on. Writes are held while the boot is pending (except under `report`), and while fail-stop holds (D16, D17). The plain sidecar may use `stop-app`; with `-exec` the child is still stopped, and the lock is held as well.
- **Ready future (owner):** `Replicator::ready(within)` resolves once the boot is judged and writes go through again, or once they cannot (the boot keeps failing, a stop, the thread gone, the wait run out). It needs no runtime, as `stop()`'s `FinalSync` does. `wait_booted` stays and gives the same answer.
- **Delegated:**
  - The lock's connection belongs to the replicator's thread, not to the engine, so a panic, a rebuild or a stop for a bug leaves it held. The thread applies the gate at every turn and after every engine step, and a hold an application transaction keeps out is tried again within one poll interval (`Writes::Blocking` until then).
  - While writes are held the engine neither checkpoints nor bumps `_litestream_seq`: the checkpointer answers `SourceError::WritesHeld`, which the engine waits on (`Policy::Wait`, event `WritesHeld`). It is never degraded and never counted as a fault. A sync bump it refuses still lets the boot be judged, so a pending boot cannot wait on its own hold.
  - `wait_booted` and `ready` answer `Booted` only once the boot is judged, so "ready" means writes go through.
  - Events `WritesBlocked { why }` and `WritesAllowed`, once per change of the lock itself; `Health::writes` says `Allowed`, `Blocking(why)` or `Blocked(why)`. SQLite's error is not changed.
  - `app_connection` and `lsr_sqlite::app_connection_raw` become optional. They turn the automatic checkpoint off and install a busy handler that fails at once while the replicator holds writes, and otherwise waits as SQLite's default handler does for the connection's busy timeout. `app_connection_raw` takes the handle from `Replicator::writes_held()`.
  - Deleted: `refuse_commits_while`, `SetupError::CommitHookReplaced`, the hook's client data, `SidecarError::StopAppWithoutExec` and the limits D82 listed for the hook.
  - The gate does not use `Checkpointer::begin_write_lock` and `end_write_lock`, which D190 left on the trait for it: its lock is a connection of the replicator's thread, not an engine step. Both methods, the `WriteLock` token and their fakes are deleted; `SourceOp::BeginWriteLock` and `EndWriteLock` stay, never called, so recorded simulator histories that name them still read.
  - A database file replaced while the replicator opened it is `StartError::Open { kind: NotFound }`, no new variant.
  - The simulator models the held lock as a door in its SQLite model, and the runner holds it by the same rule only when `Opts::write_gate` is set, so recorded seeds replay unchanged; a judge fails a run in which the held lock goes away without a crash or a release, or a commit lands under it.
  - Log lines (plain sidecar and `-exec`): `writes blocked` with `held_by` (`booting` or the trip's name), `writes allowed`, and at debug `checkpoint waits while writes are blocked`.
- **Cost accepted:**
  - One transaction already writing when writes come to be held may still commit: the lock is taken after it (`Writes::Blocking` until then).
  - `stop()` closes the gate: a stopped replicator holds nothing, and a stop under `stop-app` lets writes through.
  - The application sees "database is locked", which D20 called misleading. The `writes blocked` line, the event and health say why; an application that wants to say more listens for the event.
  - A boot that must write to the database before it is judged (a sequence bump for a missing WAL) would wait on its own hold for ever. The replicator lets writes through from that write until the boot is judged, so the boot is judged on what it finds. A held write never judges a boot: one judged on the hold released `hold-start` before the boot stopped for a changed page size.
  - Under `stop-app`, once the application was released, a snapshot that needs a sequence bump while a trip holds writes waits until the trip clears or a restart.
- **Revisit if:** an application needs a write through while fail-stop holds (a migration, an operator fix-up), or SQLite changes what a held `BEGIN IMMEDIATE` blocks.
- **Links:** D16, D17, D19, D20, D82; issue #313.
