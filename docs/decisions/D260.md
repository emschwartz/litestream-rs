## D260. A restore to a timestamp the replica cannot meet exactly is refused, not answered with an earlier state

Status: decided · Decided by: owner, 2026-11-26 · Recorded by: Claude (claude-opus-5-5)

- **Question:** `restore -timestamp T` asks for the database as it stood at T. When the level-0 files around T are past retention and only compacted files remain, the replica no longer holds the state at T exactly: T falls inside a compacted file. What does the restore do?
- **What Go does:** it restores the newest state that ends before T and exits 0, with no message.
- **Choice:** litestream-rs refuses with an error that names the newest earlier state it could restore (the transaction it ends at). `--allow-earlier` opts into Go's answer and restores that state, and `--txid` with the named transaction restores it too.
- **Why:** a backup check that restores an earlier point than it asked for passes while checking the wrong thing. This project never gives a shorter or a different history without saying so.
- **Cost accepted:** a script that runs Go's command with a timestamp that old fails under litestream-rs, and adding `--allow-earlier` makes the script litestream-rs only.
- **Links:** `crates/cli/src/args/restore.rs` (`--allow-earlier`), `crates/cli/src/render.rs` (`PlanOutcome::AsOfInsideFile`); [differences-from-go.md](../differences-from-go.md).
