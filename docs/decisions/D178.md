## D178. A restart finds a quiet snapshot from where its WAL span ends (delegated)

Status: open to owner review · Decided by: Claude (fail-stop), **delegated**

- **Question:** the open defect in D177: under `stop-app` a trip for age fired with no cause after the clock jumped forward. The engine had staged a snapshot for an operator request on a quiet WAL and marked it quiet in memory, so it dated no commit. A restart lost the mark: boot re-derives quiet files only by comparing a pending file's pages with a table seeded from the replica's newest file onward, and a snapshot rewrites pages that table never saw. The file was dated by its stamp, 26 hours old after the jump, and tripped over a replica that held every commit.
- **Choice:** at boot a pending staged file is also quiet when its header's WAL span (salts and end offset) ends where the previous file's did. It holds no frame the previous file lacks, which is the rule the running engine already uses for the same snapshot (`ended_where_synced`). No new state: the span is in the file header.
- **Options considered:** a database checksum in the file (staged files are untracked, so there is none); dating unprovable files from the boot (a crash loop would forget real commits, against D80); an exemption in the simulator's judge (it would hide the engine's false stop).
- **Cost accepted:** a commit that reached the database file without a WAL frame past the previous file's end (made and checkpointed away by another process between two engine reads) is missed by this rule as it is by the running one: a late trip, never a false one.
- **Links:** D80, D85, D177; `crates/core/src/pages.rs` (`seeded`).
