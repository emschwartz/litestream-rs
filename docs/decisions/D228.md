## D228. Every level follows on: a compaction starts right after its level's newest file, and a hole a lower level can fill is filled (delegated)

Status: decided · Decided by: Claude (claude-fable-5-2), **delegated**; the owner can overturn it · Recorded by: Claude (claude-fable-5-2)

- **Question:** after a rollback from this engine to Go, Go logged `compaction failed level=3 ... non-contiguous transaction ids in input files: (127,137) -> (142,142)` at every tick. The replica's level 2 had holes that level 1 covered. What must a level look like, and what does the engine do about a replica that already has holes?
- **What Go does.** `Compactor.Compact(dst)` reads every source file from the transaction after the destination's newest (`compactor.go`), and the ltx compactor refuses the set when one input does not start where the one before ended (`ltx/compactor.go:125`). So Go needs, for every level 1 to 8, that the files of the level below above its newest file form one contiguous run. It retries at every tick and stays stuck at that level until retention prunes the files below the hole. Go does not compare its first input with the destination, so a hole exactly at the destination's newest file is copied one level up in silence. Go's restore plans across all levels and its level-0 retention reads only level 1's newest transaction, so a hole in level 2 or 3 costs Go no data; a hole in level 1 would (Go deletes the level-0 files below level 1's newest).
- **Cause.** A compaction output carries its last input's time, so a level-1 file whose last input was committed before the window opened leaves the window open, and the next commit becomes a second level-1 file in the same window. The level-2 pass that follows reuses the listing made before those jobs (the carried listing of D193), and the engine remembered one newest file per level: the pass saw only the second file and compacted it alone. It began with the short listings (commit 382a019be). Level 1 was never affected: level 0 is listed whole.
- **Choice.**
  1. The rule, in the planner (`plan_level`): a compaction's inputs are the contiguous run that starts at the first source file above the destination's newest file, and that file starts at the transaction after it. A level never gains a file that does not follow its newest. The first file of an empty level may start anywhere.
  2. The carried listing gains every output the engine confirms after it was made, so it shows what a listing made now would.
  3. A pass that lists only tails and finds that the sources do not follow plans nothing for that level and lists the whole replica: a tail cannot tell a lost range from one a lower level still holds.
  4. Repair: a whole listing closes the first hole in any level's sources above the next level's newest file, before any other job and whatever the windows, by compacting the files the level below holds inside the hole into the hole's level (that level's own hole first, down to level 0). It then lists again, so holes close one at a time, lowest level first. A fill that fails waits out the backoff of the level it writes, and the level above the hole waits with it (a tail that does not follow asks for no whole listing meanwhile). While a level at or below the hole's holds a rejected output, the hole is neither closed nor passed: the delete goes first. A source file that starts at or below the destination's newest file and ends above it holds those transactions, so nothing is written under it.
  5. A range no lower level holds in files that line up is passed as before: the next job starts after it and the level above has the same hole. This is what Go does when the hole is right above its destination, and the engine is not stuck where Go would be.
  6. A short pass's compaction that would not start right after its level's newest file is a bug site (`CompactionLeavesAHole`), checked before anything is written.
- **Why.** The replica is the contract, and a replica Go cannot compact is a broken one even when nothing is lost. The cause is fixed where the stale view was built (2), the planner states the rule once (1, 3), and the check before the write (6) means a future stale view stops as a reported bug, never as a hole. The repair is one more compaction of files that are already there, into a key nothing holds; it writes no new kind of object and keeps no state.
- **What a hole costs this engine.** Nothing: retention deletes level-0 files only under a cover of listed level 1 to 8 files taken together, and levels 1 to 8 only below the snapshot floor; a restore plans through the level below wherever a level has a hole. Both are pinned (`holes_in_levels_two_and_three_cost_retention_nothing`, `holes_above_level_one_cost_a_restore_nothing`). No range was lost by the defect, under either implementation.
- **What an operator does with a replica that has holes.** Nothing while this engine runs: its first whole listing (at start, and at most 15 minutes of maintenance passes after any other) closes them while level 1 or the level below still holds the files. A replica already handed back to Go, where Go logs the failure: run this engine against it once, or wait for Go's snapshot retention to prune the files below the hole (the errors stop then; no data is at risk meanwhile). Holes in the top level, and holes below the next level's newest file, are left: no compaction of either implementation reads them again. Go run with `verify-compaction: true` (off by default) checks a whole level after each compaction and logs `post-compaction verification failed` as a warning for the holes that are left, until snapshot retention prunes those files.
- **Cost accepted:** the holes an earlier version left below the next level's newest file and in the top level stay until retention prunes them (closing each would cost a compaction and a whole listing for files nothing but Go's optional check reads). Each hole that is closed costs one compaction and one more whole listing. A tail that does not follow costs a whole listing where a version before would have planned at once. An engine that meets the bug site rebuilds and lists whole, which then plans the level from everything the store holds. A fill that can never succeed (a file inside the hole that does not verify, say) holds the level above the hole from compacting for as long as it fails, where an earlier version went past: the failing compaction is the degraded state health reports, and Go would be stuck at the same level on the same replica.
- **Revisit if:** Go starts comparing its first input with the destination (then a hole right above a level's newest file stops it too, and 5 would need a different answer), or a store makes a whole listing expensive enough that one per hole matters.
