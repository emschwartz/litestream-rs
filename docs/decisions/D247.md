## D247. The fault VFS does not flush the drive for the engine's FULL sync of the WAL

Status: decided (delegated) · Decided by: Claude (claude-sonnet-5-5), for the owner · Recorded by: Claude (claude-sonnet-5-5)

- **Question:** the lsr-sqlite fault tests timed out when the workspace ran under load. Each injected step of a cycle makes the engine sync the WAL with `SQLITE_SYNC_FULL`, which the unix VFS turns into `fcntl(F_FULLFSYNC)` on macOS (8 ms a call). The sync-error and read-error tests took 82 s and 71 s alone against a 180 s limit.
- **Go:** no equivalent; Go's tests do not run a fault matrix through a VFS.
- **Choice:** the test fault VFS (`crates/sqlite/src/testing/vfs.rs`) passes `SQLITE_SYNC_NORMAL` to the real file in place of FULL, as `host_fs.rs` already does for the harness's stores. Both tests take 23 s alone. The shipped engine still asks for FULL; `sync_wal` is unchanged.
- **Cost accepted:** no test in this suite exercises a drive cache flush on macOS. The tests check the durability law the VFS models in process, which a drive flush does not change, and Linux CI runs `fsync` either way.
- **Revisit if:** a defect appears that only a real drive flush would show.
