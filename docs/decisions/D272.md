## D272. The boot read-back reads each newest file's header and tail, not its body

Status: decided · Decided by: owner, 2026-11-26 · Recorded by: Claude (claude-opus-5-5) · fixes #476

Amends the reasoning of D6 for the boot read-back, and supersedes D266 (the read-back sliced across ticks): with no body to read, nothing is left to slice.

- **Question:** after every boot, maintenance read the newest file of each level above 0 whole (`crates/core/src/maintain/audit.rs`). D6 kept that read as a correctness check that changes nothing Go sees. At full size it reads the level-9 snapshot, the whole database, on every restart: billed egress where the provider charges for it. How much of each file must the boot read?
- **What Go does:** Go reads no replica file at boot; it lists for the newest file of a level (`replica.go`, `MaxLTXFileInfo`). No Go defect is named for this read.
- **What the read guards:** a compaction output or snapshot the store reported as damaged (a checksum that does not match) is deleted at once, and a crash before that delete leaves the object listed. Signed uploads (S3's SHA-256, a part's `Content-MD5`) have the store refuse a body that does not match before it publishes, so the case left is an object cut short or holding another file.
- **Choice (owner, option b):** read each newest file's header (100 bytes) and its last 25 bytes: the page index's zero terminator, the index size field and the trailer. The header must decode and name the key; the tail must end at the listed size, the index must fit between the header and the tail, and the trailer must decode against the header. A file that fails on two reads and that the other files cover is deleted, as before; one nothing covers degrades `RemoteCorrupt`.
- **Requests and bytes per restart,** at the drill's 24 GiB database (newest files: level 1 16.4 MB, levels 2 and 3 51.2 MB each, level 9 16.87 GB): before, 4 GETs, one stream a file, about 16.98 GB; after, 8 ranged GETs and 500 bytes. In the engine test (`a_boot_reads_back_only_the_header_and_tail_of_each_newest_file`, four levels), 6 GETs became 8, and the bytes went from the four files whole to at most 500.
- **Cost accepted:** a body the store damaged behind a sound header and tail is not found at boot. Its first full read finds it instead: a compaction that takes it as an input degrades `RemoteCorrupt` until a level above covers it, and a restore refuses it, never returns it (the simulator's `corrupt_l1_publish_then_power_loss` and `corrupt_l2_publish_then_power_loss` now expect exactly that). Two more GETs a file than the whole read made where the store holds a stream.
