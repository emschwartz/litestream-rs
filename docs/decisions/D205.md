## D205. A snapshot holds 18 bytes a page, not 86 (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5)

Issue #64 (the page checksum table is unbounded) and #46 (memory on the hot paths): the owner asked for the per-page memory of a snapshot to be measured at 1, 4 and 16 GiB and cut as far as its floor.

- **Question:** a snapshot held about 86 bytes for each page of the database (the gate allowed 112). At 16 GiB of 4 KiB pages (4.2 million pages) that is 360 MB. Which of those bytes does the work need?
- **Measured** (heap peak of a snapshot at 8,192 and 32,768 pages, slope per page; the law is linear, so GiB figures are the slope times 262,144 / 1,048,576 / 4,194,304 pages): 86 bytes a page at the start (22 MB at 1 GiB, 90 MB at 4, 360 MB at 16). Where it went: the plan, a list of one 32-byte entry a page (48 while it was sorted); the page checksum table, a `BTreeMap` of about 20 bytes an entry; the encoder's page index, varint bytes copied into one buffer, then into a second for the tail of the file, then into the output buffer.
- **Choice:**
  - The plan is walked, never listed (a counter and the WAL page map's own order): 0 bytes a page.
  - The page checksum table is one 8-byte slot a page, indexed by page number (a checksum always has bit 63 set, so zero means no page): 8 bytes, 32 MB at 16 GiB, where the map held about 20.
  - The encoder keeps the index in 16 KiB chunks and hands each onward as it frees it (a new `write_index_chunk`, which the snapshot and the compaction call after their last page): about 9 bytes a page, held once.
  - Measured after (the heap peak of a snapshot, release build): 16 bytes a page at 32,768 pages, 18 at a million; 4 MiB at 1 GiB of 4 KiB pages, 18 MiB at 4 GiB, 74 MiB at 16 GiB, against 86 bytes a page (22, 90 and 360 MB) before. The gate's ceiling is 20. Two first versions measured 27 at 16 GiB: a vector for the table that grew by an eighth (the old and the new copy alive together while it grew), and an index copied whole into the output buffer at the end (the buffer doubling over it). Chunks for the table, and the index handed onward in pieces, fixed them.
- **Floor:** 8 bytes of table plus the index, about 9 bytes at a 4 KiB page: 17. The index is the LTX file's own page index, written at the file's end, so it is held until the last page is encoded (Go's LTX encoder keeps 24 bytes an entry in chunks and spills to a temporary file past 1,048,576 entries, 4 GiB of 4 KiB pages, when a spill directory is set; `.upstream/ltx/encoder.go`). The table could be 4 bytes a page by keeping half of each checksum, which weakens the check on database-file pages from 64 to 32 bits; not done, the owner's call.
- **What Go keeps:** no table of page checksums across syncs (this one guards the database file against writes that bypass SQLite, and is ours); per sync, a `map[uint32]int64` of the WAL's newest frame offsets (`db.go` `pageMap`), which Go's map layout makes several times larger than this slot, and no list of the plan.
- **Cost accepted:** the table is dense: it reaches the highest page recorded, so a database with one very high page number and nothing below it holds the slots in between (8 bytes for each page of the database, at most, since callers pass pages of the database). It grows by chunks of 4,096 slots (32 KiB), so it is never copied.
- **Revisit if:** a deployment replicates databases large enough that 17 bytes a page matters (about 75 GB of heap at 16 TiB), where the index could be spooled to a staging file.
- **Links:** issues #46, #64; D206.
