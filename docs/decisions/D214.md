## D214. An older copy of the database is not "the replica plus more": a replicator counter below the replica's stops the start

Status: decided, **delegated** · Decided by: Claude (claude-sonnet-5-5), for the owner, 2026-11-25; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5) · Amends D194

- **Question:** D194 lets a boot with a brand-new working folder carry on, with a snapshot above the replica's newest transaction, when the database was written after the replica's newest file and holds at least half of its pages. A Jepsen-style review (finding F1, issue 364) reproduced a history that rule takes for the benign one: host A replicates, a file backup is taken, A commits more and replicates, A is lost, and the operator plain-copies the older backup to a new host and starts lsr on the same replica. The backup has most of the replica's pages and a modified time of now, so the boot snapshots the older database above the replica, and the replica's newest state goes back (the lost commits stay reachable by transaction id until retention). What fact tells an older copy from the replica plus more?
- **Choice:** the replicator's own counter. `_litestream_seq` (`id INTEGER PRIMARY KEY, seq INTEGER`) holds one row that each replicator checkpoint adds one to. An image that holds a lower value than another is an ancestor of it. The identity check (`crates/core/src/identity.rs`, `identity/counter.rs`) finds the counter table's root page by walking the local schema, reads the local value, keeps the replica's bytes of that same page number while it restores the replica's newest state, and answers `Other` (the boot stops, `other_writer`) when the local value is below the replica's. An empty counter table reads 0. A counter that cannot be read on either side (the schema names none, or the replica's page is not a one-row table leaf) is no evidence: the earlier tests decide, as in D194. Everything else in D194 stands.
- **What Go does, and why it is wrong in one of the two histories.** Go (`db.go`, `checkDatabaseBehindReplica`, issue 781) has no start-up identity check. With no local files it takes the replica's newest file as its position and snapshots the local database on top, in both histories. For the lost working folder with later writes (issue 329) that is right: the database is the replica plus more, and Go and D194 carry on. For an older copy it is wrong: the snapshot becomes the newest state and the commits after the backup are gone from a restore of the newest state. The owner's rule of 2026-11-24 ("avoid stopping loudly where Go would not for a circumstance that is likely to happen without someone doing something dumb") puts the first history on the ordinary side and the second, a backup put back over a newer replica, on the "dumb" side. This keeps the first working and stops the second.
- **Why the counter is monotone.** Go's `bumpLitestreamSeq` and ours run the same statement (`INSERT INTO _litestream_seq (id, seq) VALUES (1, 1) ON CONFLICT (id) DO UPDATE SET seq = seq + 1`): at each checkpoint (default every 60 s when there were writes, or at 1,000 pages) and at open when no WAL exists. Nothing lowers it. It lives in ordinary table data, so it survives checkpoints, WAL restarts, file copies, `sqlite3 .backup` and VACUUM (which may move its root page: the check then reads it as no evidence). A database Go replicated last and then lost its working folder reads the same way as one lsr replicated.
- **Alternatives, and why not:**
  - The SQLite header's file change counter (offset 24), version-valid-for (92) and schema cookie (40). Measured with SQLite 3.x: in WAL mode the change counter does not move on ordinary commits or checkpoints (only when page 1 changes, as for a schema change), and `sqlite3 .backup` rewrites both in the copy (a source with counter 2 and cookie 3 gave a backup with 1 and 1), so a backup of a newer database can read lower than an older one. Rejected: it would stop an ordinary history.
  - The WAL salts, or whether a WAL exists. A database whose extra commits were checkpointed into the file (the application's last close, a TRUNCATE) has no frames and fresh salts, and an older copy has none either. Rejected: it stops the ordinary history.
  - Matching each differing page against an earlier version in the replica's history. Weaker than it looks: a same-size UPDATE and its undo can restore a page bit for bit within one counter interval (a false stop in the ordinary history), compaction erases the versions an old backup would match, and it reads many files. Rejected.
  - Refusing `Ahead` unless the operator opts in. Safe, but it is exactly the stop in issue 329 that the owner did not want. Rejected.
  - A durable marker of our own beside the database or in the bucket. The owner dislikes new on-disk files Go lacks, and the counter is the one such fact both replicators already write.
- **What it costs.**
  - The window. The counter moves only at a replicator checkpoint, so a backup taken after the replica's last bump and before the commits that followed it carries the replica's counter and still passes. That is at most one checkpoint interval of commits before the replica's newest file (60 s by default; with `checkpoint-interval` off, until the WAL reaches the page threshold), and only for a backup taken then. The boot snapshots above, warns, and the commits after the backup leave the newest state; they stay reachable by transaction id until retention. The warning no longer claims the database is the replica plus more: it says what is known (written after the newest file, holds most of its pages, shows no sign of being older) and names what an older copy costs. `ahead::` tests and `older_copy::an_older_copy_taken_after_the_last_bump_carries_on` pin the window. A stricter fact would need the replicator to write a monotone mark on every commit, which Go does not, and the owner's rule (no stop Go would not make for an ordinary circumstance) does not ask for it.
  - A false stop in a rare ordinary history: a counter the replica holds that the database never had. A Go build without upstream bcd69ae (every release through v0.5.18) can upload a bump SQLite never committed (the known mismatch of `alternate/uncommitted.rs`); if the application then commits from the true state, the replica's counter is one above the database's. After a lost working folder the start then stops, and `lsr trust-local` answers it. The same for an application that recreates the counter table. Judged rare and loud enough to accept.
  - The check reads the local schema before the restore (about one page for a small schema, capped at 4,096 pages), keeps one replica page (one page of memory) and adds no store call.
  - A replica restored by an engine that does not write the table where the local database has it (a VACUUM that moved the root) reads as no evidence, never as a stop.
- **Second opinion** (a deep review by two other model families, given the two histories and the candidate facts without a proposed answer): gemini-4-argon: use the counter; header fields fail (the change counter does not move in WAL mode and `.backup` rewrites them), page-history matching fails (same-size updates restore pages), and the residual window is one checkpoint interval; it also asked that a root page that moved or is not a counter leaf read as unknown, not as a stop. Codex (via the codex-rescue agent): a lower counter is a veto when provenance is trusted; resolve the table through each image's own schema; warn rather than stop where a legacy Go build may have uploaded an uncommitted bump; and the window has no guaranteed bound, since it lasts until a higher bump reaches the replica. Taken: the veto, the unknown-is-no-evidence rule, and the Go-bump cost above. Not taken: reading the replica's schema (the replica is read as a stream, not at random, and the local schema's root number is checked by the shape of the replica's page; a one-row table of the same shape at that number would be misread, which needs a VACUUM and half the pages equal), and warning where a stop is chosen (the owner chose a stop for the older copy).
- **Calls:**
  - Call: no counter evidence means the earlier tests decide (a database whose counter cannot be read passes as in D194). Cost if wrong: an older copy with an unreadable counter passes; judged unreachable with lsr, whose own open creates the table before the check.
  - Call: the new simulator scenario, `older_copy_on_a_new_host`, does not let the driver answer the refusal with `trust-local` (as `after_refusal` does for a lost working folder), since an older copy is the database an operator must not trust.
- **Revisit if:** a stop is reported where an operator had a legitimate database, or the window needs closing (then the replicator itself must write a monotone mark more often than a checkpoint, a change for Go too).
