## D302. Crypto and common primitives come from established crates (owner)

Status: decided · Decided by: the owner · Recorded by: Claude (claude-opus-5-5) · Amends: D164

- **Question:** D164 allows a runtime dependency where it replaces hand-written code outside the replication contract and the Go-fidelity surface. Does that cover small primitives the code wrote itself, such as SigV4's HMAC-SHA-256?
- **Ruling (owner, 2026-11-27):** "we can definitely use the hmac crate. crypto and other super common functions like that should not be reimplemented. you can change the public type if it makes sense". Cryptography (hashes, HMAC) and other common primitives (hex, percent-encoding, date formatting, CRC) come from established crates, never hand-written.
- **Applied:** SigV4 signs with `hmac` (0.13, MIT OR Apache-2.0); hex encoding and decoding uses `hex` (0.4, MIT OR Apache-2.0), and `lsr_store_s3::hex` is gone; SigV4's query encoding, the fake S3's key encoding and the integrity check's `file:` URI use `percent-encoding`; the fake S3's HTTP-date uses `jiff`.
- **Still hand-written, on purpose:** what D164 keeps (the replication path, the Go flag parser and Go-compatible output, the YAML pipeline, the `/metrics` and `/healthz` server, the shell-words port, the slog format, and the credential chain's logic, though its primitives come from crates). Also the seeded splitmix64 generators in tests and the simulator: a crate would change every recorded stream for no gain. Test oracles written independently of the code they check (the bitwise CRC-64 in lsr-ltx's tests) stay too, since an oracle that shares the implementation checks nothing.
