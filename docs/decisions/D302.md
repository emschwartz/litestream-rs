## D302. A restore starts from a whole-database copy later in its chain (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5)

- **Question:** a restore of a 24 GiB database to a transaction past the writer's whole-database level-0 file (the copy taken when the WAL no longer continues the replica) read 34 GB: the level-9 snapshot, then a level-1 merge of the copy, each about the size of the database. The copy rewrites every page the snapshot holds, so the snapshot and every file before the copy add nothing. Go plans the same chain (`replica.go` `CalcRestorePlan` always starts from the snapshot) and reads the same bytes. How should a restore skip them?
- **What the planner can know:** nothing in a file's name or header says it holds every page; LTX calls only a file that begins at transaction 1 a snapshot. Only the file's pages prove it.
- **Decision:** the chain is planned as before. A fresh attempt then takes the newest file after the base whose size is at least three quarters of the base, when the base is 16 MiB or more (`ContiguousChain::whole_candidate`, `crates/core/src/plan.rs`), and reads it first. If its pages run from 1 to its commit with none missing, it is the start and the files before it are never read. The first page out of that run ends the read; the sink is reset and the chain is applied from the base as before (`start` and `apply_whole`, `crates/core/src/restore.rs`).
- **Rejected:** reading the copy's page index first (two more requests on every candidate, and an index no checksum covers); applying files newest first and skipping pages already written (a page map as large as the database, and a rewrite of the tail replanning and the checksum chain).
- **Cost accepted:** a candidate that is not whole costs the bytes up to its first missing page and one read Go does not make. This is the one request here beyond Go's that guards against no Go defect; it is taken because the size gate makes it rare and because a hit saves at least the snapshot's read, so the restore makes fewer requests than Go whenever the guess is right. A whole copy smaller than three quarters of the base (a database that shrank by more than a quarter since the snapshot) is read the old way.
- **Tests:** core `a_whole_database_copy_after_the_snapshot_is_the_start_and_nothing_before_it_is_read`, `a_large_file_missing_a_page_is_not_a_start_and_costs_only_the_bytes_up_to_the_gap`, `a_large_file_missing_its_last_page_is_read_through_and_not_a_start`, `a_whole_copy_whose_header_disagrees_with_its_name_is_rejected`, `whole_pages_run_from_one_with_none_missing_and_skip_the_lock_page`, the `whole_copy_candidate` planner tests; plant `restore-reads-the-base-under-a-whole-copy`.
