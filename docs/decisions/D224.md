## D224. A level with no file starts above the newest snapshot, and the first snapshot goes before the levels (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5)

Issue #340 and the outside reviews of the replication-while-copying study: a quiet first start moved the database five times (levels 0, 1, 2, 3 and 9) and downloaded it twice, because each level's planner takes every file of the level below that lies above its own newest, and an empty level has no newest.

- **Question:** which files may a level that holds nothing take as inputs, and which job goes first on a replica with no snapshot?
- **What Go does:** the same five uploads. Go's compaction of an empty level takes every file of the level below (`compactor.go`), and its level-9 monitor starts beside the others. Go's traffic is the wasteful part; its format is not.
- **Choice:**
  - A level with no file takes only source files above the newest level-9 snapshot a restore can start from (`plan_level` in `crates/core/src/maintain.rs`). A level that holds a file is planned as before, from its own newest. Every level stays contiguous from its first file, which Go's compactor requires ("non-contiguous transaction ids in input files").
  - While level 9 holds no snapshot and level 1 holds no file, the snapshot step is planned before the levels (`decide`). A snapshot that is backing off or waiting lets the levels run as before, so a failing snapshot never stops compaction. A short pass is unchanged (it runs after a whole listing has already planned the first snapshot).
  - The staged-file prune treats the newest snapshot's last transaction as the compacted bound while level 1 is empty (`level_one` in `actor.rs`). Without it, local staging would never prune on such a replica until level 1 next ran.
- **Measured (`actor::tests::first_start::the_first_start_uploads_the_database_twice_and_downloads_none`, the 40-page rig, each file 1,209 bytes):** one object at each of levels 0, 1, 2, 3 and 9 before (6,045 bytes uploaded), objects at levels 0 and 9 only after (2,418 bytes); replica reads: six before (level 1 twice, level 2 twice, level 3, the snapshot's check; 7,254 bytes), one after (the snapshot's check; 1,209 bytes). On a 4 GiB database that is two uploads (8 GiB) in place of five (20 GiB), and 4 GiB downloaded in place of 20 GiB.
- **Staging peak:** unchanged by this decision, one full level-0 file; the file is released at the next commit (the newest staged file always stays), where before it waited for level 1.
- **Restore, as-of and Go:** the restore planner, which starts from the newest snapshot at or below the target and reads the files above it, needs nothing from the levels below the snapshot. `the_snapshot_of_a_first_start_restores_the_database` restores Latest, a transaction and an instant. The pinned Go builds restore a replica of this shape and run their own compaction over it (`merged_snapshot::live::go_compacts_over_levels_that_start_above_the_snapshot`); that Go test also fails on a replica written by main until the level-hole fix lands, because main's own level 2 and 3 passes leave holes Go refuses to compact across (not caused by this decision).
- **Cost accepted:** the level-0 full file stays on the replica until a later snapshot's floor passes it (level-0 deletion is gated on a file below the floor or one a level 1 to 8 file covers), so the replica holds the database twice for the first snapshot interval. A scheduled snapshot that ends inside a source file leaves that file out of an empty level (it is covered by the file's own level), so such a level starts at the next file. A replica older than its snapshot (a hand-built one) restores by the snapshot and the files above it, as before.
- **Revisit if:** a server-side copy exists (the level-9 file could then cost no upload), or the level-0 full file's extra day on the replica matters.
- **Links:** D205 (the first snapshot is merged from level 0), D193 (what a maintenance pass lists), `docs/behavior.toml` MAINT-1 and MAINT-6.
