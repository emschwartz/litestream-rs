## D259. A compaction goes to the replica a slice a tick, with syncs and uploads between (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5) · D255's slicing, applied to compactions

- **Question:** a compaction was one unit of work. A level-3 compaction of a 4 GiB database held the engine's one thread for its length, and no commit was synced or uploaded meanwhile. How does the engine keep replicating while it compacts?
- **What Go does, and why:** `Store` runs each level's compactions in a goroutine of its own (`store.go:242-252`, `monitorCompactionLevel`), beside the sync and the level-0 uploads, so a long compaction delays neither. `Compactor.Compact` (`compactor.go:104-190`) opens each input once, a local level-0 file when it has one (`LocalFileOpener`), and streams them through one merge into one upload. Nothing stops Go's retention from deleting an input under a running compaction.
- **Choice:**
  1. A compaction, and a level-9 snapshot merged from level-0 files, keep the merge between ticks (`compact::Compacting`, `maintain::Merging`) and go through the machinery D255 built for snapshots: one job part-way (`Sliced`), its slices first, the rest of the engine a tick after every eighth, `Event::Sending` for each slice.
  2. Each slice reads about the tick's bytes of input (`UploadConfig::bytes_per_tick`, 8 MiB) and hands the replica at most the tick's bytes of output; the output is published only by the slice that handed over its last byte and found the upload's parts answered (`docs/decisions/D233.md`).
  3. The output takes in only the files listed when it began; a level-0 file uploaded meanwhile goes into the next compaction, as under Go.
  4. Each input keeps one stream across slices: a new `ObjectStore::hold_stream` returns a stream that borrows nothing, so it can live between ticks. S3's is its one GET (`docs/decisions/D257.md`). The default holds the object open (`ObjectStore::open`), so a staged copy deleted or renamed under the merge reads on from the file it opened. Making every store's `read_stream` own its store was looked at first: about 40 implementations, the role wrappers and the counting test stores among them, borrow the store they wrap, so a second method was shorter.
  5. Checkpoints run between a merge's slices: it reads files, not the database, as Go's compactor does. Maintenance lists and deletes nothing while a job is part-way, so retention never deletes a replica input under it. The staging prune waits while a merge reads staged copies, which Go does not guard; a staged copy found missing or unreadable part-way aborts the upload and starts the merge again from the replica's copies, from its first page.
  6. A slice that handed bytes over and then found its parts in the way is the tick's unit all the same, so a tick never hands the replica more than its bytes. The same holds for a snapshot's slice, which could do this before.
  7. A failed slice aborts the upload and the job is retried on its schedule; a drain runs no maintenance and ends it; a stop, a rebuild and a crash drop it, and the next start clears what it left.
- **Cost accepted:**
  - Merge slices go first for their share, as a snapshot's do, rather than after uploads: one mechanism, and level-0 uploads get one tick in nine while a compaction runs.
  - Memory between ticks: the merge's read window per input, one page per input and the encoder's 256 KiB flush, beside a sync's and a send's.
  - An S3 connection held idle between slices may be reset by the server; the retry layer opens it again where it stopped, one more GET only then.
  - A staged copy replaced in place (other bytes under the same file) between the identity check and a slice is the race D236 accepted; slicing widens its window, and the held handle narrows it again on a directory store.
  - 529 production lines (`just prod-lines`): 472 in lsr-core, 23 in lsr-store-s3, 34 in lsr-replica.
- **Measured** (Mac Studio, macOS arm64, internal disk, directory replica; main at b86551b76 against this branch, release builds; a 4 GiB database under 20 commits a second of 16 KiB; after the first snapshot one transaction rewrites every row, and levels 1, 2 and 3 at 5, 10 and 20 s windows take in that 4.3 GB file; three runs each, arms interleaved; the script is not in the repository):
  - The longest stretch with no level-0 upload, from level 2's file holding the rewrite to 3 s after level 3's: 2.62 to 2.73 s on main, 1.04 to 1.05 s here, which is the one-second poll interval (the median gap is 0.99 to 1.02 s in both).
  - Level 3's compaction ends 2.62 to 2.71 s after level 2's on main and 2.58 to 3.07 s here, in 536 slices; one level-0 file goes up in that window on main and three here.
- **Options considered:** reopening each input at every slice (requests Go does not make); merge slices after uploads (a second turn-taking rule beside D255's); a staged copy of the output (a local file Go does not write).
- **Revisit if:** a measurement shows the turn-taking costs more than a quarter of a compaction's speed, or idle connections between slices are reset often enough to show in the request count.
