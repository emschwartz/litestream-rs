## D293. A drain's retention pass reads back the newest files before its first delete (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5) · `crates/core/src/actor/once_retention.rs`

- **Question:** the retention pass `replicate -once -enforce-retention` ends with (D167) deletes the older snapshots and the level 1 to 8 files under the floor they leave, keeping each level's newest file. A drain runs no maintenance, so the read-back of each level's newest file (`crates/core/src/maintain/audit.rs`), which a boot and a refused write both owe, is still owed when the pass starts. The pass deleted on the strength of newest files nobody had read since the process began. A newest snapshot a store took cut short, or an output left under its key by a refused write, then cost the older files that could still restore.
- **What Go does, and why:** Go's `-once -enforce-retention` (`replicate.go:519-526`, `store.go:863-883`) deletes from the listing alone and never reads a file back. It has no read-back at all, so a damaged newest file is a risk Go does not see.
- **Choice:** before the pass's first delete, if the read-back is owed and retention is on, the pass reads back the newest file of each level above 0, two ranged reads of about 125 bytes each, as the daemon does before it plans from a listing. A file that does not verify, or a read that fails, ends the pass as `FinalRetention::Failed` with nothing deleted, as a failed listing does (no retry, as Go returns its first error). The read runs once per pass, not once per delete job. A stop that arrives mid read-back needs no case: a plain drain deletes nothing, and the pass only runs after the drain has uploaded everything.
- **Not done:** repairing a rotten newest file in this pass (the daemon does, after two failed reads). The next daemon start does it; a one-off run that finds one reports the failure and leaves the replica as it was.
- **Cost accepted:** two small ranged reads per level that holds a file, once per `-once -enforce-retention` run, which Go does not make. They guard against the Go defect above (D241). A single bad read of a sound file ends that run's retention as failed, exit 1, and the next run tries again.
- **Revisit if:** the pass should repair as the daemon does, or Go starts reading its newest files back.
