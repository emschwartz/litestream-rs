## D202. The engine thread's stack is 768 KiB (delegated)

Status: decided · Decided by: Claude (claude-fable-5-2), **delegated**; the owner can overturn it · Recorded by: Claude (claude-fable-5-2) · Changes the size chosen in D87; its gate stands

- **Question:** D87 set the engine thread's stack to 512 KiB, about twice the debug build's peak, and made every suite run at half that so growth fails a test first. On 2026-11-25 the half-stack run overflowed in CI on x86-64 Linux after a day's changes to maintenance (58 tests, every one "thread 'lsr-replica' has overflowed its stack"). D87 says that is when to measure again. What size now?
- **Measured** (2026-11-25, main bc16a71, x86-64 Linux built on an arm64 host and run under emulation; the replica, sidecar and CLI suites at each size): debug passes at 272 KiB and fails at 264 (it was 240 and 232); release passes at 48 KiB and fails at 40 (it was 64 and 48). On arm64 macOS debug passes at 248 and fails at 240, so the land gate was green there. The debug depth is the frames of the `async fn`s between the engine's loop and a compaction, 15 to 37 KiB each unoptimised; nothing recurses and the shipped build did not grow.
- **Choice:** 768 KiB. The gate's half is then 384 KiB, 112 KiB above the debug peak, where 512 KiB left the gate 16 KiB under it. The rule of D87 (the shipped size is at least twice the deepest path any suite reaches in a debug build) is kept, not loosened.
- **Cost accepted:** 256 KiB more reserved address space for each engine thread and each running verify thread: about 250 MiB more for a process with 1,000 databases, committed only under strict overcommit. Resident memory does not change: a thread's stack pages are backed when touched, about 48 KiB in the shipped build.
- **Options considered:** keep 512 KiB and run the gate at a larger fraction, which weakens what the gate proves for an application built in debug; box the deepest futures so their frames move to the heap, which costs an allocation per maintenance step in the shipped build to help only the debug one.
- **Also learned:** the land gate on macOS does not see the Linux margin (a Linux thread loses more of its stack before the first frame), and merging on local gates let four pull requests land on a red main. The module doc says so; landing now checks the last CI run on main first.
- **Revisit if:** the gate trips again, a deployment with thousands of databases under strict overcommit asks for less, or an HTTPS store path is added to the suites.
