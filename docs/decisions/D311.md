## D311. A read limit paces the engine's whole-database reads, off by default (owner-approved)

Status: decided; measured · Decided by: the owner (2026-11-27: the setting, off by default, named `snapshot-read-limit`, in the `litestream-rs` section, a byte rate with the config's size suffixes), built by Claude (claude-sonnet-5-5) · Recorded by: Claude (claude-sonnet-5-5) · `crates/replica/src/pace.rs`, `crates/replica/src/config.rs`, `crates/config/src/build.rs`

Closes issue 315 (the page-cache advice it also asked for was measured and dropped; the memory bound is stated in its own place).

- **Question:** in-process there is no cgroup between the replicator and the application, so a full copy of a database larger than memory slows the application's reads and commits for its length.
- **What Go does:** no limit on any read of the database. As a separate process it can be put in a cgroup.
- **Choice:** `snapshot-read-limit` (bytes a second, absent means none, zero is refused) paces every read of a database file page: the boot copy, a level-9 snapshot, the scheduled verify's read. A `Paced` page source in lsr-replica keeps a byte budget on the runtime's clock and waits between pages. The limit is lifted while the replicator holds the application's writes (the boot's identity check), and under a limit an upload tick's bytes shrink to a tenth of a second of reading (at least 256 KiB, at most the usual 8 MiB), so a sliced snapshot waits about 100 ms at a stretch and the WAL step keeps its turns (D217, D255, D264). No change in lsr-core.
- **Measured (2026-11-27, g6-dedicated-4 with 4.3 GiB of tmpfs ballast, 4 vCPU, 8 GiB database, 512 MiB hot set, 4,000 reads and 10 commits a second, A/A gate passed at 19% half width, 10 interleaved rounds, medians in ms during the copy):**

| arm | read p99 | commit p99 | copy s | WAL growth MiB |
|---|---|---|---|---|
| A (no copy) | 0.34 | 0.31 | - | 4.0 |
| B (full rate) | 3.04 | 4.61 | 100 | 2.4 |
| 1/2 | 1.98 | 5.31 | 170 | 4.0 |
| 1/4 | 1.41 | 2.90 | 273 | 8.1 |
| 1/8 | 1.00 | 2.18 | 478 | 16.1 |
| 1/16 | 0.62 | 1.42 | 890 | 32.3 |

  Read p99 against B (paired, 95% interval): 1/2 inconclusive, 1/4 -60% [-82, -11], 1/8 -69% [-89, -14], 1/16 -86% [-93, -72]; p50 never moved. No arm met the bar set before the run (p99 within 2 times A's and copy within 4 times B's): 1/16 meets the latency (1.9 times) at 8.9 times the copy time. With a 2.25 GiB hot set (5 rounds, gate forced) B's p99 was 16 ms and 1/8's 7.6 ms: pacing helps only partly once the hot set nearly fills free memory, since it lowers the rate of eviction and not the volume read. Application major faults and system refaults were the same in every copying arm at 512 MiB: the harm there is CPU and disk contention. The bench application's threads busy-wait their last 300 microseconds (D310).
- **Cost accepted:** a copy lasts about 2 x database bytes over the limit and holds its read transaction that long, so no checkpoint runs and the WAL grows by the application's write rate over that time (0.036 MiB/s here); nothing newer than the copy's start reaches the replica until it ends. The wait sits inside a page read, on the engine's thread.
- **Not paced:** reads while the replicator holds the application's writes, WAL reads, and staged-file reads.
- **Tests:** `pace::tests` (rate over any run, no banked credit, slice bytes), `config::tests::a_read_limit_shrinks_the_bytes_of_an_upload_tick`, `snapshot_limit::a_read_limit_holds_the_boot_copy_to_its_rate`, `snapshot_read_limit_is_a_byte_size_off_by_default`. Plants: `snapshot-read-limit-ignored`, `snapshot-slice-ignores-the-read-limit`.
- **Revisit if:** a sliced snapshot's waits show in commit latency on a real disk, or an embedder wants a limit that changes at run time.
- **Links:** #315, D217, D255, D264, D310, `crates/compat/bench-patches/read-pace.patch`.
