## D218. The trial drill: a Python script with a ledger inside the database, kills at observed points, and one config for both binaries

Status: decided · Decided by: delegated, Claude (claude-sonnet-5-5), 2026-11-25, for the owner · Recorded by: Claude (claude-sonnet-5-5)

- **Question:** the Jepsen-style review (finding B2, section 5, F11) found nothing run with lsr as the writer past about 10 MB end to end, and the rollback to Go never rehearsed at size. The goal is a trial as a drop-in for the Go binary on a database of tens of GB replicated to a real provider. What is the one scripted drill that would have to pass first, how does it know the right answer at any size, and where does it kill?
- **Choice:** `scripts/trial_drill.py` (`just trial-drill <gib>`, `just trial-drill-provider <provider> <gib>`), seven named phases (docs/trial-drill.md). Truth is a ledger the application keeps: in each transaction it updates `drill_state(seq, ts_ms, xor)`, the XOR of a 64-bit BLAKE2 digest of every row, and appends "I seq ts xor" before COMMIT and "A seq ts" after to a file outside the database. A restored database is judged by recomputing the XOR (the pages are one committed state), by finding (seq, xor) in the ledger (that state existed), by the instant's bound, and at the newest state by equality with the live pages (a checkpointed copy up to `--live-copy-max-gib`). The two binaries' restores are compared byte for byte, never as LTX bytes. Kill points are observed, not timed: a multipart upload in flight (read from the real listing on a provider, from a loopback proxy in front of MinIO, which lists none), a GET burst for a compaction (lsr reads its inputs only to compact), a staged snapshot or a snapshot upload in flight. The kill is SIGKILL of the whole process group, so the application dies with lsr, as a crashed container would. One config file serves both binaries: `litestream-rs: {app-readers: none}` is what lsr needs to accept `truncate-page-n`, and Go reads it as an unrecognized key and warns. Budgets are flags with defaults: lag 60 s once caught up, 900 s to catch up, 120 s without an upload, writer stalls 25 s, memory 256 MiB plus 32 bytes a page, WAL 1 GiB.
- **Calls:**
  1. Python, not a Rust binary in lsr-compat: the provider path is `scripts/provider.sh` wrapping a command (credentials, the run prefix, the cleanup assertion), the fault rig and the LazyFS rig are Python, and the drill is orchestration of processes. Page equality (about ten lines) and `integrity_check` are written again here instead of calling `hash_pages` and `integrity_check` in lsr-compat; the canary (`just trial-drill-canary`) checks them. Cost if wrong: two definitions of page equality that can drift.
  2. The budget defaults are placeholders chosen without a measurement at size. Cost if wrong: a false failure or a false pass until the first full run sets them.
  3. A restore of the small database while lsr runs (after each kill) is judged by the ledger only; two restores of the newest state taken a moment apart differ under load, so comparing the binaries there was a drill defect, not a finding.
  4. `integrity_check` runs on lsr's restore always and on Go's only when the pages differ (equal pages have equal answers).
- **Consequences accepted:**
  1. The scheduled snapshot is a kill point, so a run at the default 24 h interval waits a day for it; `--snapshot-interval` shortens it.
  2. The config defaults are Litestream's own (read from the pinned upstream source); keys with no default (`part-size`, `concurrency`, `busy-timeout`, `truncate-page-n`) are unset. A shape under test goes in through `--config-overlay` at run time, never into the repository. The script gains one dependency, PyYAML (MIT licence), to read the overlay.
  3. This MinIO lists no multipart uploads, so a MinIO run cannot assert that none are left; a provider run does, through the real listing.
  4. A restore of an instant inside a compacted file, which lsr refuses, is counted; Go's answer to the same instant is judged against the ledger and the instant.
  5. The ledger check covers the data table, not SQLite-level objects the writer never touches.
- **Cost if wrong:** the drill passes a defect that the writer's one table does not expose, or fails a healthy run on a budget set too tight.
