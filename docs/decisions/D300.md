## D300. A restore keeps the files it applied when a later planned file is gone (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5) · Amends: the retry rule in `crates/core/src/restore.rs`

- **Question:** a latest restore of a database of tens of GB with steady writes read its level-9 snapshot for most of an hour, then found level-0 to level-3 files of its plan gone (the writer's compaction and retention ran meanwhile), emptied its output and started over from the snapshot, three times, then failed with `Unstable`: hours of reading and three times the snapshot's bytes, billed. How should a restore follow a replica that changes under it?
- **What Go does (pinned 3e0fdc0):** `restorePlan` opens every plan file, up to 32 at once (`openRestoreFiles`), then streams them through the compactor, which reads every input in page order. An open GET body outlives a delete, so a file deleted after its open does not hurt. But a small file's stream idles while the snapshot streams, providers close idle connections (the `ResumableReader` comment says so), and the reopen of a deleted file returns `os.ErrNotExist`; `restore` then truncates the output and starts over from a fresh plan, up to three times, logging only at debug level. So Go can fail the same way, through idle closes.
- **Decision:** option (a). A file gone before any of its bytes were read, after the files before it were applied, keeps those files: the sink holds exactly their verified database. The restore lists again, extends the kept chain over the fresh listing (`plan_after`) toward the first plan's target (an `-timestamp` target fixed to the transaction its plan reached, so the answer does not move), and applies the rest linked to the last kept file as any next file is. At most 8 such re-plans (`MAX_TAIL_PLANS`). A file gone part-way starts over (its written pages are vouched for by no verified file), as does a rest that no longer reaches the target (retention removed it under a newer snapshot); that start over plans on the listing that showed it, so it makes no listing Go would not. `-txid` and `-timestamp` restores had the same failure and take the same path.
- **Rejected:** (b) fetching the small files first into local space, then the snapshot: a new on-disk spool Go lacks, and the files are still chosen by one plan made before any download, so compaction between the plan and the reads still removes some of them. (c) opening every body first as Go does: holds one connection per plan file for the whole snapshot (hundreds on a long chain), and idle closes bring back the same failure through the reopen; the bound on held streams would also break "memory per file is one chunk".
- **Requests:** fewer than Go in the same scenario: one listing and the files after the kept part, against Go's listing and every file again, the snapshot included.
- **Reporting:** `restore_noting` hands each re-plan (`Replan::Tail`, `Restart`, `NoTail`) to the caller as it happens; `lsr restore` prints one `restore: ...` line on stderr per re-plan, naming the file that was gone. Go logs this only at debug level.
- **Cost accepted:** a restore whose small files keep vanishing makes up to 8 more listings before `Unstable`; a part-way vanish still costs a whole start over (rare: a file's reads span only seconds, and an S3 read is one held stream).
- **Revisit if:** a store's reads of one file stop being one stream (a part-way vanish would then be common), or restores report `Unstable` after 8 re-plans.
- **Links:** `crates/core/src/restore.rs`, `crates/core/src/plan.rs` (`plan_after`), docs/differences-from-go.md.
