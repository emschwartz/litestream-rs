## D271. The simulator pins Go's request count for a steady sync (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5) · test code only (`crates/sim`)

- **Question:** D241 says lsr makes no more store requests than Go in the same scenario. The simulator's run budgets are upper bounds (`crates/sim/src/budget.rs`), loose enough that one extra request per sync passes them. Which scenarios get an exact budget taken from Go's code?
- **What Go does, and why:** once its position is known, `Replica.syncOnce` uploads each new level-0 file with one `WriteLTXFile` and makes no other call (`replica.go`). `calcPos` lists level 0 only while the position is unknown.
- **Choice:** with `Opts::record`, a run now keeps the replica's counts after each operation (`RunReport::remote_counts`). `requests::a_steady_sync_puts_each_level_zero_file_once_and_asks_nothing_else` takes a window after the boot and before the first maintenance pass. In it, lsr must make no listing, no read and no delete, and must put each level-0 file once, as Go does.
- **Cost accepted:** only the steady sync is pinned. A boot, a maintenance pass and a compaction are not yet, because lsr's counts there differ from Go's by design (the boot lists all ten levels, where Go lists level 0), and whether each difference is a guard against a Go defect is a ruling for the owner.
- **Links:** D241; plant `sync-lists-the-replica-each-time`.
