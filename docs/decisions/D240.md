## D240. A level this engine compacted waits for its next window (delegated)

Status: decided · Decided by: Claude (claude-fable-5-2), **delegated**; the owner can overturn it · Recorded by: Claude (claude-fable-5-2)

Found by counting requests in lsr-core: a steady writer got two level-1 files in every 30 second window, 8 PUTs in two minutes where the schedule says 4.

- **Question:** a level compacts when its newest file was not created inside the current window. A compaction's output carries its last input's time (so an output never looks older than its inputs, and Go reads it the same way). The compaction at the start of a window takes files committed in the window before, so its output's time is before the window too: the window stays open, and the first file uploaded after it is compacted again, alone or with the next few. What closes the window?
- **What Go does.** One compaction per level per window: the level monitor's timer fires at each window's start and at the process's start, and each firing compacts once, everything the level below holds above the destination (`store.go`, `monitorCompactionLevel` and `CompactDB`). Go's own "too early" test reads the destination's time as this engine did, and would also pass again inside the window; nothing asks it to. That is 2 level-1 PUTs a minute at the default 30 seconds. The head-to-head counted 2.7 for Go, which the code does not explain: a count over a span that is not a whole number of windows, or one that includes the start (the timer fires at once, and again every second while the database is not ready), gives such a number. It should be measured again over whole windows.
- **Choice.** The engine remembers, in memory only, when its last compaction into each level took every source file the level had (a job of fewer than the 32 inputs one compaction may take). While that instant is inside the level's current window the level waits for the next window, whatever time the output carries. The rule on the destination's time stays, for files this process did not write.
- **A backlog still drains.** A job of 32 inputs may have left more, so it closes nothing: the jobs follow one another inside the window, and the one that ends the backlog closes it.
- **Cost accepted.** A file uploaded just after a window's compaction waits for the next window to reach level 1, as in Go, where before it got there within seconds. Level-0 retention deletes nothing a level above does not cover, so nothing is lost by the wait. A compaction that closes a hole from a lower level also closes the window of the level it writes, so that level's next ordinary compaction waits one window. A new process remembers nothing and may compact once more in the window it starts in, as Go does at its start.
- **Counted.** `actor::tests::steady::a_level_is_compacted_once_in_each_window`: two minutes of a steady writer: 8 level-1 PUTs before, 4 after.
