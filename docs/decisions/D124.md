## D124. The simulator's replica can be the real S3 store, judged through the bucket (delegated)

Status: open to owner review · Decided by: Claude (sim-s3), **delegated**

- **Options:** keep `MemStore` as the replica's only double; put the replica on `lsr-store-s3`'s `S3Store` over its in-memory bucket (`FakeS3`) behind its recorded-fault layer (`FaultTransport`), read by the judges through the same store; the same, with the judges reading the bucket's stored objects directly.
- **Choice:** the last. `Weights::remote_s3` (a coin, drawn last in the swarm mix; off in the default mix) puts the replica on `S3Store<FaultTransport<FakeS3>>` under the world's own wrappers, so the object-level faults, the corrupting publish and the put log work on either backend. `Op::HttpFault` (drawn last; skipped on `MemStore`) pushes a provider fault onto the transport: a throttle (503, 429 with `Retry-After`), a 500, a 408, a lost acknowledgement, a truncated body, a wrong ETag, a reset connection. The judges read and edit the replica through `crate::remote::Bucket`, which answers from the bucket's keys, bodies, metadata and last-modified times as `MemStore` would, never through the S3 client's request, listing or classification code.
- **Why:** with the judges on the store under test, a client that misread the bucket would be agreed with. A store can also fail after the bucket took a request, which `MemStore` never does below the recorder: the recorder now asks the bucket whether a failed commit or delete landed, and lists every key whose commit failed as one the engine may distrust and delete (the S3 store removes an object whose ETag came back wrong before it reports the error). Provider faults on listings, HEADs and GETs count as reads cut short, as object-level read faults do.
- **Measured:** `MemStore` runs are unchanged (reports for swarm seeds 1 to 300 hash the same with the two draws off). On swarm seeds 1 to 100 with provider faults drawn, the same histories fail the same seeds on both backends but one, a read-call bound `MemStore` exceeds and the S3 store's batching does not. S3 runs take about 1.7 times as long. Unaided recall on the ledger's seven store-s3 plants, over 200 mixed seeds each (1000001 on) with the replica on S3 and provider faults at weight 40: none found beyond the clean tree. `spent-multipart-upload`, `completed-etag-form` and `s3-boot-forgets-killed-uploads` sit in the multipart path, which the simulator's files (far under the 5 MiB part) never take; `denial-classes` and `kms-codes-by-status` change which denial is reported, which no judge distinguishes; `delete-denial-transient` needs a per-key delete denial, which no draw makes; `drop-if-none-match` needs a write onto a taken key, which the 200 seeds did not reach. Each stays caught by store-s3's own tests.
- **Cost accepted:** multipart shapes and the two faults only a CompleteMultipartUpload meets are not drawn. Scenarios and the per-push fixed seeds keep `MemStore` (the fixed seeds pin both draws off, so their histories are main's); `sim` test `remote_s3` runs swarm seeds on S3 instead. Mixed seed 5 on S3 trips fail-stop where the judge sees every commit replicated (provider faults delay the first upload past a clock jump, then a lying-reads hold); it passes on `MemStore` and is reported for a ruling, not excused here. A 501 answer to `If-None-Match` (a provider without conditional writes) is not drawn yet: it waits for D79, which makes that refusal the loud `ConditionalWritesUnsupported` the draw would then expect.
- **Revisit if:** D79 lands (add the 501 fault); a judge is added that tells denial kinds apart, or a draw denies one key's delete (the two plants above become reachable); the simulator writes files large enough for multipart.
