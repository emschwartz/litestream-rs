## D150. How a broken read lock reaches the operator (delegated)

- **Options:** a new `Event` variant for the tick that finds it; a new snapshot cause in place of `GenerationChanged`; a count in the health handle, beside the snapshot counts.
- **Choice:** a count. The actor counts each recovery verdict that names `RecoverEvent::ReadLockViolated` (`Actor::read_lock_violations`, kept across engine rebuilds), the health handle reports it in `Counters::read_lock_violations`, and the sidecar exports `lsr_read_lock_violations_total{db}`. `recover()`, which returned the decision without the event, is gone: every caller now takes `recover_traced` and says what it does with the event.
- **Why:** the event never left `recover()` (outside review, issue #197, A1), so a broken lock or a bug in the continuity proof was visible only as one more `generation_changed` snapshot. A tick reports one event, and the violation's tick already reports the snapshot that answers it; a new snapshot cause would change a closed enum that the journal, the simulator and the behaviour table key on. A count needs no new path and survives the rebuild that a bug fault triggers.
- **Cost accepted:** no log line names the offset at the time. The count says it happened and how often; the position it happened at is not kept.
- **Revisit if:** an operator needs the offset to diagnose a violation, or the count is ever seen above zero outside a test.
- **Links:** #197, `docs/behavior.toml` RUN-8.
