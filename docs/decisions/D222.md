## D222. The S3 upload of a staged file reads each part twice and holds none of it (delegated)

Status: decided · Decided by: Claude (claude-fable-5-2), **delegated**; the owner can overturn it · Recorded by: Claude (claude-fable-5-2) · It changes the public `Upload` and `Transport` traits, so it carries both outside reviews · Does what D226 left undone ("streaming parts from the staged file is not done")

- **Question:** an S3 upload buffered every part and sent `concurrency` of them at once, so it held `concurrency x part size` for as long as it ran, whatever the object's size: about a gigabyte at a large part size with ten parts at once (D226). Go holds almost none of that for a staged file. Can the upload of a staged file hold no part, without ever sending a byte that was not verified on the read that produced it?
- **What Go does, and why:** for a staged level-0 file (`s3/replica_client.go`, `uploadSizedLTX`) Go hands the SDK the open file. The SDK cuts it into section readers, one per part, with no part buffers, and each part is read from the file when it is sent (where the SDK hashes a part first, it reads it, seeks back and reads it again). Go never compares what it sends with the staged file it verified. For a streamed output with no file (`uploadStreamedLTX`, a compaction) the SDK fills pooled part buffers. Go's way for the staged file is the one taken here, with the check Go lacks: the second read is compared with the first, which the engine decoded and verified.
- **Choice, in five lines:**
  1. `lsr_core::Reread` is the object being written, read again: `read(offset, was: &ByteTally)` answers with the bytes only when they tally as they did when first handed over. `Upload` gains `write_from(chunk, again)` and `commit_from(again)`, both defaulting to `write` and `commit`, so a store without parts (the file store, `MemStore`) is unchanged.
  2. The engine hands the replica each verified chunk of a staged file with a source that is the staging directory's own read of the same file (`upload::Staged`): one bounded read per call, built on the stack each step, nothing held between ticks.
  3. The S3 store, when an upload's first write comes with a source, keeps for each part its MD5 and one 72-byte tally for every 256 KiB in place of the bytes (`again.rs`). A batch of `concurrency` parts goes out as before, each body read back through the source 256 KiB at a time while it is sent, each request carrying `Content-Length` and `Content-MD5` of the first read.
  4. A second read that differs or fails ends the body short of its declared length, the upload is aborted before anything is published, and the engine reports it as the staged file's (`StagedLost`) or the staging directory's fault, never the replica's, with no listing and no delete owed. The retry starts at the file's first byte, as any failed send does (D217).
  5. Outputs with no file behind them (every compaction, a level-9 snapshot) still call `write` and still hold their parts.
- **The five questions the design had to answer:**
  1. *Is the verified-bytes rule kept?* Two checks stand between a wrong second read and the replica. The source's tally comparison runs before a byte of the read is released, on every provider and transport. `Content-MD5`, taken over the first read, is on every part and every single PUT (`request.rs` cannot build a write without it), and the store checks what it received against it; the returned ETag is compared with the same MD5 where it is one. The tally is not cryptographic: it guards against a file that changed or a read that went wrong, as the engine's first read does, and the MD5 the store checks is the strong one.
  2. *The trait shape.* Two defaulted methods and one small trait. Two, not one, because a file below one part is sent only at the commit. The source is borrowed per call, never owned by the upload, so no descriptor or handle on staging lives between ticks and the simulator's staging faults reach the second read with no new seam. An implementer breaks only by forwarding one method and not the other through a wrapper: an S3 upload written from a source refuses a plain `write` or `commit`, loudly, since it no longer holds what it would send. `Transport` gains one defaulted method, `send_streamed`, that buffers each body and calls `send_many`.
  3. *What a tick does.* A slice is 8 MiB, so a part's first read spans ticks: each slice feeds the part's MD5 and tallies and is dropped. The call that hands over the last byte of the batch's last part sends the batch inside that call, on `concurrency` threads, all joined before it returns. Between ticks: no thread, no descriptor, no request, and at most `concurrency` part records. During a batch: `concurrency` threads, sockets and staging reads, each holding one 256 KiB read and the HTTP client's buffers.
  4. *What the second read costs.* Every byte of a staged upload is read and tallied twice. Measured below with the file in the page cache; not measured cold (see Measured).
  5. *Which outputs have no file.* Every level-0 file is staged, the first sync of a whole database included. Every compaction and every snapshot read from the database stream straight to the store and keep `concurrency` buffers. Sending them through this path would need a local spool file per output, which Go does not write; not built.
- **The two reviews** (on the design document, before any code; both said to build, with changes):
  - Codex (through the codex-rescue agent): "Verdict: build with these changes." Its strongest reason: "withholding the last buffer prevents a complete request ... but earlier buffers have already left before their reread is verified. Verify each bounded range against a strong digest recorded on the first pass before releasing it." Built as a tally per 256 KiB read, checked before the read is released, with the MD5 as the strong digest the store checks. It also reported that "A final UploadPart checksum failure currently reaches commit handling, which can mint a deletion token even though Complete never ran": true on main, fixed first on this branch with its own tests and planted bug (`part-mismatch-deletes-the-key`).
  - Gemini (gemini-4-argon, through pi): "Verdict: **Build with these changes**". Its changes, all made: a second read that fails inside a commit "published nothing and must return `PutError::Before(fault)`"; the ureq client must keep `content-length` on a streamed body and the body must never end cleanly while bytes remain; failures are judged per part in part order, not from one remembered error; every wrapper and the real-server test transport forward the new methods. What would change its mind: "Move to **do not build** if the cold-cache benchmark on a 4 GiB initial sync shows the second disk read regresses end-to-end upload time by more than 25%". That benchmark could not be run (below), so the condition stands open.
- **Cost accepted:**
  - A staged upload reads its file twice: under 1% of a loopback upload at the default part size and up to about 6% at a large one (below). On a machine whose page cache has dropped the staged file, that is a second disk read of it.
  - Only the ureq client streams. The reqwest client takes the default and still holds each part while it sends it.
  - Compactions and level-9 snapshots still hold `concurrency x part size`, so the whole first start of a large database peaks where it did (below): the staged file's upload was one of several users of that memory, and this removes only that one.
  - A request in flight holds 768 KiB by the gate, where the design said 256 KiB: the HTTP client's own buffers.
  - A wrapper around an upload must forward both new methods or every staged upload through it fails, typed, at its first plain call.
  - Two more public methods on `Upload`, one on `Transport`, and the public `Reread`, `ByteTally` and `StreamedRequest`.
- **Measured** (studio, macOS arm64, 10 cores, 32 GB, native MinIO on loopback; release builds made there, main at efc92fe3f against this branch with that main merged in, cd8cac9f1; a first start of `lsr replicate` on a 4 GiB database, half of each row incompressible, whose staged level-0 file is 2,040 MiB; wall is process start to the first object on the replica, memory is the peak physical footprint to that moment, and the process is killed there; 10 A/A pairs, then 20 A/B pairs, interleaved in alternating order, for each configuration; smallest effect of interest 5% of wall, fixed before the runs; the staged file was in the page cache for both reads):
  - A large part size, ten parts at once. Peak footprint 979 MiB before, 32 MiB after (medians): -96.74% [-96.77, -96.71], n = 20 pairs (A/A +0.01% [-0.02, +0.03]). Wall, two runs of 20 pairs. The first, 9.7 s before and after: -0.08% [-14.50, +16.78], with five pairs under another session's load (walls of 14 to 45 s) and a median pair of +1.14%. The second and last, registered as such, on a machine busier still (load average 3 to 11): 10.8 s before, 11.1 s after, +3.53% [+0.97, +6.15] (A/A -2.28% [-6.69, +2.33]; its memory figure the same, -96.75% [-96.78, -96.71]). **Not shown equivalent within 5%**: the second read costs this loopback upload between nothing and about 6% at this size, and the machine was never quiet enough to say more.
  - The default part size (5 MiB, five at once). Peak footprint 49.3 MiB before, 28.2 MiB after: -42.69% [-42.91, -42.47], n = 20 pairs (A/A -0.00% [-0.10, +0.10]). Wall 10.09 s before, 10.17 s after: +0.82% [+0.55, +1.10], equivalent within 5% (A/A +0.05% [-0.36, +0.46]). The second read costs about 0.08 s of this upload, and it reads the same bytes whatever the part size.
  - The whole first start, to the first level-9 snapshot (two runs an arm, no interval claimed): the peak does not move, because the compactions and the snapshot that follow the first file hold their parts. At a large part size 983 and 982 MiB before, 986 and 987 MiB after, in 61 and 55 s before, 61 and 59 s after. At the default 49 and 52 MiB before, 47 and 54 MiB after, in 64 and 61 s before, 61 and 59 s after.
  - An earlier run of the same design, on the builds before main moved three times (dcbd5ca5a against 484db1c17), agrees: 1,050 to 100 MiB at a large part size (-90.49% [-90.54, -90.45]), 120 to 98 MiB at the default (-18.27% [-18.57, -17.97]), wall at the default -0.15% [-0.53, +0.23]. Its wall at a large part size failed its A/A gate under other sessions' load and is not a result.
  - Not measured: a cold page cache (the machine gives no way to drop it without root). The engine writes and first reads the staged file moments before it sends it, so the second read is of cached pages unless memory is short. Where it is not, the cost is one more sequential read of the file from the staging disk; that is an estimate, not a measurement.
- **Checked by:** the memory gate (`crates/store-s3/tests/store-s3/memory.rs`): an upload from a file at 16 MiB parts, three at once, peaks at 2,304 KiB where buffering peaks at 49,647 KiB, and at 5 MiB parts, five at once, 3,649 KiB against 26,426 KiB. Four planted bugs, each killed by its named tests: a part sent without its digest, a second read trusted when it no longer tallies (against the core tests and against the simulator), a part read back from the wrong offset, a rejected part deleting its key. The simulator's recorder keeps the first read and judges every second read (`crates/sim/src/oracle/reread.rs`); a short scenario changes the staged file between its two reads and the run sees the refusal. Unaided recall of the second plant is zero in two registrations of 300 swarm seeds each, 1,000,001 to 1,000,300 (the default mix, then the same with the replica on the S3 store): the swarm sends a file whole in one tick and no draw lands damage between its two reads, a listed generator gap. Cargo-mutants over the changed lines of `lsr-core` and `lsr-ltx`: 58 mutants, 26 caught, 32 that do not build, none missed. The sidecar's meters sit between the engine and the store, and a test fails if they hand a write on without its source (`crates/replica/src/store.rs`).
- **Found and left for a decision:** a `400 BadDigest` on a single PUT is classified as a checksum mismatch of the whole object, so the engine asks for a delete of a key the store refused to write (a needless request for a new key; under `WriteMode::Replace` it would remove the older object the retry then writes again, which no test here shows). `leaves_bad_output` (`crates/core/src/maintain.rs`) and `Fault::leaves_bad_snapshot` read a rejected part the same way. The simulator's S3 double does not check `Content-MD5` against the body, so the store's half of the check is shown only against a real server (`minio::wrong_content_md5_is_refused_by_minio`, `minio::shared_cases::an_upload_from_a_source_round_trips`).
- **Options considered:** streaming a part while the engine first reads it (the digest must go before the body, or in trailers that S3-compatible providers do not all take, and a request would be in flight across ticks); a source owned by the upload (a handle and a descriptor alive between ticks, and the simulator's staging faults would not reach the second read); trusting `Content-MD5` alone (a provider that ignores it and returns an ETag that is no MD5 would store an unverified second read); a whole-part MD5 compared when the part's last buffer is about to leave (the earlier buffers have left by then, the first reviewer's point); a new `StoreError` variant for a source that changed (the engine's source remembers what it refused instead, so no store learns a new error); a spool file for streamed outputs (a file Go does not write).
- **Revisit if:** a cold-cache measurement shows the second read costs more than a quarter of the upload's time; the reqwest client is to hold no part (it needs a streamed body of its own); the owner wants compactions and snapshots to hold less than their parts, which needs a file behind them; a provider is found that ignores `Content-MD5`.

A part's MD5 is now taken on the thread that sends it, over a second read checked cell by cell against the first read's length and CRC-64, and the part is read a third time as it is sent; each part has a reader of its own, so a descriptor on the staged file lives between ticks; `commit_from` is gone.

2026-11-25: amended by D250. A part's MD5 is no longer taken or sent: the hash pass takes its SHA-256, which the request is signed with, and the ETag that comes back is not compared with anything.
