## D173. v1's fault model: what the engine handles, what stops it, and what it leaves out

Status: decided · Decided by: owner, 2026-11-23 · Recorded by: Claude (claude-fable-5-2)

- **Question:** D131 put every accident in scope: a lagging listing, a bucket rolled back, a volume or meta directory put back from an older copy, a failed sync of the WAL. Each got a defence that detects it and then recovers without an operator. The recoveries need remembered state (the engine journal, the confirmed floor, witness tokens, the regression watch), they contradict each other (PR 259 against the listing check of #203), and about a third of the engine's fix commits (33 of 92, sorted by subject) repaired them. Go Litestream handles none of them. Which accidents does v1 answer, and how far?
- **Choice (owner):** v1 handles what a correctly configured deployment meets in ordinary operation. It stops only where D7 already stops: another writer, or a database that did not write this replica, which takes a mistake to reach and where continuing damages the backup. Where a correctly configured deployment can reach a circumstance and Go continues, v1 continues too, degraded and loud, and never stops. It leaves the rest as documented limits, and it does not repair by itself what broken storage or an operator's act caused. The four tables below are the whole list; `docs/behavior.toml` stays the row-by-row account.

### Handled: replication continues, and every restore is a state the application committed

| Failure | What v1 does |
|---|---|
| A crash or a kill at any point (every deploy is one) | Resumes from the staging directory and the WAL, with no snapshot when the WAL is intact |
| Power loss on a disk that keeps what it synced | As a crash: the WAL is synced before any frame read from it is staged |
| Power loss on a disk that loses writes it acknowledged | The boot finds the database behind what was staged and takes a snapshot (`LocalRewound`) |
| Store errors, throttling, timeouts, an outage of any length, revoked credentials | Retries with a capped wait, and reports a typed degraded state |
| An upload whose answer was lost | A listing settles it, and a create-only write refuses a duplicate |
| A torn or corrupt staged file or replica object | Every file is verified on the read that uses it. A restore that meets a bad object fails with a typed error, never with wrong pages |
| What SQLite and the application do: a checkpoint from outside, a WAL restart, `VACUUM`, a page-size change, a deleted WAL | Continues, or takes a snapshot with a named cause |
| A full local disk | Degraded, and retried |
| A clock that steps backwards | Clamped and reported |
| Go and Rust taking turns on one prefix | A plain restart, with no snapshot when the WAL is intact |

### Continues, degraded and loud: Go continues here, so v1 does

| Failure | What v1 does | Why no stop |
|---|---|---|
| A failed sync of the WAL (a dying disk, a full thin volume, a network volume that dropped out) | Reports `wal_sync_failed` and retries, as today's default does. No repair, and nothing remembered across a restart | Nobody erred, and it can be transient. Go never syncs the WAL at all, so going on after a failed sync is Go's everyday exposure. If power is then lost, the boot finds the database behind what was staged and takes a snapshot |
| The replica's newest file is gone (a bucket rolled back, files deleted by hand) | The next listing that shows it reports `remote_regressed`, and replication goes on, as today's default does | The next snapshot makes the replica whole; a stop would prevent it |
| A database whose meta directory is on ephemeral storage, restarted after its WAL was checkpointed away | The identity check (D170) compares the local database with the replica and goes on when they are equal | An ordinary deployment shape, and Go continues. Without the check every such redeploy would stop |
| A store without conditional writes | Runs as Go does and says so (D79) | Unchanged |

### Stopped on: the engine stops with a typed cause, and an operator acts

| Failure | What v1 does | Why a stop |
|---|---|---|
| Two engines on one meta directory (an overlapping deploy on one volume) | The second start waits for the first to exit, then starts (`lsr-lock`; D178) | Both would stage the same transactions, so one engine at a time. Waiting is D178's, not a stop |
| Another writer on the prefix, or a database that did not write this replica (an empty volume, a wrong prefix) | A create-only upload is refused; a boot that finds replica files the WAL cannot vouch for stops (D12); a listing that shows a foreign file past the engine's position stops. `lsr take-over` clears it | Continuing makes a foreign or empty database the newest state, and retention then removes the real one |
| A volume, a VM, the meta directory or the staging directory put back from an older copy | The same boot stop. The operator runs `lsr take-over`, or restores from the replica | A deliberate act with a person present |

### Left out: v1 neither detects nor repairs these

| Failure | What happens | Why it is out |
|---|---|---|
| A store whose listings lag its writes | Unsupported. A restore inside the lag can succeed with an earlier committed state | AWS S3, Cloudflare R2, same-region Tigris and MinIO document consistent listings. A Tigris global or dual-region bucket read from another region does not qualify. The release bar's consistency probe (R9) is the gate for a store |
| A hole below the replica's newest file (files deleted mid-history, an expiry rule shorter than the snapshot interval) | The engine does not watch for it. A restore fails with `Gap`, the scheduled verify reports it, and the next snapshot makes the replica whole | Loud at restore, and it heals by itself |
| Repair after a failed WAL sync | None: no debt carried across a restart, no verified checkpoint, no check of the database against the replica | A dying disk is not replicated around, and Go does none of it |
| Remembering across a restart which replica files this engine wrote | None. A boot asks the WAL, then the identity check, then stops for an operator | The witness pass and the spent and re-asserted takeover records existed to spare a stop after a volume was put back, which is a deliberate act |
| A degraded state or a retry count across a restart | Each run counts from zero. A replicator that restarts before a fault has failed eight times in a row can halt replication while health reports nothing. The age of a staged commit that was never uploaded does carry over | Go forgets them too, and remembering needs saved state that change 4 removes. Decided afterwards, in D174 |
| Files forged to pass the engine's checks | As D131 | Unchanged |

- **What goes, each in its own change, in this order:**
  1. The reads past a listing (`crates/core/src/probe.rs`) and the simulator's lagging-listing law. Supersedes D60, D61 (issue #169 is declined), D63, D171.
  2. The regression watch, the journalled confirmed floor and the acknowledged mark. Supersedes D51 and D107. PR 259 closes unmerged.
  3. The spending and re-asserting of a takeover record, and the witness pass at boot (D175 names what replaces it: a boot checks the staged files it finds and uploads them, as Go does). The identity check stays. Supersedes D172. First, in its own commit: `lsr restore` writes the takeover record to the configured meta directory, which the identity check hides today.
  4. The unproven-WAL debt, the verified cure and the ahead-of-WAL check; a failed WAL sync keeps today's default response. With the floor gone the engine journal holds nothing: the `lsr-journal` crate, its model in `lsr-spec` and the obligation ledger go. Supersedes D8, D9 and D100 to D108.

  The simulator operations, laws, planted bugs and behaviour rows that exist only for these go with them.
- **Rule for new work (amends D131's):** a circumstance found outside these tables is not a defect. Its default answer is what Go does, said loudly: a degraded state when a check with no remembered state can see it, and otherwise a row under "left out". A stop needs both a mistake to reach it and damage to the backup from going on. A new defence, a new simulator fault law or new remembered state is a change of scope that the owner decides, never a delegated decision.
- **Cost accepted:** after a volume or a staging directory is put back from an older copy, the engine stops where it used to work out an answer. Two narrow silent cases reopen: the lagging-store restore above; and a bucket rolled back while the engine is down, with a new WAL generation and a stale takeover record, where the boot snapshots at the rolled-back end (closed in change 2 by removing a record once the snapshot above it is confirmed). After a failed WAL sync the replica can hold commits that a later power loss takes from the database, as it can with Go on any day; the boot's rewind check answers it with a snapshot.
- **Not decided here:** the meta-directory lock, decided in D178: the sidecar waits for it. Fail-stop (D14 to D22, D80 to D86) was open here and is decided in D177: it stays. Whether degraded states and retry counts must survive a restart was open here and is decided in D174: they do not.
- **Why:** the likely accidents (overlapping deploys, a fresh or wrong database on a live prefix) are caught by checks that remember nothing. The machinery removed serves the rare ones, and is about 5,000 of 37,000 production lines by four read-only audits on 2026-11-23, with some double counting between changes 1 and 2.
- **Revisit if:** a supported store is measured listing behind its writes; an accident under "left out" is reported from a real deployment; or Go wires its `lock.json` lease into `replicate`, in which case v1 speaks that lease and grows no mechanism of its own.
- **Links:** D6, D7, D12, D79, D131; issues #171, #197, #283.
- **Note (2026-11-24, Claude (claude-opus-5-5)):** the "Handled" row for a disk that loses writes it acknowledged claims more than the engine does (issue #12). Caught, with a `LocalRewound` snapshot: a database whose committed WAL ends before the staged end, or whose WAL holds other pages or another commit size in a staged file's range, while staged copies of the rewound range exist. Not caught, as under Go: a rewind whose regrown last transaction is byte-identical at the same WAL offset over an earlier transaction that differs, once the staged copies of that earlier range are pruned (about 30 s after upload), or with a brand-new meta directory, where the boot compares only the replica's newest file. A brand-new meta directory over a rewound database is a stop or, since D194, an `ahead_of_replica` snapshot when the database was written after the replica's newest file. The choice above is unchanged. Also not caught at boot (found by the simulator on 2026-11-24, reduction on issue #12): a staged snapshot that took a page from a WAL frame the loss dropped, when the regrown WAL agrees with the snapshot on every page it holds and on the commit size. The boot compares only the pages the WAL range holds, so it carries on and uploads the next file over a mixed state; the page checksum table then reports `DatabasePageMismatch` at the next read of that page. The loss is detected late, after the mixed state is on the replica, and not prevented.
