## D204. A listing page may come in any order; strays are counted where the provider listed them (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5)

Issue #342: the provider checks found Cloudflare R2 failing one case of 51. R2 lists a name after the longer names that extend it (`X.ltx.tmp`, `X.ltx`, `X`; `000`, `00`, `0`), and the S3 store refused any page whose keys were not in bytewise order, so a stray name in a level folder stopped every listing of it on R2. Go does not look at order.

- **Question:** what did the order check protect, and what does the store keep of it?
- **What it protected:** the check was the only guard against a listing that goes back, repeats or skips (a cursor or continuation token that does not advance), because the store trusts a page as a run of files from the cursor on. Nothing else relied on a page being sorted: `build_listing` sorts the files itself, the engine's callers read the sorted result, and a name that is not an LTX key is only counted.
- **Choice:** the store accepts any order inside a page. It sorts a page's files (they have a fixed width, so they list ascending on every provider, R2 included) and requires each page's files to lie above every file of the pages before it, which keeps a cursor that went back from hiding a file. Still refused, as a retryable `InvalidData` and never as a shorter listing: a key outside the level's prefix, a key listed twice (in one page or across pages), a page whose files are at or before one already passed, a continuation token sent back, a page that does not parse, an entry with no readable `LastModified`.
- **Counting strays:** a name that is not an LTX key is counted on the listing whose last file the provider listed it before, by where it was listed, not by comparing bytes. The next listing starts after that file, in the provider's own order, and finds the strays left, so each counts once whichever order the provider uses. Counting by bytes, as before, loses or doubles a stray that R2 lists after the files it is a prefix of (the conformance case plants `0`).
- **Cost accepted:** the count of unrecognized names at a page cut follows the order the provider listed, so a page that a provider lists in two different orders can count a stray on a different page; the total over a whole paging does not change. Memory is as before (a stray is held once, in a map instead of a list). The count feeds the operator's report (`unrecognized names skipped`) and the retention hold on unparsable names; both read the total over a whole paging, which does not change.
- **Revisit if:** a provider lists LTX file names themselves out of order across pages (it would be refused on every listing), or a decision starts to turn on the count of strays.
