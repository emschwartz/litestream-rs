## D265. A staged upload is hashed on its first read, and a part of one cell keeps its bytes (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5) · Amends D222 and D233; fixes #478

- **Question:** an upload written from a staged file read every byte of it three times: the engine's own read, a hash pass for the SHA-256 the request is signed with, and a send pass for the body. In the simulator one tick of 56 small whole puts made 168 staging reads. Go reads each file once. Can the store read less without buffering parts (D222, D233) or sending a byte that was not verified on the read that produced it?
- **What Go does:** the uploader buffers a part and hashes the buffer, so a staged file is read once.
- **Choice:**
  1. The SHA-256 is taken in `Run::add` over the bytes as first handed over, the same bytes the per-cell tallies are taken of, and carried into the sealed part. The hash pass is deleted. The body is still checked cell by cell against the first read, and the store checks the body against the signed hash, so the bytes sent equal the first read.
  2. A part of at most one cell (256 KiB) keeps the bytes it was handed, and its body is those bytes: its source is never read again. A larger part reads each cell again, in the send pass only.
- **Result:** a level-0 file of at most 256 KiB is read once, as Go does it. A larger part is read twice instead of three times.
- **Cost accepted:** a part of at most one cell holds up to 256 KiB while it waits for a lane and is sent, where it held 16 bytes while it waited. Such a part is the only or the last part of its object, so an upload holds at most one. The peak for a part stays one cell, and the memory gate (`crates/store-s3/tests/store-s3/memory.rs`) is unchanged. A source that would give other bytes to a one-cell part is not asked, so its change goes unseen; the bytes sent are the ones first read, which is the stronger statement.
- **Calls:** the one-cell threshold equals the tally cell, so no new size is introduced (a larger one would save more reads and hold more per waiting part). The cell size became a test-only setting, `S3Config::with_cell`, because the simulator's staged files are a few kilobytes: with the 256 KiB cell no simulated part would be read again and the simulator's judge of second reads, and its scenarios that change a file between its reads, would reach nothing. The simulator sets 32 bytes. If the setting is wrong the cost is one test-only method and one field.
- **Revisit if:** a measurement shows a large part's second read costing more than the staging reads it saves elsewhere, or the part-buffer bound of D222 is relaxed.
