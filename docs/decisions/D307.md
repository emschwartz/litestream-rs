## D307. A buffered upload has `concurrency` parts in flight whatever the part size, and logs what that may hold (amends D232)

Status: decided · Decided by: the owner, 2026-11-27 · Recorded by: Claude (claude-sonnet-5-5) · Closes #503

- **Question:** D232 capped the parts a buffered upload (a compaction's output, a level-9 snapshot) holds at 256 MiB, which cut the parts in flight below the configured `concurrency` for large parts: 100 MB parts with `concurrency: 10` ran one part at a time, with no word to the operator. Should the setting stand?
- **What Go does, and why:** the AWS SDK uploader takes parts from a pool of `Concurrency + 1` buffers (`feature/s3/manager/upload.go`) with no byte bound, so memory is `part size x (concurrency + 1)`. An unset concurrency is 5 and an unset part size 5 MiB; lsr has the same defaults (Go forces 2 on R2 and Tigris; lsr gives 2 on R2 and 5 on Tigris, unchanged here).
- **Decision:** the setting is honoured as Go does. Parts in flight are `concurrency`; a buffered upload holds at most `part size x (concurrency + 1)`. `HELD_BUDGET` and `held_width` are deleted. The parts-per-object rules (10,000 parts, 5 TiB) stay. At start the daemon logs once for each S3 replica, at info, `multipart upload may hold in memory` with `part_size`, `concurrency` and `max_buffered_bytes`, so a large setting is visible. A staged file's upload still holds no part (D222).
- **Measured (studio, macOS arm64, local MinIO, first start of a 4 GiB random database to the level-9 snapshot, 100 MB parts, six interleaved pairs against main, three A/A pairs; the box carried other agents' load, so A/A wall spread was wide):** concurrency 10: peak footprint 225 to 320 MiB (+42.3% [+41.5, +43.1], A/A +0.1%), wall -13.7% [-16.6, -10.8] (A/A +9.6% [-14.4, +40.2], not resolved), CPU -1.1% [-3.9, +1.7]. Concurrency 2: peak +42.2% [+41.5, +42.9], wall -9.8% [-21.5, +3.6] (A/A +6.4% [-3.6, +17.4]), CPU -0.3%. Both peaks are about 320 MiB because a first start's streamed uploads are small beside its staged file's; the bound, not the peak, grows to about 1.1 GB at ten parts.
- **Cost accepted:** an operator who sets a large part size and a high concurrency gets the memory Go would use (1.1 GB at 100 MB x 10) per database uploading at once; for a 5 TiB object a buffered part is about 524 MiB, so 3 GiB at the default five.
