## D216. The fault rig's canary damages what a restore reads, and a nemesis or damage that did not apply fails the run

Status: decided · Decided by: delegated, Claude (claude-sonnet-5-5), 2026-11-25, for the owner · Recorded by: Claude (claude-sonnet-5-5)

- **Question:** the first Linux run of the fault rig (nightly run 45541631723, 2026-11-25) missed all three canary damages with 0 anomalies, so the rig had judged nothing there. Why, and what must the rig do so that a canary, or a nemesis it was asked for, that did not apply can never read as a pass?
- **Cause:** the canary chose its victim among all level-0 files in the bucket, at their middle. The engine writes a level-9 snapshot over the early ones, and a restore of the latest state reads that snapshot and only the level-0 files after it, so a middle level-0 file under the snapshot is read by no restore. A run on a loaded macOS machine missed it the same way (0 anomalies, 135 s, the victim at transaction 0x43 under a snapshot covering 0x01 to 0x3f). The first Linux run also judged only about three new level-0 points in 8 cycles against 100 or more on macOS; that is not explained here, since no Linux machine was available when this was written (see the status note in D195).
- **Choice:**
  1. The canary asks the engine's own plan (`lsr restore --dry-run --json`) which files the latest restore fetches and damages only level-0 files in that plan (drop the middle one, swap two neighbours, flip a byte of the second to last), then judges at once, before compaction can change the plan.
  2. Damage that cannot be applied (fewer than three level-0 files in the plan) is the verdict `NOT APPLIED`, which fails the canary like `MISSED`; a `run` asked to damage the replica and never doing so exits 2.
  3. A segment's first cycle waits up to 45 s for three level-0 files on the replica and raises a rig failure (exit 2, with the engine log tail) when the engine uploads less: a run whose engine uploads next to nothing is a failed rig, not a quiet pass.
  4. `--require-all-nemeses` exits 2 before the first cycle when a nemesis of the menu cannot run here (no LazyFS, no libfaketime). `just fault-rig` passes it on Linux, so the nightly cannot reduce its menu to the macOS subset without failing.
  5. libfaketime fakes the wall clock only (`FAKETIME_DONT_FAKE_MONOTONIC=1`): the second Linux run (nightly 45553967625) showed the engine, with libfaketime preloaded at an offset of zero, uploading two level-0 files in its first second and none in the next 45 s while the writer committed 891 times; boot had finished in 11 ms, and the first Linux run's three new points in 8 cycles fit the same stall. The likely mechanism is that the Rust runtime builds absolute futex deadlines from the faked monotonic clock and the kernel reads them against the real one; that is an inference from the evidence, not a measured one, and the next Linux run decides it. A wall-clock step does not move monotonic clocks either, so the nemesis is now the faithful one. libfaketime is also preloaded into the engine only when the clock-step nemesis is on the menu, so the canary and menu-restricted runs run the engine as it ships.
- **Consequences accepted:** a canary run takes a few minutes longer under load (it judges at once after the damage). A damage that the engine compacts out of the plan between the plan read and the restore reads as `MISSED`; the window is about a second.
- **Cost if wrong:** (4) turns a Linux machine without LazyFS into a failing counted run rather than a partial one; the plant runs do not pass the flag. (5) removes libfaketime from runs that do not step the clock; if libfaketime was what slowed uploads on Linux, the counted run (full menu) still shows it, through (3).
- **Links:** `scripts/fault_rig.py`, `docs/decisions/D195.md`, issue #364 (finding B4).

What it does not show:
- One seed and one run: no rate for other seeds, and the zero failing anomalies bounds nothing by itself (the 3/N bound in the simulation-testing skill applies to a fault distribution over many independent cycles, and the cycles of a segment are not independent).
- Nothing about segments the Go nemesis touched beyond the count: every anomaly in one is excused, so a new defect in such a segment is hidden.
- Unaided recall of planted engine bugs: one plant (wal-barrier) was run, once, and found. No other plant was run on Linux.

The 35 Go cycles with no `OtherWriter` logged (of 45): in 28 of them the segment held anomalies (51 in total; the 10 cycles that logged it held 100), in 7 it held none. The exemption is by segment, not by signal, so it excuses an unsound restore whether or not the engine said anything: that is the second half of #346 (the engine does not always log `OtherWriter`) and expected until it is fixed, but the exemption is wider than the issue, since it cannot tell a new defect in a tainted segment from #346. The 28 silent cycles with unsound restores are the finding the rig exists to make: a second writer that lsr did not report.
