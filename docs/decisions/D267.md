## D267. The boot's identity check restores the replica a slice a tick (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5) · fixes #477

Amends point 3 of D265: the allowance for a boot that finds nothing staged to restore the replica in its one tick is gone (`Spare::boot_restore`, its reach count `tick_cost.boot_restore_read` and its test), and `liveness::a_boot_over_another_writer_reads_the_replica_a_slice_a_tick` runs that boot under the plain per-tick bound.

- **Question:** a boot over a new meta directory, facing replica files the live WAL cannot vouch for, runs the identity check (docs/decisions/D170.md, D176.md): it restores the replica's state at its newest transaction and compares it with the database. The restore ran inside the one boot tick: at full size the 16 GB level-9 snapshot and every later file, about 230 s in the full-size drill, in a tick nothing could stop. How is it spread out?
- **What Go does, and why:** Go reads one file here: `checkDatabaseBehindReplica` (`db.go`) downloads the replica's newest level-0 file and builds on it. D170 records the Go defect the check guards against (an empty meta directory taken as consent), so the restore stays and only its shape changes.
- **Choice:**
  1. The restore reads at most a tick's bytes (`upload.bytes_per_tick`; one read asks for at least 256 KiB, so a step may end that far past them) and opens at most 16 files a step, applying files oldest first with the checks a restore makes (`restore::Stepped`). A file costs a request or two whatever its size: a replica of many small level-0 files made hundreds of requests in one tick by bytes alone (19.6 s against an 18.3 s bound in the simulator's boot over another writer). Its place, and the image of one checksum a page, are kept in memory between ticks.
  2. A restore that finishes in the boot's own tick compares in that tick, as before: a replica under one tick's bytes costs nothing more.
  3. Otherwise the boot ends its tick with `Event::CheckingIdentity`, the next ticks read on with no listing, and once the image is whole the boot runs again from its listing and compares. The local counter is read once, as the restore begins, so the restore keeps the right page.
  4. When the replica's newest transaction is not the one the image is of, another writer put it: this engine writes nothing to the replica before it boots. The refusal stands and the boot stops with `OtherWriter`.
  5. Writes stay held through every tick of the check, and health names it (`WhyBlocked::CheckingIdentity`, `Actor::checking_identity`).
- **Cost accepted:** a check longer than one tick lists the replica once more (the second boot's listing) and reads the newest staged file's header again. A store fault part-way fails the boot, and the next attempt restores again from the start.
