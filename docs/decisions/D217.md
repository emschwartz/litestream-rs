## D217. A large staged file goes to the replica a slice per tick (delegated)

Status: decided · Decided by: Claude (claude-fable-5-2), **delegated**; the owner can overturn it · Recorded by: Claude (claude-fable-5-2) · First step of the design chosen for issue #364's finding that one thread goes blind for the length of each whole-file upload

- **Question:** the engine is one thread that does one unit of work a tick, and the upload of one staged file was one unit. A multi-gigabyte staged file (a first sync, a large transaction) therefore held the thread for the whole upload: no commit was staged, no checkpoint ran and the WAL grew until the file was on the replica. How does the engine keep replicating while it sends?
- **What Go does, and why:** Go runs two goroutines for each database. `Replica.monitor` uploads the staged level-0 files in order, each with one blocking `WriteLTXFile` call that streams the whole file (`replica.go` `uploadLTXFile`), while `DB.monitor` keeps syncing the WAL into new staged files and checkpointing. So under Go a large upload does not stop syncing or checkpoints, and the files staged meanwhile wait behind the large one. That outcome is the one wanted here. Go's means, a second thread sharing the position with the first, is not taken: the engine's decisions are pure functions the simulator drives one tick at a time, and a second thread would put the interleavings between upload and sync outside it.
- **Choice, in ten lines:**
  1. The upload task keeps at most one file in flight between ticks: the decoder that verifies it, the count and digest of the bytes read, and the upload open on the replica (`upload::Sending`, boxed, in memory only).
  2. An upload step reads the staged file from where the last one stopped and hands the replica what it read, until the file ends or the tick's bytes run out: 8 MiB (`UploadConfig::bytes_per_tick`), shared by every file the tick sends.
  3. The file is published only by the step that reaches its end, after the decoder verified the whole of it and its length, digest and trailer checksum, on the reads that were sent, are the ones its token was minted for. Nothing is visible before that.
  4. A tick that sent a slice and published nothing reports `Event::Sending { bytes }`, and the next tick runs at once.
  5. A file in flight goes first, and the WAL step has the tick after every eighth slice: the share an upload has after eight syncs in a row, turned around. At most 64 MiB of the file goes between two chances to sync, and with no new commits that tick is a slice too.
  6. Prune and maintenance keep the fair share they had (every 8 upload ticks that passed them over): they run in the WAL step's tick when it has nothing to sync.
  7. Anything that deletes staged files must first hold `upload::Unsent`, which only stopping the send (and aborting its upload) or bounding the delete below the file in flight gives. The compiler checks it.
  8. Any failure of a slice aborts the upload and ends the send. The retry starts at the file's first byte. A send is never resumed from bytes an earlier read verified.
  9. A drain keeps slicing; at its deadline the send is aborted and the file is counted as not uploaded. A stop, a rebuild and a crash drop it, and the next start's `remove_scratch` clears what it left.
  10. Later level-0 files wait behind the file in flight, as Go's do. Level-9 copies, compactions and the staging of a whole database are still one unit each (the later steps of the same design).
- **The budget and the bound on a tick:** the budget is bytes, not time, so the engine reads no clock for it and the simulator needs none. A tick with a slice makes at most 32 reads of 256 KiB from staging and 32 writes to the replica, and one commit when the file ends. Each of those is bounded by its store, not by the engine: the file store by the disk, the S3 store by its own deadline (a write only buffers until `concurrency` parts are ready, 25 MiB by default, and the batch that then goes out fails as a timeout after four deadlines). A byte budget cannot bound a tick against a store that is slow without failing; that needs the store's deadline, which S3 has and the file store does not (a hung mount hangs every unit, as before).
- **What an abandoned upload costs:** on the file store, a temporary file. On S3, a multipart upload whose parts are billed until it is aborted. A send that is stopped is aborted then. One that is dropped (a stop, a rebuild) puts its id on the store's orphan list, aborted before the next upload begins. One lost with the process is listed and aborted by the next start, and a bucket lifecycle rule is the backstop (`docs/limitations.md`). None of this is new: a killed whole-file upload left the same.
- **The two reviews** (Gemini and Codex, on the design document, before any code):
  - Gemini: "Build **D (items 1–2) plus A**. Reject **B** and **C**." and "A preserves the single-threaded, sans-IO core: every interleaving between slices ... is driven deterministically by the existing simulator without thread scheduling". Its weakest point was the level-9 copy's point in time and that a turn to a snapshot or a drain "must abort any in-flight level-9 `Copy` and `Merge` first". The copy is a later step; the rule is built here for the one job this step has, by type (line 7).
  - Codex: "Verdict: build A in stages, starting with resumable level-0 uploads and compactions (they need no SQLite access)". Its conditions: "Abort condemned sends before deleting their inputs" (line 7), "Preserve same-read verification through commit" (lines 3 and 8), "Land cancellation, deadlines and input protection with the first resumable job" (lines 7 and 9; the deadline is the store's), and its warning that "an 8 MiB write budget alone cannot bound a blocking S3 batch or guarantee lag behind an earlier level-0 file" is accepted as written above: the store's deadline bounds the batch, and the lag behind the large file is Go's too.
- **Cost accepted:**
  - Commits made during a send are staged and checkpointed but reach the replica only after the large file, as under Go. `lsr_unreplicated_age_seconds` still grows for the length of the upload.
  - A commit made during a send waits up to eight slices to be staged (64 MiB of upload: about a second on a link of 50 to 100 MiB a second, Go's monitor interval), where it waited for the whole file.
  - An application that commits continuously pays one sync, and stages one file, for every 64 MiB sent. A send long enough for 4,096 staged files to wait stops staging, as any backlog does (`docs/limitations.md`): 256 GiB at that rate.
  - Memory is a sum where it was a maximum: a maintenance step that runs between two slices holds its own buffers beside the send's (a decoder and the store's open upload, at most `concurrency` parts on S3). The send itself holds what the whole-file upload held: the gate in `crates/store-fs/tests/store-fs/memory.rs` measures 533,772 bytes against 533,268 before, whatever the file's size.
  - A staged file that goes bad is found at its end, not at its first bad byte, and is read and sent whole on each try before it is dropped, as before.
  - Bytes read before the 100-byte header is whole are held until it is (the upload is begun from the header's timestamp), so the first write can carry up to 99 bytes more than the tick's bytes.
  - `ObjectStore::Upload` must be `'static` (it is owned across ticks), and `Event::Sending` is one more public variant.
- **Measured:** MEASURED
- **Options considered:** the WAL step's turn after every slice, which was built first: TURNS; its turn once a monitor interval, which is Go's cadence exactly but needs time to pass between the simulator's ticks, which all run at one instant while there is work; a second thread for uploads, as Go has (above); a time budget read from the clock each chunk (a tick's length would then depend on the machine, and the simulator would need a model of store speed to reach the boundary); resuming a failed send from its last verified byte (S3 parts make it possible, but it trusts bytes a previous read verified, which `AGENTS.md` rules out, and Go restarts the file too).
- **Revisit if:** a store is added whose single write can block without a deadline; the later steps (level-9 copies, compactions, staging a whole database) need more than one job in flight; a measurement shows the turn-taking costs more than a quarter of the upload's speed.
