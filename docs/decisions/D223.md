## D223. The format's CRC-64 runs on carry-less multiply through `crc-fast` (needs the owner's approval)

Status: proposed, **needs the owner's approval** (a new runtime dependency, D164) · Recorded by: Claude (claude-sonnet-5-5)

The CRC-64 over every page and every file is the largest CPU cost left in a first start once the byte digest is fixed (see D210): 11 passes over the data, at about 3.4 GB/s each with the slice-by-16 table CRC in `crates/ltx/src/checksum.rs`.

- **Question:** may `lsr-ltx` depend on a SIMD CRC crate for the one CRC the format uses?
- **Choice:** replace the table CRC with `crc-fast` 1.10.0 (MIT OR Apache-2.0; `default-features = false, features = ["std"]`), behind the existing `PageChecksum`, `FileChecksum` and `Crc64` types. One implementation, no `cfg` switch, no fallback of ours. The crate picks its path once at run time: PMULL (with AES, and SHA3 where present) on aarch64; PCLMULQDQ with SSE4.1, AVX-512 or VPCLMULQDQ on x86-64. An x86-64 without PCLMULQDQ and a target with no SIMD CRC path use the crate's own table fallback, which has no `unsafe`. The `crc` crate stays as a dev-dependency: the second, independent implementation the equivalence test checks against.
- **Lock entries:** six, `crc-fast`, `digest` 0.10, `crypto-common`, `generic-array`, `spin`, `version_check`, all MIT or Apache-2.0 (`just deny` checks the licences, advisories and bans).
- **Measured** (Apple M1 Max, macOS arm64, 512 MiB random database, file replica, first start to L9, 12 interleaved pairs, A/A +0.73% [-0.04, +1.50] over 6 pairs, SESOI 2%): CPU -46.1% [-46.55, -45.64], wall 4.09 s to 2.41 s, all 12 pairs faster. Micro: 55 to 59 GB/s against 1.7 to 3.4 GB/s for slice-by-16 (the table CRC read low in that run, so the ratio is rough).
- **Not measured:** x86-64 and Linux (the rented box), any CPU without PCLMULQDQ or PMULL, and the effect on a restore (the same CRC passes, so the same direction, but not timed here).
- **Safety:** the crate has about 340 lines mentioning `unsafe` outside its tests and C API, nearly all intrinsic wrappers and `#[target_feature]` functions in its `arch` modules; the table fallback has none. Equivalence is checked by property test against the `crc` crate over random lengths and splits, by the standard check value, and by the page checksums Go computed. The nightly address sanitizer job runs the replica thread tests, which hash pages through this code on x86-64, so the SIMD path is instrumented there for heap errors. Miri cannot execute these intrinsics and reports no PCLMULQDQ, so under Miri the crate takes its table fallback: Miri covers our use of the API and the fallback's arithmetic, never the SIMD kernels. Their only evidence is the equivalence test on real hardware.
- **Alternatives:** (a) keep the table CRC: no dependency, 11 passes at 1 byte per cycle. (b) hand-written PMULL and PCLMULQDQ: `unsafe` in our tree, which D164 reserves for the SQLite crate. (c) a four-stream slice-by-8: tried, +9% on the CRC alone, rejected.
- **Cost accepted:** a new runtime dependency with about 340 `unsafe` lines we do not own, and one more path the nightly cannot check under Miri.
- **Revisit if:** the crate is yanked or unmaintained, an advisory names it, or its output differs from the table CRC on any CPU.
- **Links:** D164, D210; `crates/ltx/src/checksum.rs`.
