## D168. One read of the newest staged file decides no snapshot at boot (delegated)

Status: open to owner review · Decided by: Claude, **delegated**

- **Question:** at boot, recovery reads the newest staged file's header and pages and compares them with the WAL. One read that answers with other bytes (a lying disk or page cache) made the file look unreadable, or its last page look unlike the WAL's, and the boot snapshotted on that one read. Elsewhere (the staging sweep, the witness passes, the uploader) one failed read says nothing. Should a snapshot that rests on that read wait for a second?
- **Choice:** yes. When a boot would snapshot with `NewestStagedFileUnreadable` or `LastPageMismatch`, nothing the sweep or the witness passes proved explains it, and the file is not already the suspect, the file becomes the suspect and the boot fails with `StagedLost`. The next boot that reads the same answer snapshots as before.
- **Options considered:** read the file twice inside one boot and compare (twice the read cost on every boot); doubt every boot snapshot that follows a read of the newest staged file (a retry before every ordinary generation change).
- **Why:** a snapshot costs every restore point since the last one, and the rule that one failed read proves nothing already holds on every other path; the triage session found the two causes a single lie reaches.
- **Cost accepted:** a newest staged file that is truly torn, or a WAL whose last page truly differs, now snapshots one boot later, after one `StagedLost` retry (about a second with the default backoff). Other causes a lying header could fake (`GenerationChanged`, `LocalRewound`) are not doubted.
- **Revisit if:** a lying read is found to reach another boot snapshot cause.
