## D175. A boot uploads the staged files it finds, after checking them, as Go does

Status: decided · Decided by: owner, 2026-11-23, confirming the choice Claude (claude-fable-5-2) made as delegated the same day · Second opinion: a design review by Claude (claude-opus-5-5) on the same day reached the same choice

- **Question:** D173's change 3 removes the boot witness pass, which after a restart re-derives every staged file not yet uploaded from the live WAL before the engine will upload it. D173 named its replacement: delete those files and stage them again from the WAL. Built, that replacement broke behaviour v1 keeps. Files staged again carry a new time, so the age of the oldest commit not yet on the replica started again from zero in a crash loop (D174 keeps that age), and the files' boundaries changed. What does a boot do with staged files that were not yet uploaded?
- **Choice:** what Go does, with more checking than Go. A boot reads each such file whole, verifies its checksum, checks that it starts where the file before it ended in the WAL (the same salts and the next offset, or a new WAL generation, or a snapshot), and uploads it as staged. The first file that fails is dropped with every file after it, as a refused file is today. The existing comparison of the newest staged file with the WAL stays, and covers the staged files below it that the live WAL still holds (at most the newest 4096). Go verifies only the newest file and uploads the rest by name.
- **What the removed pass caught that this does not:** (1) the staging directory alone put back from a copy of another timeline, with the database in a new WAL generation and the copy holding files above the replica: those files are uploaded, and the boot then takes a snapshot, so a restore of the newest state is right and a restore to a transaction inside that range gives the other timeline's state. D173 lists putting staging back as an operator's act; (2) one staged file replaced by a well-formed file with other content and the same header claims, which is D173's "files forged to pass the engine's checks"; (3) after a power loss on a disk that lost acknowledged writes, staged files holding commits the database lost are uploaded before the boot's snapshot, where the pass refused them. They are commits the application made, and Go uploads them. A power-loss rewrite of an earlier file's frames is caught while that file's staged copy is still in staging: the boot compares the staged files below the newest that chain to it (each made in the live WAL's generation and ending where the one above starts, the newest 4096) with the WAL by the comparison it makes for the newest file, and a mismatch takes a snapshot. A file a snapshot was taken above does not chain, so the snapshot's answer is not asked for again at every boot. It stays open once the copy has been pruned, or a snapshot has been taken above it (after level-1 compaction covers it, 30 seconds by default), and Go has the same gap.
- **Design rule kept:** "never use bytes that were not verified on the read that produced them" holds. The boot's read verifies the file and gives the upload its expected bytes, and the upload verifies again on its own read. What goes is the proof that the bytes came from the live WAL, a separate defence.
- **Cost accepted:** case (1) above, silent for restores to a transaction in the uploaded range.
- **Why:** it keeps the files' times and boundaries with no new remembered state, it is about 270 fewer production lines than the pass (the replacement adds about 100), and the pass itself took about eight fixes.
- **Revisit if:** a real deployment reports a replica holding commits its database never made after a restart.
