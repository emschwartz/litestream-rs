## D237. New commits are synced once per poll interval, however often the engine ticks (delegated)

Status: decided · Decided by: Claude (claude-fable-5-2), **delegated**; the owner can overturn it · Recorded by: Claude (claude-fable-5-2)

The same head-to-head (a counting proxy in front of MinIO, 20 commits a second) counted 101 level-0 PUTs a minute for this engine and 61 for Go. Of the 203 gaps between this engine's level-0 PUTs, 79 were 0.0 s and 124 were 1.0 s: the files came in pairs.

- **Question:** how many level-0 files does a steady writer cost per poll interval?
- **What Go does.** One. Its monitor runs one `db.Sync` per tick of a one-second ticker (`db.go`, `monitor`), and `Sync` loops only while the byte cap cut a file short. The replica's own one-second ticker uploads what is staged.
- **Cause.** The engine's WAL step ran on every tick and staged whatever was committed since the last one. The replicator thread ticks again at once whenever work is ready, and after a sync it is: the staged file waits to be uploaded. A commit that landed during the 20 ms the first file took to write was therefore staged as a second file by the next tick, and both went up together. The same happened on every tick that followed a compaction or a listing. The daemon's debug log of a run against a file replica shows it: `wal synced` at 17:38:03.662 and again at 17:38:03.682, then one upload of both. Of that run's 40 seconds, 16 saw one sync, 16 two, 5 three and 3 more than three (84 level-0 files); with this change every second of a like run saw one (42 files).
- **Choice.** The engine has a sync interval (`ActorConfig::sync_interval`), which the replicator sets to the poll interval. A sync step that only new commits ask for runs no sooner than one interval after the last step began; the tick that holds it names that time as its wake. Nothing else is held: the rest of a sync the byte cap cut short, a snapshot, the proof a due checkpoint needs and a drain all run at once. Zero is the old behaviour and stays the default of the simulator and the engine's own tests, which tick when they have something to stage.
- **Why in the engine.** The thread cannot hold the step from outside: the tick that uploads a file is the same call that would stage the next one.
- **Cost accepted.** A commit is staged up to one poll interval after it was made, as before and as under Go (the poll was already the bound for a commit that landed just after a tick); what changes is that a commit that happened to land during other work is no longer staged early. Engine time runs at half rate after the wall clock steps back, so a held sync can then wait two intervals of wall time. The simulator does not exercise the interval.
- **Counted.** `actor::tests::steady::a_steady_writer_stages_one_file_per_poll_interval` (lsr-core, two minutes of 20 commits a second, a sync taking 20 ms and a put 20 ms): 120 level-0 PUTs with the interval, more than 150 without.
- **Revisit if:** the simulator gains a driver that ticks at once on ready work, which would let it run with an interval too.
- **Links:** `crates/core/src/actor.rs` (`wal_unit`, `sync_held_until`), `crates/replica/src/config.rs`, D217.
