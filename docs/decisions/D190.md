## D190. The boundary snapshot after a TRUNCATE holds no write lock

Status: decided · Decided by: owner (asked for it), Claude (claude-opus-5-5), delegated (how) · Recorded by: Claude (claude-opus-5-5)

- **Question:** after a TRUNCATE checkpoint that moved the WAL, the engine copies the whole database into a snapshot (CKPT-4). It held SQLite's write lock for the whole copy, so the application could not write for minutes on a large database (issue #323). The owner, 2026-11-24: "We definitely should not be holding the write lock for the whole time." Can the lock go, and what keeps the copy whole without it?
- **Choice:** the copy takes no lock. `boundary_snapshot` in `crates/core/src/checkpoint.rs` runs the snapshot step alone. The `Checkpointer` trait keeps `begin_write_lock` and `end_write_lock`, which the engine no longer calls; removing them is left to the change that settles issue #313's gate, which may reuse them.
- **Why it is safe:** the read transaction the engine retakes inside its checkpoint call, before the copy starts, already stops every change that could mix two states into the copy:
  - On read mark 0 (nothing committed between the TRUNCATE and the retake), the engine's shared lock on mark 0 makes every backfill by any connection busy: the database file does not change during the copy.
  - On a mark m above 0 (a commit landed before the retake), a backfill reaches no further than m. The snapshot reads its committed end E after the retake, so m is at most E: every page a backfill may write has a WAL frame at or below E, and the copy takes it from that frame, never from the database file.
  - A WAL restart or truncate that would rewrite frames 1 to E needs every mark above 0 free and the WAL fully backfilled; the engine's own mark, or the engine's sequence frame left unbackfilled under mark 0, stops both.
  - Commits after E are the next incremental step's, read from the WAL. Commits made between the last step and the TRUNCATE were backfilled before the lock was ever taken; the full copy covers them, the lock never did.
  - The lock came from Go (`db.go`), which reads the WAL to its file end and needs it to pin the WAL's state. This engine bounds its read by one wal-index read.
- **Second opinion:** Codex, through the codex-rescue agent,, asked to find a breaking interleaving: "safe to remove the boundary copy's write lock with bundled SQLite 3.54.1, provided the same engine read transaction stays held through the copy". It found one flaw in the argument, not in the code: a PASSIVE checkpoint that passed its "everything backfilled" test before the engine sampled E can cut the database file to an older, shorter size during the copy. Every page past that cut that the snapshot needs has a WAL frame at or below E, and the snapshot's page count comes from the commit at E, so the copy survives it. Gemini (gemini-4-argon), asked the same: "Safe". It adds that the argument leans on the engine's sequence frame being committed after the retake and before the copy (`truncate` returns on a failed bump, so no copy runs without it), and on the page count coming from the last commit at or below E rather than the file's size.
- **Evidence:** `crates/sqlite/tests/sqlite/boundary_snapshot.rs` on real SQLite: an application commit at every engine call from the TRUNCATE to the end of the step after it, and one inside the TRUNCATE's own call between the WAL truncate and the read retake (the engine then sits on a mark above 0), with another connection running PASSIVE checkpoints (and TRUNCATEs) at every call. Every state the staged files restore to is one some commit made, page for page, and the newest is the live database. Under the old code the commit during the copy failed with "database is locked". The plant `copy-without-read-transaction` (page reads with the read transaction dropped) makes the restore check fail.
- **Cost accepted:** none new. The copy still reads the whole database and uploads it once per TRUNCATE; the page checksum table is still cleared and nothing is checked (D121). Writes now wait only inside SQLite's own TRUNCATE, for its copy of the WAL into the database file: bounded by the WAL's size, not the database's.
- **Revisit if:** the sequence bump moves after the copy or stops being required before it; the copy ever reads the database file for a page the WAL also holds at or below E, or reads without the retaken read transaction; or issue #334 removes the copy, which makes this moot.
