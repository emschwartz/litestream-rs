## D280. A write the store refuses against its checksum deletes nothing, at any level, and a reset an in-tick commit ends still excuses a snapshot (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5) · Amends D75 and D78 (the delete after a rejected create-only write); settles what D222 left for a decision

- **Question 1:** after an upload whose bytes the store rejects (`CorruptCause::ChecksumMismatch`), may the engine delete the key? It deleted it after a create-only write, on the premise of D75 and D78 that "the bucket refuses a taken key before it takes any bytes", so a rejected object is the write's own.
- **What was found:** a nightly simulator seed (0x0000126d693806e2, on the S3 replica, under reads that lie) lost a transaction a restore had already shown. A create-only PUT of level-0 file 2 published and then failed with a 500 (ambiguous). The retry's body was refused against its signed SHA-256 (`XAmzContentSHA256Mismatch`, read as a checksum mismatch, D250). The engine took the rejection as proof the object under the key was its own and deleted it, and the replica's newest transaction went from 2 back to 1. S3 checks a body against its signed hash before it looks at `If-None-Match`, so the refusal proves nothing about the key; D222 had already noted the needless delete and left it for a decision.
- **What Go does, and why:** Go deletes nothing after a failed write. It writes the file again on the next sync.
- **Choice 1:** a rejected level-0 write deletes nothing, in either mode. `publish::Rejected` and `remove_rejected` are gone; the uploader keeps its state and writes the same key again, and a create-only retry that finds the key taken reads it back as any refusal does (the same bytes confirm it, an object that does not verify is replaced). One request fewer than before on every rejection.
- **Question 3:** the same refusal of a compaction output or a level-9 snapshot was still answered with a delete of the key (`maintain::leaves_bad_output`, `Fault::leaves_bad_snapshot`). The same hole is there: an earlier attempt's output or snapshot that published and then answered a 500 is listed, retention may delete the files below it, and a delete on the retry's refusal then takes the only copy.
- **Choice 3:** a checksum refusal of an output or a snapshot deletes nothing, in either write mode, whole or by part. A commit the store took at another size than the one sent (`CommitSizeMismatch`) is still this attempt's own and still deleted. Instead of the delete, the refusal owes the read-back a boot owes (`maintain/audit.rs`): the next listing reads back the header and tail of the newest file of each level before anything is planned from it, and a file that fails two reads and that lower levels cover is deleted and built again. That removes an output a store took cut short or with a bad tail before it refused it; a body damaged behind a sound header and tail is left to its first whole read, as at boot (D272). On S3 the store crate itself deletes an object answered with a wrong ETag. The plant `compact-rejected-output-kept` is retired: keeping the output is now the rule.
- **Requests:** the refusal costs two ranged reads (about 125 bytes) of the newest file of each level above 0 where it cost one delete. Go makes neither; the read guards against an object a store took damaged, which Go leaves listed as cover no restore can decode, and it runs only after a refusal, never in steady state.
- **Question 2 (simulator):** the needless-snapshot check notes `PositionUnproven` when a step ran under a wal-index reset ahead of the WAL header, looking once the tick ends. A commit the application makes inside that tick writes the header and ends the reset first, so the check missed it and failed the running engine's next snapshot (seed 0x0000126d6937d0f6: a boot after a power loss, a commit inside its snapshot step, then `Resnapshot(GenerationChanged)`).
- **Choice 2:** an operation the application makes inside a tick records whether the index was reset ahead right before it, and a reset found so notes `PositionUnproven` in that tick, as a reset that outlasts the tick does. The engine's snapshot is right: its step ended unproven (`StepEnd::Unproven`), so it holds no read-lock proof for the new generation.
- **Cost accepted:** between a refusal and the read-back's second failed read a damaged output stays listed; retention waits for the read-back, so nothing below it is deleted meanwhile. A drain's final retention pass is skipped when its final snapshot failed, as before. A running snapshot in a tick whose in-tick operation found a reset is excused even when no step read under it; the window is one tick.
- **Checked by:** `core::upload::tests::a_refused_create_only_body_deletes_nothing` and `a_rejected_commit_deletes_nothing_and_its_retry_reads_the_key_back` (both fail on the old code), plant `rejected-write-deletes-the-key`, which replaces `part-mismatch-deletes-the-key` and `rejected-replace-deletes`; `sim::needless_snapshot::a_commit_inside_a_step_under_a_reset_index_justifies_the_next_snapshot` (fails on the old check), and the needless-snapshot plants still killed.
