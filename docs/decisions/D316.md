## D316. A restore overlaps the round trips of its small files and of its created-at reads (delegated)

Status: decided · Decided by: delegated, Claude (claude-sonnet-5-5), 2026-11-27, for the owner; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5)

- **Question:** a drill against Tigris (20 to 60 ms a request) restored a small database, a snapshot and many small level-0 and level-1 files, in 11.1 s where Go took 5.4 s; the same replica at an instant took 14.2 s against 6.6 s. Why, and what is the fix?
- **Cause, latest:** a restore applied the files of its plan one after another, each as one GET started when the one before it was done, so a plan of N small files waited N round trips. Go opens its plan files 32 at a time before it decodes any (`openRestoreFiles`, `restoreOpenConcurrency` in `replica.go`). Both make one GET per file; the request count was never the difference.
- **Cause, instant:** the plan for `-timestamp` needs the created-at time of each file of the chain (one HEAD each on S3) and asked for them one at a time, though the store runs 16 at once, so a chain of N files waited N more round trips. Go reads them concurrently.
- **Decision, files:** a store that reads several streams at once (`BatchKind::Spans` width of two or more, as for a window) opens the next 32 files of the plan, those of at most 1 MiB listed size, while the restore applies the one in front. Each is the rest of the object from byte 0, one GET, opened by `read_span` with an end of `SPAN_TO_END` and read ahead by the store one piece deep. Bytes are still decoded, verified and written in plan order from one stream per file, and a file longer or shorter than listed reads as before. A larger file is opened when its turn comes (a file of two spans or more through its window).
- **Decision, created-at times:** the planner names the files it will ask for after the one it needs, by growing the chain from the files not yet touching as it would if every one proves eligible, and the store's existing batch (`created_at_many`, 16 wide on S3) reads them together. A wrong guess costs a HEAD: the files past the instant, about a batch or two.
- **Measured (studio, replica of 301 files written by Go, MinIO behind a proxy adding 30 ms to every request, interleaved rounds, 5 each; pages equal to Go's restore):** latest, median 11.07 s before, 0.71 s after, Go 1.55 s; instant, 8.71 s before, 4.55 s with the files change alone, 0.80 s with both, Go 1.77 s. GETs: 301 and 121, the same before and after. HEADs for the instant: 124 before, 146 after, Go 623. LISTs: 10, Go 21.
- **Bounds:** 32 is Go's own bound for files, and 16 is the store's existing created-at batch, so this adds no parallelism beyond Go's or the store's own. Memory is at most 32 files of 1 MiB read ahead (32 MiB) and 32 read-ahead threads of the store's, where a restore held one file. A restore that fails or finds a file gone drops the streams opened ahead: up to 31 GETs that were not needed, once per attempt.
- **Cost accepted:** a thread per small file on S3 (the store's read-ahead thread, as a window's span has), one at a time up to 32; about 22 HEADs more on a restore to an instant of 301 files (146 against 124), under a quarter of Go's 623.
- **Revisit if:** a store bills a GET that is dropped unread differently, a deployment needs restore memory under 32 MiB more than a single stream, or a replica's shape makes the guessed chain wrong often (a HEAD count well above the plan's files).
