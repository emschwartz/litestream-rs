## D200. Which SQLite builds the library runs on: a verified list across libsqlite3-sys 0.37 to 0.40 (delegated)

Status: decided · Decided by: delegated, Claude (claude-opus-5-5), 2026-11-24, for the owner, on the direction recorded on issue #314 · Recorded by: Claude (claude-opus-5-5) · Supersedes: D152

- **Question:** `lsr-sqlite` accepted exactly one SQLite build (3.54.1 from `libsqlite3-sys` 0.40.0) and reached it through rusqlite 0.43, which pins one `libsqlite3-sys` minor. `libsqlite3-sys` declares `links = "sqlite3"`, so a build holds one version of it, and an application on sqlx 0.9 (which needs 0.30.1 up to 0.37) could not build with the library at all. Which builds may the library run on, and may an application link its own?
- **Options:** document the pin and keep it; widen to a `libsqlite3-sys` range while keeping the run-time check to one build; widen to a range and check against a list of builds, each verified.
- **Choice:** a range and a list. `lsr-sqlite` uses `libsqlite3-sys` directly (rusqlite is an optional feature, `rusqlite`, for the convenience functions that take a rusqlite connection; any rusqlite from 0.39 to 0.43), declared once in the root manifest as `>=0.37, <0.41`: SQLite 3.51.3 to 3.54.1, and nothing older, because 3.51.2 shipped a bug in the WAL reset. At open, `sqlite3_libversion_number()` and `sqlite3_sourceid()` must match one entry of `VERIFIED` in `crates/sqlite/src/version.rs`: 3.51.3, 3.53.1, 3.53.2, 3.54.0 and 3.54.1, the builds bundled by `libsqlite3-sys` 0.37.0, 0.38.0, 0.38.1 and 0.38.2, 0.39.0, and 0.39.1 and 0.40.0. Anything else is `OpenError::SqliteBuild` (`StartError::SqliteBuild` in `lsr-replica`), which names the version and source id found and the versions verified.
- **bundled:** a default feature of `lsr-sqlite` and `lsr-replica`, which an application turns off (`default-features = false`) to link its own SQLite. It is safe only with the list: the run-time check, not the feature, keeps a build nobody verified out. A distribution's build of a listed release passes, since the source id names the upstream check-in, not the compile flags.
- **Verified means:** the whole lsr-sqlite suite has run on that build. CI runs it once per entry (`just sqlite-build <libsqlite3-sys> <rusqlite>`, a matrix job), and once against the runner's system SQLite with `bundled` overridden (`just sqlite-system`): the open must accept that SQLite exactly when it is listed, and the suite runs on it when its version is in the range. Ubuntu 24.04 ships 3.45.1, so today that job checks the refusal. `just sqlx-check` builds an application crate on sqlx 0.9 and `lsr-replica` together.
- **Adding a build:** read `identity` and `shm` against its `sqlite3.c` (`struct unixFile`, `WalIndexHdr`, `WalCkptInfo`, `WALINDEX_MAX_VERSION`), add its `libsqlite3-sys` version with the rusqlite that pairs with it to the CI matrix, add its entry to `VERIFIED`, and see the suite pass. A `libsqlite3-sys` minor past 0.40 also widens the root range.
- **Why:** the `identity` and `shm` modules read SQLite's private `unixFile` and wal-index layouts, unchanged since the 3.7 era but outside SQLite's interface, so a wrong field is a wrong descriptor or a wrong committed end, never an error (D152's reason, which stands). A list keeps that guarantee per build while letting an application's SQLite stack choose any version in the range.
- **Cost accepted:** four more CI jobs per pull request, one per entry beyond the lock's own (the land gate already runs the suite on 3.54.1), plus the system job and the sqlx build; each new `libsqlite3-sys` release is refused at open until someone verifies it and adds it. The library's own test code must compile on every rusqlite from 0.39 to 0.43 (`Connection::file_control` and owned-only authorizers are newer, so the suite reaches those through the raw handle). An unbundled SQLite older than 3.44 does not link (`sqlite3_set_clientdata`), which is outside the range anyway. A second copy of SQLite the application links for its own connections is still not detected; that remains an embedding rule.
- **Revisit if:** a deployment needs a build that the list cannot carry (a patched SQLite with its own source id), or the layout reads go away.
