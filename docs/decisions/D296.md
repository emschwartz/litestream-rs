## D296. A first start's listings after both listing fixes: the boot's and one more (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5) · Amends: D287, D294

- **Question:** D287 (a first start plans its first snapshot from the boot's listing) and D294 (the levels above the top are listed once per boot) landed together, and each one's tests pinned a count that assumed the other absent: D287's counted the levels above the top in both whole listings (level 5 twice, 20 LISTs in all), D294's counted three whole listings. Which counts are right?
- **Decision:** both changes hold at once, so the counts are the least either allows: a first start makes two whole listings, the boot's and the one after its first snapshot; the boot lists all ten levels and the second leaves out the empty levels above the top, so a first start sends 15 LISTs (levels 0 to 3 and 9 twice, levels 4 to 8 once), against 30 before either change. Go sends no request that either change removes: it lists its configured levels once as each monitor starts and plans the first snapshot from one listing of level 9 (`store.go`, `CompactDB`). No request guards a Go defect, so none is kept.
- **After the boot:** a steady writer's whole listings are one per snapshot window. Its level 9 is listed twice in eight minutes (it was three or more when a first start listed whole again before its first job); the test pins the two.
- **Tests:** core `a_first_start_lists_the_levels_above_the_top_once`, `a_first_start_lists_the_replica_at_boot_and_after_its_first_snapshot_only`, `a_restart_lists_the_replica_before_its_first_maintenance_pass`, `after_the_boot_a_steady_writer_never_lists_the_empty_levels_above_the_top`.
