## D81. What counts as lag for fail-stop (delegated)

Status: open to owner review · Decided by: Claude (fail-stop), **delegated**

- **Question:** the false-trip judge, run over random simulator histories, found the clock running with nothing of the application's off the replica. Which staged files are lag?
- **Choice:** every staged file the replica lacks, except: a file that changes no page against the page checksum table at the same size (the driver's start and the frame after each checkpoint rewrite page 1 unchanged; a boot finds such files among the pending ones while it seeds the table); and a snapshot staged for a doubt alone (an operator's request, a WAL whose continuity cannot be proven) while nothing was off the replica. A snapshot owed for a doubt alone no longer keeps earlier lag running; one owed because commits went past staging (a TRUNCATE after a failed WAL sync, a checkpoint past the synced end) does.
- **Cost accepted:** a commit made and checkpointed away by another process between two ticks while nothing was off the replica is missed until the next commit starts the clock: a late trip, never a false one.
- **Amended (false trips found by the simulator on main):** the rule that a file changing no page is not lag also covers the files a checkpoint stages (the seal, the frame that moves the WAL past a restart), which had skipped it. And while a snapshot is owed for a doubt alone with no synced position and every staged file on the replica, the WAL end when the doubt is first observed is a baseline: frames up to it, and a snapshot that ends at it, are not lag. A commit that lands between the boot and that observation is missed until the snapshot stages it, again late, never false.
- **Amended again (delegated, decided by a Fable review; seeds 0x92d, 0xf465d):** committed WAL frames the engine cannot read are lag, whatever it owes and whatever the simulator knows. With a torn WAL header held past the bound, the engine cannot tell frames it never read (a vacuum that rewrote identical pages) from commits the replica lacks, and with staging found behind the replica (`BehindRemote`), "every staged file is on the replica" says nothing, so the trip is correct by what the engine can know. `BehindRemote` stays out of the doubt causes. The simulator's false-trip judge carries one exemption for this, counted as `failstop.excused.unread_wal`: an age trip while the WAL holds committed frames, no staged file waits for the replica, and the engine has read the WAL at no point after its clock's start. Cost accepted: when the WAL stays unreadable for the whole bound, fail-stop trips even if every commit was in fact on the replica. Revisit if the engine gains a way to show the replica covers the WAL without reading it (a durable mark, #140; tracked database checksums).
- **Amended a third time (delegated, decided by Claude for the owner as the parent session approved; seed 0x734):** a snapshot taken at a boot whose logged cause says continuity broke (`StagedUnverified`, `LocalRewound`) is lag the engine cannot rule out until its own upload lands. After a rollback of the replica, staged files the live WAL cannot vouch for are deleted and their end state is snapshotted; that snapshot may hold commits never staged, and there is nothing to compare it with: Go writes LTX files without a checksum (`ltx.HeaderFlagNoChecksum`), so a tracked checksum is not owed, and a journal record of a quiet transaction would be unsound because continuity is exactly what broke. The judge's second exemption, counted apart as `failstop.excused.unvouched_snapshot`, excuses only an age trip, dated at or after such a boot, in that life, before the engine's first believed upload since. Both counts are reported by the swarm campaign (`unaided::seeds_to_first_failure`) so either one growing into a hiding place shows. Cost accepted: a rollback followed by uploads refused for the whole bound trips fail-stop even when the snapshot held nothing new. Revisit if the engine gains a way to show a snapshot equals the replica's newest state (tracked checksums).
- **Revisit if:** the doubt causes change, or a fault appears that puts commits only in a doubt snapshot.
