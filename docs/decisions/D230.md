## D230. A listed file the uploader has not judged is no input to maintenance: it waits, and makes no stop of its own (delegated)

Status: decided · Decided by: Claude (claude-fable-5-2), **delegated**; the owner can overturn it · Recorded by: Claude (claude-fable-5-2)

- **Question:** the nightly simulator run of 2026-11-25 restored a database no commit made, four times in 7,046 histories. Another writer had put a level-0 file at an id this engine had staged and not yet sent. Maintenance listed the replica between two slices of the send, took the file for the engine's own and compacted it into level 1. The engine's own put of that id was then refused and it stopped for another writer, as it should. After the other writer's file was removed and the engine started again, the boot found level 1 covering the id, dropped its own staged copy and uploaded the next file on top: the newest restore was the other writer's pages under this database's later ones. What may a maintenance listing take as input?
- **What Go does.** Nothing here to follow. Go has no other-writer check: its level-0 uploads are unconditional puts (only the optional leaser sends `If-None-Match`, `s3/leaser.go`), so a second writer's file replaces or is replaced in silence, and its compaction reads whatever the level below lists. The stop for another writer is this engine's own rule (UP-10 in `docs/behavior.toml`), and the question exists only because of it.
- **Cause.** Both maintenance listing checks (the whole pass and the short one) trusted every listed file up to the newer of the staged and the confirmed transaction. That was sound while maintenance ran only with uploads idle, when staged and confirmed are the same. Since uploads go a slice a tick (`docs/decisions/D217.md`), maintenance takes turns while a staged file waits or is in flight, and the range between confirmed and staged holds ids the engine has staged and the replica has not taken from it.
- **Choice.** A listing whose newest file is above what the uploader confirmed is not planned from: no compaction, snapshot or delete takes that file as input, and maintenance lists again after the retry interval. The file is judged where it always was, by the uploader, which compares bytes when its create-only put of that id is refused or when it lists (`crates/core/src/upload.rs`): its own file (a put whose answer was lost) is confirmed and maintenance goes on; another writer's stops the engine. A file past everything the engine staged still stops maintenance at once, as before.
- **Not chosen.** Stopping from maintenance as soon as it sees such a file. The file may be the engine's own, published by a put whose answer was lost, and telling the two apart means reading and comparing the bytes, which the uploader already does on its next step. A second place that judges would be a second rule to keep in step with the first, and a stop made without the comparison would be a stop for an ordinary lost response.
- **Why.** The uploader is the one place that knows which bytes this engine wrote. Maintenance needs only to keep its hands off what has not been judged, and waiting is the rule it already follows for a listing a read contradicted. No new stop, no new state, nothing written to disk.
- **Cost accepted:** a maintenance pass that lists before the uploader has judged a file is spent: one listing, and its work is late by the retry interval. With a file in flight for many ticks over a published copy of itself this can repeat until the send ends, a listing each time. While the uploader waits out a long retry of its own, maintenance waits with it.
- **Revisit if:** the uploader stops judging a refused put by the bytes, or maintenance is given a way to run that does not list.
