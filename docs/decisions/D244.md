## D244. An upload to a directory is written one block behind, on a thread (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5) · It adds `FsStore::with_write_behind` and `replica::Config::write_behind`

- **Question:** a first start to a file replica builds three files (staged level 0, its copy, level 9), and each upload's bytes were written on the engine's thread, so reading, checking and compressing the next block waited for the disk. Should the directory store write on a thread of its own?
- **What Go does, and why:** Go has no write-behind. It streams on goroutines, and the kernel's page cache absorbs the writes. The engine here is one thread by design (sans-IO, one unit a tick), so what Go gets from the runtime this store has to ask for.
- **Choice:**
  1. `FsStore::with_write_behind()` makes each upload gather 1 MiB and hand it to a thread that appends blocks in order. The hand-off has no buffer: at most one block is being written and one is being filled (2 MiB an upload; the heap measured 3 to 4 MiB more at 4 GiB).
  2. A failed write is returned by the next `write` or by `commit`; the thread writes nothing after it. `commit` waits for the thread and then takes the same steps (mtime, fsync, size check, publish); `abort` and drop wait for it before the scratch file is removed.
  3. Off by default. The library and the simulator keep one thread. The binary turns it on for a file replica and for the staging directory when the machine has more than one core (`replica::Config::write_behind`, no YAML key). Failing to start the thread fails the upload, which the engine retries as any upload failure.
- **Not changed:** every chunk is still verified by the engine before it is written; the file is still checked against its size and token before it is published; the order of bytes in a file; the store traits.
- **Measured** (Linux, 4-core EPYC, ext4, release builds, file replica, 4 GiB first start to "snapshot complete", interleaved pairs, order alternated, against main a1889fede built on the same box):
  - Random pages, 6 pairs: wall -32.6% [-35.1, -30.0] (about 54 s to 37 s), CPU +12.0% [+10.7, +13.3], peak anonymous memory 19 to 22 MiB.
  - Text-like pages, 6 pairs: wall -4.3% [-8.7, +0.4] (not resolved), CPU +9.4% [+5.7, +13.3].
  - A second build that also reused each written block's memory gave the same (random -27.0% [-35.8, -17.1], CPU +10.4%; text -4.1%, CPU +7.9%, 5 pairs); it was dropped for lack of a gain.
  - The extra CPU is the copy into a block and the thread's own work. Wall resolution is 0.5 s.
- **Cost accepted:** about 10% more CPU for a first start (random data, where the wall is I/O bound, wins a third; text data, bound by compression on one core, gains little); one thread and 2 MiB per open upload; a hung mount now blocks `commit` and drop, where it blocked the write.
- **Checked by:** `write_behind_writes_every_byte_in_order_in_whole_blocks`, `write_behind_reports_a_failed_write_and_writes_nothing_after_it` and `a_write_behind_upload_commits_its_bytes_and_an_abort_leaves_nothing` (crates/store-fs/src/tests.rs); the planted bug `write-behind-drops-the-last-block`.
- **Revisit if:** the text-like case needs the compression moved off the engine thread (a worker pool for `pack`), or a measurement on macOS shows the thread costs more than it saves (the studio runs there are CPU-bound).
