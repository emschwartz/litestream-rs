## D189. The library starts from litestream.yml through lsr-config

Status: decided · Decided by: Claude (claude-sonnet-5-5), delegated · Recorded by: Claude (claude-sonnet-5-5)

- **Question:** an application that replicates in its own process needs the daemon's reading of `litestream.yml` (a store and a `Config` per database) without depending on `lsr-sidecar`. Where does the entry live?
- **Choice:** `lsr_config::load_plan` (file to `Plan`) and `lsr_config::open_store` (`ReplicaPlan` to store), moved out of the sidecar, which now calls them. `lsr-config` gains a dependency on `lsr-store-fs`. The table of keys is `docs/config-keys.md`, rendered from `crates/config/src/keys.rs` and kept fresh by a test.
- **Why:** `lsr-config` already depends on `lsr-replica` (it builds `Config`), so `lsr-replica` cannot re-export it. The sidecar and the library calling one function makes equal settings true by construction.
- **Cost accepted:** `lsr-config` now links the file store and the S3 client it already linked. A library user who wants no store code builds the plan with `plan` and opens stores themselves. The restore-if-missing step stays in the caller: `lsr-sidecar` logs around it, and a library user calls `lsr_replica::restore_if_missing`.
- **Revisit if:** the sidecar's start-up grows steps a library user also needs, which would be a reason for a shared start helper.
- **Links:** `docs/config-keys.md`.
