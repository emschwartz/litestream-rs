## D242. A restore reads each file through one GET, verified as it arrives (delegated)

Status: decided · Decided by: Claude (claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5)

- **Question:** a restore read each file as ranged GETs of 4 MiB, eight in flight (`READ_CONCURRENCY`). A 4 GiB snapshot was 1024 GETs where Go sends one, and the eight bodies in flight held 32 MiB. How should a restore read a file?
- **What Go does, and why:** one GET per file. `Restore` reads each file through `internal.NewResumableReader` (`replica.go:836`), which opens the whole object with `OpenLTXFile` and decodes it as it streams; a body that fails part way is opened again from the bytes already read. Go is right here, and the extra requests were lsr's.
- **Choice:**
  1. `ObjectStore::read_stream(key, offset)` hands out an object from an offset to its end as pieces of the length asked, in order (`crates/core/src/store.rs`, `ReadStream`). The default is a ranged read per piece, so a store that bills nothing per request needs no code; the S3 store overrides it with one GET (`crates/store-s3/src/store/stream.rs`), and every wrapper forwards it (retry, the fault roles, the replica's erased and metered stores).
  2. A restore takes each file from one stream, a 4 MiB chunk at a time (`LtxRead::read_streamed`). The decoder, the checks and the order are the ones a chunked read had: pages reach the sink, which is unpublished; a file counts only once its trailer checksum over the whole file verified; the sink is published only after every file verified and the end-state checksum matched. Nothing streamed is trusted before its file verifies.
  3. A body that ends before its declared `Content-Length` is `Transient`, never the end of the object. The retry layer opens a new GET from the bytes already handed out (`bytes=N-`), as Go's resumable reader does, and the policy bounds it as any read. A 206 for another range is refused; a 200 to a ranged GET (a server that ignored `Range`) is read from the offset.
  4. The transport reads the body from the connection as pieces are taken, with no `MAX_BODY` limit. Its bounds are those of D235: each socket read is bounded by the stall deadline (60 s), and the whole body by the cap of its declared length at 16 KiB a second, counted from the response head. A 4 GiB body has 60 s plus 262 144 s (about 73 hours), so a body that keeps moving is never cut, and one that stops fails at the stall bound. reqwest bounds each chunk by the stall deadline and the body by the same cap.
- **Cost accepted:** the eight-wide read-ahead is gone, so on a link whose latency dominates its bandwidth a restore is one stream's throughput, not eight requests'. Go has the same. `read_many` stays for batches that need it; nothing in a restore uses it.
- **Measured:** requests for a restore are one GET per file of the chain (a 4 GiB snapshot: 1 GET, was 1024). Restore heap is one 4 MiB chunk plus margin, flat from 72 to 144 MiB through the real client (4.2 MiB, was up to 35 MiB) and from 16 to 64 MiB in the core gate (4.1 MiB).
- **Tests:** core `gates::restore_of_a_chain_sends_one_request_per_file`, `gates::restore_through_the_retry_layer_reads_a_file_in_one_request`, replica `gates::restore_through_the_public_entry_reads_each_file_in_one_request`, store-s3 `gates::restore_reads_each_file_in_one_get`, `memory::a_restore_through_the_real_client_holds_one_chunk`, `stream::cases::*`, `store::cases::a_stream_*`, core `retry::tests::a_stream_*`, `ltx_read::tests::a_streamed_read_*`; plants `stream-short-body-taken-as-end`, `stream-resumes-from-the-start`, `restore-reads-a-request-per-chunk`, `erased-store-drops-the-stream`.
- **Revisit if:** a restore over a high-latency link proves slower than Go's single stream by more than measurement noise, or a store bills per byte in a way that makes ranged reads cheaper.
- **Links:** D199, D235; `crates/core/src/ltx_read.rs`, `crates/core/src/retry.rs` (`Resuming`), `crates/store-s3/src/ureq_transport.rs` and `reqwest_transport.rs` (`open`).
