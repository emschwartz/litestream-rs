## D208. An upload's part size grows to fit 10000 parts, and an object over 5 TiB is refused first (delegated)

Status: decided · Decided by: Claude (claude-sonnet-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-sonnet-5-5)

- **Question:** S3 takes 10000 parts in one upload. At the 5 MiB default part, a staged file over 48.8 GiB uploaded all it could, was refused at part 10001, waited and sent the same bytes again for ever. The file's length is known before its upload starts. What does the store do with it?
- **Go:** a level-0 upload hands the AWS SDK uploader a sized, seekable file (`s3/replica_client.go`, `uploadSizedLTX`), and the SDK raises the part size to `length / 10000 + 1` when the configured one would need more parts. Go has no ceiling there other than S3's 5 TiB. The review that raised this said Go has the same ceiling; for a sized file it does not.
- **Choice:** the length rides on a new `ObjectStore::begin_sized_upload` (`begin_upload` is the same call with no length). The S3 store plans the part size once per upload (`crates/store-s3/src/part_plan.rs`): the configured size, or the smallest size that fits the length in 10000 parts, never below the configured size. A length over 5 TiB is refused by `begin` with the new `StoreError::ObjectTooLarge` before any request is sent. The engine reports it as `StoreRefused`.
- **Memory:** an upload holds up to `concurrency` parts, so the bound is `concurrency x max(part size, length / 10000)`. It exceeds the configured part only for a file over `10000 x part size`: 48.8 GiB at 5 MiB, 977 GiB at 100 MB (the trial's setting, where it never applies). At 5 TiB the part is 524 MB, 5.5 GB at a concurrency of 10. The branch `claude/memory-floor` makes upload memory independent of the part size by streaming parts from the staged file; this change does not touch that and its bound term reads the same after it.
- **Cost accepted:** a file whose length is not known when its upload begins (a compaction's output, still being encoded) is cut at the configured part and still meets S3's refusal at part 10001; no run writes 50 GiB to test it. `ObjectTooLarge` has no cause of its own in health: it reports as `store_refused`, because a new cause needs a new response setting, which is user-visible vocabulary. If it were wrong, an operator sees `store_refused` and no sizes; the typed error carries them to library callers.
- **Options considered:** a part size from the database's size in the configuration (the review's workaround), which asks an operator to know the compressed size in advance; checking the size in the engine instead of the store, which would put an S3 limit in the engine.
- **Revisit if:** a store with another limit is added, or compaction outputs can exceed 48.8 GiB.
- **Links:** `crates/store-s3/src/part_plan.rs`, `docs/BEHAVIOR.md` UP-20 and UP-21.
