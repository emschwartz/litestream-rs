## D233. A multipart upload keeps its parts in flight between ticks, and a part's MD5 is taken on the thread that sends it (delegated; amends D217, D222)

Status: decided · Decided by: Claude (claude-fable-5-2, finished by claude-opus-5-5), **delegated**; the owner can overturn it · Recorded by: Claude (claude-opus-5-5) · It changes the public `Upload`, `Reread` and `Transport` traits, so it carries both outside reviews

- **Question:** a multipart upload sent its parts in batches inside the write that filled a batch: the engine thread hashed every part, started a scoped thread per part (`s3-batch`), and waited for the whole batch before it read another byte. Measured on main: no part was in flight for 79 to 88% of each upload's span, and MD5 was 42% of the engine thread's time on a staged send (LZ4 decode 31%). How do parts stay on the wire while the engine reads the next ones, without a tick that waits?
- **What Go does, and why:** the AWS SDK's uploader (`feature/s3/manager`, `upload.go`) starts `Concurrency` workers on a channel and feeds them parts continuously; the producer waits only when the channel is full. A staged file is cut into section readers, read while sent; a streamed one is copied into pooled buffers (D232). Go sends no `Content-MD5` on parts. First error wins, the workers drain, then Complete or Abort. Taken: the continuous feed and the section reads. Not taken: a producer that blocks, since the engine is one thread that must keep syncing the WAL (D217).
- **Choice:**
  1. A part starts the moment it is whole and a lane is free, and stays in flight while the engine goes on. Each store has one sender: at most `concurrency` threads (`s3-part`), started on demand and kept, fed through a queue whose submitters bound it (`crates/store-s3/src/lanes.rs`). It replaces the threads spawned for every batch.
  2. `Upload::flight(rest)` (default `Ok(Idle)`) says where the parts are and never waits: `Room`, `Full` (a whole part waits for a lane: the slice ends and the tick goes on to its WAL step), or `Idle`. After the engine has verified the whole file it says `Rest::None`, the last part starts, and the commit (CompleteMultipartUpload) runs once nothing is in flight. A part that ends wakes the replicator's park.
  3. A part's MD5 is computed on the thread that sends it. `Reread::open` gives each part an owned reader; the store reads the part twice more (a hash pass, then the send) and every 256 KiB cell must match the length and CRC-64 the engine's first read saw, on both passes, before a byte of it is hashed or sent. `Content-MD5` then binds what was sent. `commit_from` is deleted.
  4. Every exit but a drop waits for the parts it started: an abort, a failed commit, a stop. So no staged file is deleted under a reader (`Unsent`) and no part lands after an abort. A drop does no I/O; the id goes on the orphan list when the last part lets go, and the boot sweep of abandoned uploads first waits for this process's parts to end.
  5. Any failure restarts the file from its first byte, as before (D217).
- **Reviews (on the design, before code):** Codex (GPT-6): "build with changes"; its strongest point, that the boot sweep could abort an upload whose part was still on the wire after an engine rebuild, was true and is fixed (item 4). It disagreed with moving the MD5 off the first read. Gemini (gemini-4-argon): "build with these changes": `Unsent` with sibling parts in flight, a stall at full width, and the simulator's per-tick judges, all taken. The parent session ruled the MD5 may move if the second read is checked against the first with something stronger than a per-part tally; the per-cell CRC-64 of item 3 is that check, confirmed before each part's request starts.
- **Simulator:** before this the simulator's S3 replica never sent a multipart upload (its part size was the 5 MiB minimum and its files are small). It now runs the S3 store at a tiny part size over the in-memory bucket, with lanes the history drives: a started part stays started until the engine next asks its upload or the store waits itself, and the seed lands none, some or all of them in a drawn order; a crash lands or loses each one. Two new judges: no part may reach an upload that is no longer open, and a sweep that returned leaves no upload open. Explicit scenarios in `crates/sim/tests/sim/parts.rs`.
- **Measured:** studio (macOS arm64, M1 Max), local MinIO, first start of a 4 GiB database of random pages until the level-9 snapshot is in the bucket, 8 interleaved pairs per setting against the code before this change (main with the held-open staged file it builds on), after 4 A/A pairs each; the box was shared with other work (others used 0 to 5 cores during a run). Default settings: wall -25.5% [-36.2, -13.0], not resolved (A/A -13.1% [-37.2, +20.0]); CPU -1.2% [-4.6, +2.3]; peak footprint -8.8% [-17.5, +0.9], not resolved. A large part size with ten parts at once: wall -4.7% [-6.5, -2.8] (A/A -2.3% [-4.9, +0.4]); CPU +0.2% [-1.0, +1.4]; peak footprint 987 MiB to 218 MiB, -78.0% [-78.0, -77.9] (A/A -0.04% [-0.19, +0.12]). Not registered beforehand, read from the same runs: the level-0 file reached the bucket 43% sooner at the defaults (10.4 s to 5.9 s, [-47.8, -38.8]) and 41% sooner at the large setting (9.6 s to 5.7 s, [-42.9, -39.8]). The share of an upload's span with no part in flight and the engine thread's LZ4 share after the change were not measured.
- **Cost accepted:** a stop past its deadline can wait for a part's request to end (at most the transport's timeout); a tick may now end while parts are out, so the WAL step runs sooner; three reads of each staged part instead of two (the later two from the page cache).
- **Open:** the reqwest client still buffers a streamed body; a single PUT below one part still runs inside the tick; a thread the OS refuses narrows the sender and is not reported to an operator; whether Linux ever refuses an `s3-part` thread is not checked.
