## D193. A maintenance check lists level 0 and a tail, and the whole replica every 15 minutes

Status: decided (the design, by the owner, 2026-11-24) · Decided by: owner; the 15-minute interval is Claude (claude-sonnet-5-5), delegated · Recorded by: Claude (claude-sonnet-5-5)

- **Question:** every 15-second check and every compaction window listed every level in full, so a replica with 20,000 level-1 files cost about 25,000 LIST requests and about 20 million entries an hour while uploads continued ([#324](https://github.com/emschwartz/litestream-rs/issues/324)). How does the engine ask the store for less without a shorter history ever being decided on?
- **Choice:** the engine keeps, in memory only, the newest file it knows at each level (about nine small records), learned from full listings and from its own confirmed uploads. The check and the compaction windows list level 0 whole and, at levels 1 to 8, only after the newest file known there (level 1 also after a cursor that keeps every file that could cover a level-0 file). Level 9 is always whole. A whole listing runs at boot, after any fault or refused upload, before a snapshot job or a delete at level 1 to 8 or of a snapshot, when a retention wake comes, and every 15 minutes as the backstop. The records are dropped on any fault, stop or restart; nothing is written to disk.
- **Why:** it fixes the cost at its cause (the request count and size no longer grow with the history) and keeps no new state on disk, so a restart or fault can only cost one whole listing. A short pass deletes only level-0 files, and only a subset of what the whole rules delete: its anchor, floor, cover and stop rules each keep more than the whole rules, and a remembered record is never a cover, since it may name a file that is gone. The retention gate is read from the last whole listing, at most 15 minutes old. The argument and the per-delete-kind table are in `crates/core/src/maintain/short.rs`; `maintain/retain/tests/short_view.rs` checks the subset property over random replicas.
- **Measured** (one simulated hour of one commit a second, `actor/tests/listing.rs`): at 2,900 level-1 files, 10,773 requests and 2,952,201 entries before, 3,161 and 227,407 after. At 20,000 level-1 files, about 25,000 requests before (the run is too slow to finish in the dev profile, and its entries, scaled from the 2,900 run, are about 20 million), 3,230 requests and 295,807 entries after. Monthly, about 18.3 million and 7.8 million requests before, about 2.3 million after.
- **Cost accepted:** another writer's file at a level 1 to 8 that sorts below the newest known file there is seen only at the next whole listing, at most 15 minutes later. Another writer's level-0 file is still seen by every pass. A second writer already stops the engine at its next upload; this only bounds how late a writer that uploads nothing is noticed at the compaction levels. The interval is an entries-versus-delay trade: a whole listing at 20,000 files is about 21 requests and 20,000 entries, so 15 minutes adds about 84 requests and 80,000 entries an hour (a quarter of the 295,807 above), 5 minutes would add about 250 requests and 240,000 entries, and 60 minutes would save about 60,000 entries.
- **Revisit if:** a store charges per entry returned rather than per request, which would favour a longer interval, or a user needs another writer noticed faster, which would make the interval a setting.
