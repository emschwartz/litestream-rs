## D193. A maintenance pass lists only what its decision reads, and the whole replica every 15 minutes

Status: decided (the design, by the owner, 2026-11-24) · Decided by: owner; the 15-minute interval, the 120-second default retention check and the carried listing are Claude (claude-sonnet-5-5), delegated · Recorded by: Claude (claude-sonnet-5-5)

- **Question:** every 15-second check and every compaction window listed every level in full, so a replica with 20,000 level-1 files cost about 25,000 LIST requests and about 20 million entries an hour while uploads continued ([#324](https://github.com/emschwartz/litestream-rs/issues/324)). How does the engine ask the store for less without a shorter history ever being decided on?
- **Choice:** the engine keeps, in memory only, the newest file it knows at each level 1 to 8 (about eight small records), learned from whole listings and from its own confirmed compactions. A pass lists only what its decision reads: level 0 whole; a compaction level's own tail (after the newest file known there) and the level below it (after that level's last transaction), only while that level's window is open and it has sources; level 1 after a cover cursor and level 9 whole when level-0 retention is due. A pass with nothing due lists nothing. The pass after this engine's own compaction reuses a listing at most five seconds old (it keeps the time it was really made, so a run of own jobs cannot stretch it), but never for a pass that may delete: a delete is decided from a listing made in the same pass. A level whose window one of its own outputs closed is quiet until the next window. Level-0 retention is checked every `l0-retention-check-interval` as set, exactly; when unset it is every 120 seconds, not Go's 15 s, and it waits for a pass with no compaction to plan (a whole interval overdue at most). A whole listing runs at boot, after any fault, refused upload, step back of the clock or change of the retention mode, after a compaction that found an input gone, before a snapshot job or a delete at level 1 to 8 or of a snapshot, when a retention wake comes, and every 15 minutes as the backstop. The records are dropped on any fault, stop or restart; nothing is written to disk.
- **Why:** it fixes the cost at its cause (the request count and size no longer grow with the history) and keeps no new state on disk, so a restart or fault can only cost one whole listing. A short pass deletes only level-0 files, and its deletes are a subset of what the whole rules would delete from the same replica: its anchor reads the newest known file of every level 1 to 8 (a remembered file is read for its age only, never as a cover), and its floor, cover and stop rules each keep more. With a record above the configured top (a level no short pass lists, so the file may be gone) level-0 retention is decided on whole listings only, so a stale record cannot hold the anchor too high. The retention gate is read from the last whole listing, at most 15 minutes old. The argument and the per-delete-kind table are in `crates/core/src/maintain/short.rs`; `maintain/retain/tests/short_view.rs` checks the subset property over random replicas, including a level 1 to 8 newest file younger than the last level-0 file, a stale gate and overlapping files, and holds the reviewed nine-file case that broke the first version.
- **Measured** (one simulated hour of one commit a second, `actor/tests/listing.rs`): at 2,900 level-1 files, 10,773 requests and 2,952,201 entries before, 610 and 161,238 after (about 0.45 million requests a month, from about 7.9 million). At 20,000 level-1 files, about 25,000 requests before (too slow to finish in the dev profile; entries scaled from the 2,900 run are about 20 million), 679 requests and 229,638 entries after (about 0.50 million a month, from about 18.3 million). The gated tests fail above 700 requests and 250,000 entries an hour. Bounded cases also cover an idle writer, a bursty one, retention off (every pass lists the growing level 0 whole, 652 requests and 450,000 entries, as the whole listing it replaced did), busy levels 2 and 3 (1,271 and 281,078), a backlog that starts a chain of own compactions, and a level-0 file no rule deletes (without keeping the cover cursor across whole listings that hour cost 664 requests and 220,427 entries, 59,000 more). A first version of this change that carried listings across several own jobs and into retention passes made 511 and 580 requests; the review found that a delete could then be decided from a listing 24 seconds old, and fresh retention passes cost about 95 requests an hour. At 240 s the unset default would be 562 and 631, still over 600 at 20,000 files with a larger level 0, and a 30-minute whole listing would save about 42 requests at 20,000 and weaken the foreign-file check further; neither was taken.
- **What the second-writer check sees, and when.** Level 0 is listed whole on every retention check (the set interval, or 120 seconds when unset, was 15) and by every compaction pass of level 1 or when level 1 has sources; an upload another writer's file holds is refused at once, as before. A foreign file at a compaction level above the newest file known there is seen by the next pass that lists that level (its next window). A foreign file below the newest known file of its level, a foreign snapshot (level 9 is listed only when the snapshot window opens or retention is due, was every pass), a foreign file at a level above the configured top, and a replica that lost files below the tail are seen only at the whole listing, at most 15 minutes. **Gap accepted:** levels above the configured top (levels 3 to 8 with the default top of 3) are never listed by a short pass; only the whole listing sees them, and the anchor reads the remembered newest file of each, so a foreign file there is noticed up to 15 minutes late and a remembered record of one that is gone is dropped only by the next whole listing. A restore reads the whole replica and never depends on a short pass.
- **Cost accepted:** the delay above, for a writer that uploads nothing at those levels. A second writer that uploads at level 0 is still seen at the retention check or the next level-1 compaction pass (both list level 0 whole; 240 seconds at most) and stops at its next upload. The intervals are entries-versus-delay trades: a whole listing at 20,000 files is about 21 requests and 20,000 entries, so 15 minutes adds about 84 requests and 80,000 entries an hour; the 120-second default check (against Go's 15 s) is the one difference from Go's keys: a set interval is honoured exactly, and docs/differences-from-go.md and docs/config-keys.md say so. A level-0 file lives up to `l0-retention` plus the check interval, so by default up to 4 minutes longer than Go keeps it: the default check waits one more interval behind a compaction job, so the job goes first and the pass lists once, and a set interval never waits. A replica that keeps files above the configured top (from an earlier configuration) has level-0 retention decided only at whole listings, every 15 minutes.
- **Revisit if:** a store charges per entry returned rather than per request, which would favour a longer interval, or a user needs another writer noticed faster, which would make the intervals settings.
