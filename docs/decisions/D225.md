## D225. A busy write lock is not a failed checkpoint, and the engine's own checkpoint never costs a snapshot (delegated)

Status: decided · Decided by: Claude (claude-fable-5-2), **delegated**; the owner can overturn it · Recorded by: Claude (claude-fable-5-2)

A drill ran a steady writer beside the replicator. Again and again the log showed `retrying error=SqliteBusy`, and about a second later `snapshot required cause=GenerationChanged`: a copy of the whole database, uploaded, for a database nothing was wrong with. The retries backed off to five minutes, the checkpoint task was reported degraded as stalled, and a warning said the application had checkpointed the database, which it had not.

**What happened.** A PASSIVE checkpoint holds SQLite's write lock from its barrier (`BEGIN; INSERT INTO _litestream_lock`) to the barrier's ROLLBACK, and writes one frame of its own afterwards, the sequence bump. A writer that waits for the write lock is handed it the moment the ROLLBACK lets go (a SQLite built to block in the kernel on its locks, as the system SQLite on macOS is, gets it at once; one that polls gets it at its next try). The bump then ran on a connection with no busy timeout, was refused, and the checkpoint was counted as failed. The read transaction retaken during the checkpoint was recorded as proving nothing, since only the path that ended with "the WAL header is unchanged after our bump" pinned the position to it. The PASSIVE had copied every frame, so that writer's commit restarted the WAL (new salts), and the next sync found a new generation with no proof of continuity: `GenerationChanged`. The failure also doubled the checkpoint's wait each time, so the WAL grew past the size at which an application's automatic checkpoint would run, and the observer of the application's checkpoints (`crates/core/src/app.rs`) reported a stall under a line that said a checkpoint had happened. A writer that held the lock at the instant the barrier asked for it was counted as a failure in the same way.

- **Question:** what should a checkpoint do when the application holds SQLite's write lock at the barrier or at the bump, and what may its own checkpoint ever cost?
- **What Go does, and why:** Go opens its connection with `busy_timeout` (one second by default, `DefaultBusyTimeout` in `db.go`), so the barrier and the bump wait inside SQLite's busy handler and a writer between two transactions is never seen. A PASSIVE that is still refused at the page or time trigger is logged at trace level (`passive checkpoint skipped`, reason `database busy`) and returns no error: the next sync, a second later, tries again (`checkpointIfNeeded`, `db.go:1529`, `1559`, `1584`). At the truncate threshold a refused PASSIVE is followed by the TRUNCATE in the same call. After a restart of the WAL, Go's `verify` continues in the new WAL with no snapshot when it had synced to the WAL's end (`syncedToWALEnd`) or its last page still matches and no unknown generation lies between. Go never backs a checkpoint off and never calls replication degraded for a busy lock. The reason is plain: a busy write lock means the application is working.
- **Choice:**
  1. *The read transaction retaken under the barrier pins the position, whatever follows.* The barrier keeps writers out from the seal's proof that everything committed is synced until the checkpoint call has retaken the read transaction. So the position is pinned to that hold as the call returns, on every answer but a retake that was lost, and stays pinned through a refused bump, a failed release or a failed step. A WAL the next writer restarts is followed (`Recovered::WalRestarted`), not snapshotted. A `GenerationChanged` snapshot is owed only when a restart happens with no such proof: a boot, a lost read transaction, or damage.
  2. *A refused barrier is an outcome, not a fault* (`CheckpointOutcome::LockBusy`). SQLite is not asked to checkpoint and nothing changes. The checkpoint is asked for again after 10 ms, doubling to the retry interval (one second by default), and the count starts over once a checkpoint gets the lock. No failure is counted, so nothing backs off to minutes, stalls or degrades. The event is `CheckpointDeferred`, a debug line in the sidecar.
  3. *A refused bump is an outcome too.* After a PASSIVE (`Overtaken`): the writer that holds the lock moves the WAL on in place of the engine's frame; the checkpoint counts as run. After a TRUNCATE the engine acts on what SQLite reported: with every frame copied (`checkpointed >= log`) the boundary snapshot that TRUNCATE always takes (D190) is owed to the next sync under its own cause (`BoundaryOwed`), because the new generation has no header to snapshot under yet; with frames left uncopied the WAL cannot restart and the outcome is `Busy`.
  4. *Connections keep a busy timeout of zero.* The rule is older than this entry and is stated in `crates/sqlite/src/lib.rs` and `docs/config-keys.md`: a contended lock is an answer at once and the caller's policy decides what waits, so the engine thread never sleeps inside SQLite, every wait is a deadline the simulator can drive, and an application's lock can never hold a tick. The doubling wait above is SQLite's busy handler moved outside SQLite: the same few-milliseconds first retry, the same slower retries after.
  5. *RESTART and TRUNCATE are unchanged:* no RESTART; TRUNCATE only under `app-readers: none`, only at `truncate-page-n`, only after a PASSIVE there did not restart the WAL.
  6. *The log line is true.* "the application checkpointed the database" is printed for a backfill or a restart the engine did not make. A stall is printed as "the WAL grew past the application's automatic checkpoint threshold with nothing new checkpointed".
- **Why this one:** it is Go's behaviour (skip, try again soon, say nothing loud) without Go's wait inside SQLite, and the pin is not a new rule: it is the proof the protocol already relied on for the path that did work, taken at the moment it becomes true instead of three steps later.
- **Every place the engine concludes that something else changed the WAL, and whether its own actions can reach it:**

  | Inference | Where | Reachable by the engine's own checkpoint? |
  |---|---|---|
  | `GenerationChanged` while running: a new generation with no pinned position | `recover.rs`, `restarted` | Before: yes, after any fault between a PASSIVE's checkpoint call and its last step. Now: not after a PASSIVE. After a TRUNCATE only when a real fault (an I/O error, a lost read transaction) follows the checkpoint call, since a TRUNCATE takes no barrier and proves nothing until its next step |
  | `WalMissing`: no WAL header | `recover.rs` | After a TRUNCATE emptied the WAL and a fault stopped the protocol before any writer wrote a header. A refused bump no longer does this (`BoundaryOwed`) |
  | `LocalRewound`, `PrevFrameMismatch`, `LastPageMismatch`: the WAL at the position is not what was staged | `recover.rs`, `same_generation` | No. The engine writes to the WAL only through SQLite, one frame at a time, and a TRUNCATE of its own that lands inside a sync step is retried as `WalMoved` |
  | `ReadLockViolated`: frames abandoned under a pinned position | `recover.rs` | No by construction: it is the alarm for a broken proof, and it is the check that would fire if the pin above were ever wrong |
  | `WalMoved`, `Synced::IndexReset`: the WAL changed between two reads of one step | `sync.rs`, `checkpoint.rs` | No: the engine's writes and its reads are one thread's steps. Retried, never a snapshot |
  | `ReadTxLost`: the position is pinned to a hold that is gone | `sync.rs` | Only when the engine's own retake fails; the position is then unpinned, which is true |
  | The application's checkpoints: `Backfilled`, `Restarted` | `app.rs` | No: every checkpoint of the engine's, finished or not, resets the baseline (`AppCheckpointObserver::ours`) |
  | The application's checkpoints: `Stalled` | `app.rs` | Indirectly, before: a checkpoint backed off for minutes let the WAL grow past the threshold. It is an inference about an application that checkpoints automatically, and wrong for one that does not unless the replicator is told (`app_autocheckpoint: None`). The line now says what was read, not what was inferred |

- **The simulator.** Its SQLite model already refused the barrier and the bump while another connection held the write lock, but an application could take that lock only between two ticks, never between two of the engine's calls, so a refused bump could be drawn only as an injected error. An injected error counts as damage to the WAL, and every retry excused the snapshots after it, so the needless-snapshot oracle had nothing to say about this defect. Now the application can begin a write transaction it leaves open right before any call of a tick (`AppOp::Spill`, `crates/sim/src/sqlite/in_tick.rs`, and the same on real SQLite in `crates/sqlite/src/testing/real/in_tick.rs`), which is no fault and excuses nothing, and a retry on a busy answer from SQLite no longer excuses a snapshot (`crates/sim/src/run.rs`). The scenarios `bump_overtaken_then_the_wal_restarts` and `write_lock_held_at_the_barrier` are the drill's two shapes with no fault injected.
- **Alternatives:** (a) give the connections Go's busy timeout: the smallest diff, but the engine thread then sleeps inside SQLite for up to the timeout on every contended lock, a wait no deadline bounds and the simulator cannot drive; it also reopens the rule in 4 for every other caller. (b) Take the bump inside the barrier's transaction: the bump would then be rolled back with the barrier, and committing the barrier instead writes a frame before the checkpoint, which Go's protocol does not. (c) Keep failing the checkpoint but cap the backoff: still a WARN and a failure count for an application doing nothing unusual. (d) Never write the bump: Go writes it after every checkpoint (`db.go:1667`) so the WAL moves past the checkpoint at once, and the differential tests compare against that.
- **Cost accepted:** an application that holds the write lock at every attempt (one long write transaction, or writes with no gap at all) defers the checkpoint for as long as it does so, one attempt a second, and the WAL grows meanwhile; Go's busy handler polls more often inside its second and may get in sooner. Each deferred attempt still runs the sync that precedes it. After a TRUNCATE whose bump was refused, a boundary snapshot is taken even in the case where the writer that held the lock rolled back. A sync that must write the engine's frame itself, because the WAL has no header (a boot over an empty WAL, or a boundary snapshot owed before any writer wrote a frame), still retries as a failure while a writer holds the lock without having written one, as Go's sync fails after its busy timeout. An overtaken checkpoint leaves the WAL file at its size for that round: SQLite cuts the file to `journal_size_limit` on the connection whose commit restarts the log, which is then the application's and not the engine's.
- **Revisit if:** a run shows a checkpoint deferred for minutes under a writer that does release the lock between transactions (the wait should then start lower or poll more often), or a `GenerationChanged` snapshot appears in a run with no fault, no restart and no lost read transaction.
