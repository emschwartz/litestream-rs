## Task 8s: rusty-s3 against MinIO

Server: Chainguard's build of MinIO, `cgr.dev/chainguard/minio@sha256:e9cf6b99c226e9539ed0f14b6f00e37b07da153c7ba1f4f8709c807574b471ec` (`minio version RELEASE.2026-11-16T00-11-40Z`, commit ee9fee0715118245ff4d9149c102608653748196, go1.27.4 linux/arm64), pulled as `cgr.dev/chainguard/minio:latest` on 2026-11-20. MinIO no longer publishes images at quay.io or docker.io, so this is a third-party build. **If the digest stops resolving, 8c re-pins and these questions are re-run.** Entrypoint `/usr/bin/minio`, run as `server /tmp/data` with the public defaults `minioadmin`/`minioadmin`, path-style, region `us-east-1`, plain HTTP on 127.0.0.1. Every answer below is "verified on MinIO cgr.dev/chainguard/minio@sha256:e9cf6b99c226e9539ed0f14b6f00e37b07da153c7ba1f4f8709c807574b471ec" unless marked "open: needs Tigris (8t)".

Client: `rusty-s3` 0.12.0 (BSD-2-Clause), `ureq` 3.5.2, `http_status_as_error(false)`. Dependency count for those two alone (`cargo tree -e normal --prefix none | sort -u | wc -l`): 100 lines, 99 packages plus the root. Only licence outside the `deny.toml` allowlist: `webpki-roots` (CDLA-Permissive-2.0), already ruled in by F4 (`ring` is `Apache-2.0 AND ISC`, both allowed).

**Plan correction, features.** The plan says features `rustcrypto`, `xml`. `DeleteObjects`, `ObjectIdentifier` and `DeleteObjectsResponse` are behind rusty-s3's `full` feature (which also pulls `md-5`, `base64`, `serde`, `serde_json`), so 8b needs `rustcrypto` + `full`, not `xml` alone. The 99 packages above are measured with `full`; with `xml` alone it was 92.

1. **Signed metadata header: accepted, byte for byte.** `headers_mut().insert("x-amz-meta-litestream-timestamp", "2026-11-20T15:04:05.123456789Z")` puts `host;x-amz-meta-litestream-timestamp` in `X-Amz-SignedHeaders`; PUT with the header returned 200; HEAD returned the identical value (nanosecond fraction kept). MinIO enforces the signing rule both ways: the header sent but not in the signature, and the header signed but not sent, each returned 400 `AccessDenied` "There were headers present in the request which were not signed". Departure from Go recorded: rusty-s3 signs by query string with `UNSIGNED-PAYLOAD` (Go signs the payload), so a body altered in flight is caught only by Content-MD5 (F7).
2. **Wrong Content-MD5: 400 `BadDigest`** ("The Content-Md5 you specified did not match what we received."). A malformed value (not base64) is 400 `InvalidDigest`. The correct value is 200. The header must be in `headers_mut` (lowercase `content-md5`) so it is signed and sent. 8b maps BadDigest to a checksum cause and InvalidDigest to a refusal.
3. **Multipart: matches.** Create 200 with an UploadId. Each part's ETag header was the quoted lowercase hex MD5 of the part bytes (5 MiB part and a 9-byte tail, both matched). Complete returned 200, header and body ETag `"528dc964193f0e986d6713e3297a1f51-2"`, equal to the MD5 of the concatenated part MD5s plus `-2`. The body's ETag is XML-escaped (`&#34;` quotes); `CompleteMultipartUploadResponse::etag` is what 8c should read. HEAD size 5242889.
4. **Last commit wins.** Two PUTs to one key: the second survives. Two multipart uploads to one key, initiated A then B, completed B then A: **A survives** (the last completed, not the last initiated). Both completes returned 200. Not representative of providers that order by initiate time: open: needs Tigris (8t).
5. **Listing: keys round-trip.** `rusty-s3` sends `encoding-type=url`; MinIO URL-encodes keys in the XML (`q5/foo+bar/a%2Bb.ltx`, `q5/pct%2520lit`) and `ListObjectsV2::parse_response` decodes them: `"q5/foo bar/a+b.ltx"`, `"q5/plus+key"`, `"q5/pct%20lit"` and `"q5/ünï"` all came back exactly. `start_after` in the response is decoded too. `start-after` of `q5/pct%20lit` with `max-keys=2` returned `q5/plain`, `q5/plus+key`, `IsTruncated=true` and a `NextContinuationToken`, so seek plus paging works (F8). Order is by raw key bytes.
6. **Ranges.** `bytes=100-200` on a 10-byte object: 416 `InvalidRange` (body carries `ActualObjectSize` 10). `bytes=10-20` (start equals length): 416. `bytes=5-100`: **206**, clipped, `Content-Range: bytes 5-9/10`, 5 bytes (a range that straddles the end is not an error; the reader must check the length it got). `bytes=0-9`: 206 with 10 bytes. Zero-byte object: `bytes=0-0` and `bytes=0-` both 416 `InvalidRange`; a plain GET is 200 with an empty body.
7. **DeleteObjects quiet with a missing key: no `<Error>`.** Content-MD5 from `body_with_md5` accepted. One existing and one missing key, quiet: 200 with an empty `<DeleteResult>`; parsed `deleted` 0, `errors` 0.

Not covered here (open: needs Tigris, 8t): signature acceptance against Tigris's own region and host style, provider differences in question 4, and lowercase metadata header normalisation on a provider other than MinIO.

Provider questions:

- Q1 (what the plan left to the credentialed run for presigning): answered by item 1.
- Q2, metadata on a 206: yes. A ranged GET answers 206 with `x-amz-meta-litestream-timestamp` (and the ETag), so `read_with_stamp` needs no HEAD.
- Q3, multipart LastModified: the completion time, not the initiation. Initiated at server clock T, completed at T+3 s: the listing says T+3 s.
- Q4, metadata in the listing: no. `ListObjectsV2` with `metadata=true` returns key, ETag, size, owner, storage class and LastModified only, so a stamp still needs `stamp` or `read_with_stamp` (ruling G1 as built).
- Q5, CopyObject: a copy keeps the user metadata under the default directive; `x-amz-metadata-directive: REPLACE` without metadata drops it.

Other findings, each pinned by a test:

1. Tigris starts multipart at 16 MiB in our store (`Provider::Tigris`). The shared cases use `part(h)` so a body is large enough to go multipart there; at 5 MiB the same cases pass by sending one PUT.
2. A multipart upload that has no part yet is not created at all, so a dropped upload below one part leaves nothing to abort. ListMultipartUploads does list an open upload (200, no `prefix` accepted from our raw signer).
3. Aborting an unknown upload is 404 `NoSuchUpload` (MinIO says 204). `classify(StoreOp::Upload, ..)` on that response is `Refused { status: 404 }`, not `Ok`; the store's abort path handles the 404 itself. Pinned by `abort_of_an_unknown_upload_is_not_a_failure`, which accepts 204 or 404.

## S1: the wal-index through SQLite's own mapping

Run on 2026-11-20, Linux 6.18 x86_64 (4 KiB pages, so one 32 KiB region per `mmap`), SQLite 3.54.1 as bundled by `libsqlite3-sys` 0.40.0 under rusqlite 0.43. The probe is `crates/compat/tests/shm_mapping.rs`, 11 tests, part of `just check` (the file runs in about 0.1 s to 1 s; the race test is the longest). Its `unsafe` is confined to that file under one `#![expect(unsafe_code)]`, a `// SAFETY:` comment per block, one operation per block. `cargo nextest run -p lsr-compat --test shm_mapping --no-capture` prints the values quoted below. Line numbers are `sqlite3.c` from the bundled crate.

How the probe reads, which is what task 1 should copy:
- Guard first, in this order: `sqlite3_txn_state(db, "main")` is READ or WRITE, `PRAGMA main.journal_mode` is `wal`, `PRAGMA main.locking_mode` is `normal`. Only then is `xShmMap` guaranteed to find `pShm` already set and return `apRegion[0]` under the node's mutex with no file operation (`unixShmMap`, 45760).
- `SQLITE_FCNTL_FILE_POINTER` (192592) gives the pager's own `sqlite3_file*`. `pMethods` null is refused; `iVersion` is read through a raw field pointer (never a reference to the whole table, so a shorter version 1 table is not read past its end) and below 2 is refused; `xShmMap` null is refused; a non-OK return (`SQLITE_READONLY` included), a null region, or a misaligned one are refused. Each refusal is a variant of `Refusal`.
- The region is borrowed for the life of the `&Connection` and read as `&[AtomicU32]` (8,192 words). One read is `walIndexTryHdr`'s order: twelve relaxed loads of copy 0, a `SeqCst` fence (SQLite's `walShmBarrier` is a full barrier), twelve of copy 1, a fence, then `nBackfill` (word 24). Then SQLite's checks: copies equal, `isInit` set, `iVersion` 3007000, and `aCksum` (`walChecksumBytes` native over the first 40 bytes). A failed check is `NotReady` (`Torn`, `Uninitialised`, `BadChecksum`, `UnknownVersion`), which a caller retries as `SourceError::Busy`.

Answers:

1. **Same region: yes.** Two connections in one process, each in a read transaction, get the identical pointer from `xShmMap` (one `unixShmNode` per inode, one `apRegion[0]`). A commit through the second connection moves `mxFrame` and `iChange` (by one) in the first connection's mapping, with no call in between (`the_mapping_is_the_one_every_connection_in_the_process_uses`).
2. **Same values as `LiveSqlite`: yes, at every step.** Under the library connection's read transaction, `mxFrame`, both salts and `nBackfill` from the mapping equal `LiveSqlite::committed()` after: open, three commits, an outside PASSIVE `(0,4,1)` (backfilled 1, the pin's mark), RESTART `(1,4,1)` and TRUNCATE `(1,4,1)` while pinned (busy, salts unchanged), a commit, the library ending its read and `LiveSqlite` checkpointing to backfilled 5 of 5 (its new read takes mark 0), an outside RESTART `(0,5,5)` that is not blocked, the next commit (salts `s1+1` and a new `s2`, `mxFrame` 1, `nBackfill` 0: the WAL restarted), the library's read retaken, and an outside TRUNCATE `(1,1,0)` while pinned (`the_mapping_agrees_with_the_file_read_across_checkpoints_and_a_restart`). The mapping taken before the library's read ended stays valid and keeps tracking: the region lives as long as the connection's WAL is open, not the transaction. Also "no WAL yet" agrees: see 4. Byte order as `LiveSqlite` documents: `mxFrame`, `nBackfill` and the checksum native, the salts big-endian.
3. **No descriptor opened or closed: yes.** `/proc/self/fd` targets under the database's directory are the same before and after 50 map-and-read cycles interleaved with commits and an outside PASSIVE (one `db` and one `db-wal` per connection, one `db-shm` for the process), and the process's POSIX locks on the database (`READ 1073741826-1073742335`, the shared byte range) and on `-shm` (`READ 123 123`, `READ 128 128`: a read mark and the DMS lock) read from `/proc/locks` are unchanged. A transient descriptor would not show in the fd list, but its close would have dropped those locks, so the lock list is the check that it never happened (`mapping_and_reading_opens_and_closes_no_descriptor`).
4. **Not initialised, or methods missing: typed refusals, no call.** No read transaction is `NoReadTransaction`; `locking_mode=exclusive` (heap-memory wal-index) is `NotNormalLocking("exclusive")`; a rollback-journal database is `NotWal("delete")` and no `-shm` is created (`the_probe_refuses_every_connection_whose_wal_index_is_not_mapped`). Synthetic tables give `FileNotOpen` for a null `pMethods`, `OldIoMethods` for `iVersion` 0 and 1, `NoShmMap` for version 3 without the method (`missing_methods_are_refused_before_any_call`). Why the guard must come before the call: unguarded `xShmMap` on a rollback connection returned `SQLITE_OK`, a null region, and **a new descriptor on a newly created `rollback-shm`** (`unixOpenSharedMemory`, 45606), which then needs `xShmUnmap` (a close) to undo, and `unixClose` asserts `pShm` is null (43021) (`unguarded_shm_map_on_a_rollback_connection_opens_a_descriptor`). "No WAL yet" in the realistic sense (a WAL database whose last connection closed and removed `-wal` and `-shm`): the first read transaction runs recovery, the header maps initialised with `mxFrame` 0, salts 0, `nBackfill` 0, and `LiveSqlite` reads the same (`a_database_with_no_wal_yet_maps_an_initialised_empty_header`). A zeroed region is `Uninitialised`; a copy changed in one word is `Torn`; both copies changed alike is `BadChecksum`; another version is `UnknownVersion` (`header_checks_refuse_what_sqlite_refuses`).
5. **Racing a writer: consistent or retryable.** A second thread's connection commits 2,000 times (`synchronous=OFF`) while the test thread reads the mapping until it finishes. Three runs: 27,026 checked reads and 886 `Torn`; 27,092 and 878; 42,589 and 960 (about 3% torn). No `BadChecksum` and no `Uninitialised`; every checked read had the same salts and `iChange` and `mxFrame` never went backwards; the final read was `iChange` 2001 (`reads_racing_a_writer_are_consistent_or_retryable`). So the copy compare is not theoretical: a reader that skips it would use a half-written header about once in 30 reads under write load. `LiveSqlite`'s file read compares the copies too but does not check `aCksum`; `CommittedRead`'s doc says it must, and the probe does. Threading constraint: the `&Connection` is `!Sync` and the region is borrowed from it, so the reads happen on the thread that owns the reader; other connections and processes write concurrently, which the atomic loads plus the copy and checksum checks are for. Rust's memory model cannot see writers in other processes or in C, so atomic loads are the least wrong reading, the same stance as SQLite's `volatile` and `memcpy`.

**The fallback is not needed, and it would also work.** One `-shm` descriptor opened after the read transaction and kept open reads the same header as the mapping across five commits and changes no lock (`one_long_lived_shm_descriptor_reads_the_same_header`); the test closes it only after every connection. The plan should use the mapping: no descriptor at all, the header SQLite itself reads, and nothing to leak. The descriptor fallback stays for a VFS whose methods lack `xShmMap`, which the guard reports.

**`LiveSqlite` today opens and closes a `-shm` descriptor on every `committed()`** (`File::open(&path).and_then(|mut file| file.read_exact(..))`, dropped at the end of the expression), and holds a database descriptor (`db: File`, opened in `open`, closed when the last clone drops). Measured: the process held `READ 123 123` and `READ 128 128` on `-shm` before one `committed()` and nothing after (`live_sqlite_file_read_drops_the_process_shm_locks`). SQLite still believes it holds them, so another process could take the DMS lock exclusively and rebuild the wal-index under live readers. Test support only, and phase 3 deletes it, but it must not be the model for `lsr-sqlite`.

Side finding for ruling P0: readers that began on an empty WAL hold read mark 0, and an outside PASSIVE then backfilled nothing (`(0,3,0)`), because a mark-0 reader reads the database file, which backfill would overwrite. Mark 0 blocks backfill but not a restart, as P0 says.

For task 1: `lsr-sqlite`'s `shm.rs` is this probe's `check_reader`, `file_pointer`, `shm_map_of`, `map` and `read_header`, with `NotReady` mapped to `SourceError::Busy`, the refusals to `OpenError`, and the map taken once at open (after the first read transaction) and kept for the reader's life. The region is only valid while the reader's WAL is open, so the reader connection must never change its journal mode or close while the region is borrowed; owning the connection inside `Sqlite` gives that by construction.
